# 为什么多数 Agent POC 无法上生产？

## 研究问题

**核心问题**：为什么大多数 Agent POC 演示阶段表现惊艳，但一旦投入生产环境就问题频出甚至完全不可用？

这个问题的本质是：POC 验证的是 Agent 的**原始能力上限**，而生产要求的是 Agent 的**可靠运行下限**。两者之间横亘着一道系统性鸿沟。

## 六大失败类别

### 1. Harness 体系缺失

**Evidence**：Anthropic 明确指出"Agents are incapable of accurately evaluating their own work"——Agent 无法准确评估自身产出质量，因此外部化的约束和反馈不是可选增强，而是 Agent 可靠运行的必要条件。在裸用 Agent 模式下，质量瓶颈从"写代码"转移到"看代码"，而人工审查速度远低于 Agent 产出速度^[raw/articles/harness-engineering-90-percent-ai-coding-rate.md]。

**具体表征**：
- POC 阶段靠人工全程盯着，每步手动确认，自然平稳
- 生产环境无人值守，Agent 自行决策后产出质量随上下文窗口填充率超过 40% 快速衰退（One-shot Syndrome）
- 没有质量门禁，Agent 产出"语法正确、风格统一，但业务语义存在微妙错误"的代码

**应该怎么做**：
- 构建完整 Harness 体系（上下文架构 + Agent 专业化 + 持久化记忆 + 结构化执行四根支柱）
- 将质量保障从"依赖人工检查"转变为"依赖机器验证"——"一切不可被机器验证的约束，在 Agent 执行中都是无效约束"
- 设计 10 阶段 Pipeline，每个阶段之间有明确的质量门禁

---

### 2. 评估体系错配（Eval Mismatch）

**Evidence**：Harness 报告数据揭示了一个反直觉的事实——**81%** 的工程领导者表示，编码节省的时间中有相当一部分现在被用于审查 AI 的工作产出；开发者每天有**近三分之一**的时间花在审查 AI 输出的"隐形工作"上。传统 productivity metrics（输出量、周期时间）只反映代码交付，却完全看不见审查 overhead。

**具体表征**：
- POC 阶段评估指标是"功能是否跑通"，不看代码质量和维护成本
- 生产阶段才暴露：AI 代码率从 25% 提升到 90%，但人工审查成本同步膨胀
- 度量框架失配——"行业过去十年所依赖的度量框架，并非为这种新型工作单元而构建"

**应该怎么做**：
- 建立 Code Delivery Rate 指标，同时追踪"工程师审查 AI 结果所花费的时间"
- 区分自动化层级：哪些环节可以完全信任 AI，哪些必须人工审核
- 将审查 overhead 计入 AI 真实 ROI，而非只看产出增量

---

### 3. 上下文腐化（Context Rot）

**Evidence**：上下文窗口填充率超过 40% 后质量快速衰退（Anthropic 四种失败模式之 One-shot Syndrome）。POC 通常在干净的单会话环境下运行，上下文窗口充裕；生产环境则是多会话、长周期、跨文件依赖的复杂场景。

**具体表征**：
- POC 阶段：单次会话上下文完整，Agent 始终有"上帝视角"
- 生产阶段：多会话累积、跨文件修改、上下文窗口被历史记录撑满，Agent 开始遗忘关键约束
- 持久化记忆缺失（Cold Start Problem）：真正用于编码的 Token Budget 被重新理解项目挤压

**应该怎么做**：
- 实现上下文分层加载（L1 会话常驻层 / L2 阶段触发层 / L3 按需查询层），让 Agent 任何时刻都拥有"刚好够用"的上下文
- 进度持久化在文件系统而非上下文窗口中，Agent 启动时自动检查 Git Log 和 progress.md
- 控制 L1 层总量，避免窗口填充率超过 40%

---

### 4. 工具链脆弱性（Tool Fragility）

**Evidence**：企业级 Java 应用涉及 RPC 框架（HSF/Dubbo/gRPC）、流程编排引擎（LiteFlow/Temporal）、配置中心（Diamond/Apollo/Nacos）、分布式缓存（Tair/Redis）等复杂工具链。POC 阶段通常只验证 Agent 与核心代码的交互，不验证与所有生产依赖工具的交互。

**具体表征**：
- POC 阶段：只测 Agent 写代码的能力，不测 Agent 调用配置中心、消息队列、CI/CD 流水线的可靠性
- 生产阶段：Agent 遇到 RPC 超时、降级策略、事务边界等问题时行为不可预测
- 隐性知识从未被记录——如"某配置项有 85 处引用"、"某链路是高频变更区"

**应该怎么做**：
- 将所有外部依赖的调用规范（超时设置、降级方案、事务边界）写入 Skills 作为可执行 Spec
- 外部服务调用必须设置超时和降级——这条约束背后是真实发生过的雪崩事件
- MCP Servers 配置完整记录并纳入 CI 验证

---

### 5. 团队能力断层

**Evidence**：AI 正在将工程职责从"写代码"迁移到"管理 AI 输出"。工程师需要的新核心能力：审查代码质量和安全 / 为下游结果承担责任 / 判断何时信任 AI 何时 override。**68% 以上**的开发者表示交付项目压力增大。

**具体表征**：
- POC 阶段：少数技术强者用个人技巧搞定一切
- 生产阶段：需要团队级 Harness 维护、规范化迭代、知识沉淀——这些能力大多数团队从未建立
- 开发者角色范式转移：从"写代码的人"变成"设计 Agent 工作环境的人"
- 规范编写能力稀缺——"规范的每一行都对应一个历史失败案例"，需要足够的踩坑经历才能写出有价值的规范

**应该怎么做**：
- 建立专门的 Harness 维护角色，而非假设所有工程师都能维护 Harness
- 将知识沉淀纳入工程流程——不只是修代码，而是修 Harness，从根源上防止同类问题再次出现
- 渐进式提升团队 Harness 能力，从 Dry Run 虚拟需求开始

---

### 6. 知识未外部化

**Evidence**：腾讯 AI Team 指出——"工作流只是管道，知识才是流过管道的活水"。Model/Toolchain/工作流会迭代重构，但团队积累的领域模型、架构决策、最佳实践、已知陷阱、业务流程——这些知识是永恒的，不会因模型换代而失效。企业级项目中存在大量隐性知识（价格字段必须用 `long` 分而非 `double`、某配置 85 处引用），这些从未被系统化记录。

**具体表征**：
- POC 阶段：Demo 场景简单，不涉及复杂隐性知识边界
- 生产阶段：Agent 的知识边界等于代码库的文件边界，所有隐性业务约束它都不知道
- 没有知识闭环的工作流——上一次踩过的坑，下一次照踩不误
- 架构熵增是每个"局部最优"累积的必然结果（k10s 的 500 行 Update() 是 234 次局部最优的叠加）

**应该怎么做**：
- 建立五层知识存储架构（个人偏好 → 团队约定 → 技术知识 → 业务知识 → 项目知识）
- 用五种知识类型（model/decision/guideline/pitfall/process）为团队知识打标签
- 建立 maturity 验证机制（draft → verified → proven）并配置自动衰减，保证知识库不随时间腐化
- 将知识生产嵌入日常工作流（INIT 阶段 git pull 知识仓库，ARCHIVE 阶段自动提取知识条目）

## POC 上生产前的快速检查清单

在将 Agent 方案投入生产之前，逐项核对：

| # | 检查项 | 通过标准 | 参考来源 |
|---|--------|----------|---------|
| 1 | **Harness Dry Run 完成** | 用虚拟需求完整走完全流程，发现并修复了 CI 门禁逻辑漏洞、评审报告生成条件缺失、摘要文件重复行问题、部署参数推测错误 | |
| 2 | **质量门禁可程序化验证** | "CI 通过"被拆解为 `status == SUCCESS && total_tests > 0 && passed == total`，而非自然语言描述 | |
| 3 | **执行与评判角色分离** | 编码 Agent 和评审 Agent 分离，评审 Agent 发现了编码 Agent 遗漏的潜在问题 | |
| 4 | **上下文分层加载落地** | L1/L2/L3 分层策略已实现，上下文窗口填充率不超过 40% | |
| 5 | **知识显性化启动** | 核心隐性知识（价格字段类型约束、外部调用超时降级策略、高频变更链路）已写入规范 | |
| 6 | **度量框架已更新** | 追踪代码交付率和审查 overhead，而不只是产出量 | |
| 7 | **团队角色已调整** | 有专人负责 Harness 维护，工程师角色已从"代码编写者"转为"AI 管理者" | |
| 8 | **外部依赖调用规范已记录** | 所有 RPC/缓存/配置中心的调用规范（超时、重试、降级）已写入 Skills | |
| 9 | **变更 Audit Trail 已建立** | 每个需求有完整的变更目录链（summary.md / tasks.md / review records） | |
| 10 | **知识生命周期机制已设计** | draft/verified/proven 三级 maturity 和自动衰减机制已规划 | |

## 核心结论

POC 成功≠生产可用。POC 验证的是 Agent 的原始能力，生产要求的是在没有人全程盯着的情况下 Agent 依然可靠运行。这需要：

1. **Harness 体系**（结构化约束 + 质量门禁 + 执行评判分离）
2. **知识外部化**（隐性知识→显性规范，活文档持续迭代）
3. **团队能力升级**（从代码编写者到 AI 系统设计者）
4. **度量框架更新**（看见审查 overhead，看见真实 ROI）

> "高 AI 代码率本身不是目标，在质量可控前提下的高 AI 代码率才有意义。"
