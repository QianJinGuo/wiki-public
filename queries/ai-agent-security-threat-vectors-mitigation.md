# AI Agent 安全威胁向量与缓解策略有哪些？

## 核心问题

AI Agent 面临哪些主要安全威胁向量？如何在系统生命周期各阶段实施有效的缓解策略？

---

## 一、威胁向量分类

### 按攻击面分类

|| 威胁向量 | 描述 | 典型案例 |
|---------|------|---------|
| Prompt Injection | 恶意指令注入用户 prompt | 越狱攻击、指令覆盖 |
| Context Pollution | 上下文被污染影响决策 | 长对话中的上下文遗忘 |
| Tool Poisoning | 工具链被恶意篡改 | 恶意 MCP 工具 |
| Memory Poisoning | 记忆系统被污染 | 长期记忆注入恶意经验 |
| Supply Chain | 依赖组件被植入后门 | 第三方 Skill 恶意代码 |
| Data Exfiltration | 敏感数据通过输出泄露 | 日志/错误信息泄露 |

### 按 Agent 生命周期阶段分类

| 阶段 | 主要威胁 | 缓解措施 |
|------|---------|---------|
| 开发阶段 | Skill 供应链攻击、代码注入 | 代码审计、签名验证 |
| 部署阶段 | 配置漂移、权限过宽 | IaC 扫描、最小权限审计 |
| 运行阶段 | Prompt injection、上下文污染 | 输入过滤、分层治理 |
| 演化阶段 | 记忆污染、策略退化 | 记忆完整性检查、版本回滚 |

## 二、全生命周期安全体系

### Agent Security Full Lifecycle System

覆盖 Agent 从设计到退役的全生命周期安全：

```
设计安全 → 开发安全 → 部署安全 → 运行安全 → 演化安全
```

#### 设计阶段
- 威胁建模：识别所有信任边界和数据流
- 最小权限原则：每个 Skill 仅获取必要权限
- 失败安全：默认拒绝、优雅降级

#### 开发阶段
- Skill 签名验证：每个 Skill 有可验证的来源
- 沙箱隔离：危险操作在受限环境执行
- 代码审计：敏感 Skill 强制人工审查

#### 部署阶段
- 配置验证：Harness 配置语法和权限检查
- Secret 管理：API 密钥使用 Vault 或 K8s Secret
- 网络策略：限制 Agent 的网络出站流量

#### 运行阶段
- 实时监控：工具调用日志、异常行为检测
- 上下文隔离：防止跨会话信息泄露
- 熔断机制：异常行为触发自动暂停

#### 演化阶段
- 记忆完整性：定期检查长期记忆一致性
- 版本控制：所有策略变更可审计可回滚
- 模型更新验证：新模型版本需通过安全评测

## 三、对抗攻击类型与缓解

### Prompt Injection

**攻击方式**：
- 直接注入：`Ignore previous instructions and...`
- 隐式注入：通过上下文累积改变行为
- 跨会话注入：利用记忆系统传播恶意指令

**缓解策略**：
- 输入层过滤：检测常见 injection 模式
- 指令分离：系统 prompt 与用户 prompt 严格分离
- 上下文边界：限制上下文中的指令数量
- 分层验证：敏感操作二次确认

### 数据 poisoning

**攻击方式**：
- 训练数据污染：恶意数据影响模型行为
- 检索结果污染：向量数据库被注入恶意文档
- 行为数据操纵：用户反馈被恶意刷单

**缓解策略**：
- 数据来源验证：所有外部数据经过来源审计
- 向量数据库定期扫描：检测注入的恶意文档
- 行为异常检测：识别异常的用户反馈模式
- 黄金集验证：定期用已知答案的测试集验证系统

## 四、红队测试方法论

### 核心测试维度

| 测试类型 | 测试方法 | 攻击面 |
|---------|---------|-------|
| Prompt 红队 | 越狱 prompt、指令注入 | Prompt 层 |
| Context 红队 | 上下文溢出、记忆污染 | Context 层 |
| Tool 红队 | 恶意工具、工具链劫持 | Tool 层 |
| Multi-Agent 红队 | Agent 间通信劫持、信任滥用 | 协作层 |

### 红队最佳实践

- **自动化 + 人工结合**：自动化扫描已知漏洞，人工发现新攻击面
- **攻击模拟**：使用同级别 LLM 生成对抗样本
- **定期演练**：每次模型或 Harness 更新后重新评估
- **多维度评分**：不仅测安全性，也测对正常用户的影响

## 五、AWS Bedrock 与 API 安全

### Amazon Bedrock API 安全最佳实践

- **认证与授权**：使用 IAM 角色而非长期密钥
- **流量限制**：设置 API 调用频率限制防止滥用
- **输入验证**：所有用户输入经过验证再传至模型
- **输出过滤**：对模型输出进行敏感信息检测
- **日志审计**：完整记录所有 API 调用
- **网络隔离**：使用 VPC 私有子网部署 Agent

---

## 六、容器与云安全

### Fedora Hummingbird 容器安全模型

- 不可变容器镜像：防止运行时篡改
- 最小化容器权限：使用 seccomp、AppArmor 限制
- 主机级隔离：容器与主机 OS 分离安全边界
- 运行时安全监控：检测异常容器行为
