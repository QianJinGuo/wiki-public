# 拒绝“感觉有效”：用数据证明 AI Coding 的真实团队价值【天猫AI Coding实践系列】

本文基于天猫团队的真实实践，提出一套三层 AI Coding 度量体系：^[raw/articles/拒绝感觉有效用数据证明-ai-coding-的真实团队价值天猫ai-coding实践系列.md]

**质量指标**（离线评测）——用垂直化业务用例 + 复杂度矩阵（业务复杂度×组件成熟度）+ 结果分/行为分双评分，定位模型能力短板；

**链路指标**（在线埋点）——追踪上下文“调用→命中→采纳”漏斗，通过四象限分析识别高频低效知识，驱动知识库、SPEC、Skills 等优化；

**结果指标**（真实交付）——以需求为单位，计算 AI 参与覆盖率、代码上线采纳率（Diff 级比对）、Token 成本，验证实际价值。

核心目标：将“感觉有效”转化为可诊断、可调优、可共识的数据闭环，推动 AI 从工具升级为团队知识治理基础设施。^[raw/articles/拒绝感觉有效用数据证明-ai-coding-的真实团队价值天猫ai-coding实践系列.md]

## 摘要

天猫团队 2025 年 11 月起开展“后端全栈”试点——让零前端基础的后端工程师通过 AI 独立完成中后台前端需求。“感觉挺好”无法回答团队落地后的投入追问，文章由此提出质量、链路、结果三层相互校验的度量体系，形成“发现问题→定位原因→验证效果”闭环；它不定义“AI Coding 标准”，而是业务团队指导自身调优的工具。

## 核心要点

- “感觉有效”经不起推敲：幸存者偏差、归因错误（无基线无法归因）、个体差异（少数高手拉高均值）。
- 团队落地关心三件事：效果证明（追踪终点从 IDE 延伸到代码合并上线）、能力边界（“能跑通”≠“能力可靠”）、问题诊断（只有一个数字就只能盲调）。^[raw/articles/拒绝感觉有效用数据证明-ai-coding-的真实团队价值天猫ai-coding实践系列.md]
- 质量指标借鉴 SWE-bench 结构但垂直化定制：60 个真实历史需求用例覆盖 9 个矩阵象限，评分为“结果分 75% + 行为分 25%”。
- 链路指标用“调用→命中→采纳”漏斗归因：调用率低是 Prompt 引导问题，命中率低是覆盖/索引问题，采纳率低是召回精度问题。
- 四象限分析（使用频率×关联采纳率）识别“高频低效”知识：调用率 43.2% 看似健康，逐条优化后关联采纳率从 18% 升至 35%。^[raw/articles/拒绝感觉有效用数据证明-ai-coding-的真实团队价值天猫ai-coding实践系列.md]
- 结果指标以 (repo_project, branch) 为关联键跨系统打通，用规范化 Diff 比对计算上线采纳率；深层认知是 AI Coding 本质为知识资产治理革命，文档、SPEC、Prompt 由此成为可度量的团队资产。

## 深度分析

### 三层度量体系设计逻辑

业界方案各有侧重但不完整：Copilot Metrics 止于“接受补全”，无法验证代码上线；SWE-bench 只评结果，而前端场景存在多解性、交互需求测试成本高、过程盲区三类问题，通用基准无法适配。

解法是三层互补：离线评测验证调优方向（能力边界），在线埋点追踪真实效果（问题诊断），结果指标回答最终价值（效果证明），三层相互校验。最具辨识度的设计是行为分——受过程监督（PRM 优于 ORM）研究启发，提出“开卷考试”理念：不仅看答案对不对，还看有没有翻对书、查对资料。综合得分 = 结果分×0.75 + 行为分×0.25；行为分的价值不在惩罚而在预测稳定性，“碰巧正确”比“稳定正确”更危险。^[raw/articles/拒绝感觉有效用数据证明-ai-coding-的真实团队价值天猫ai-coding实践系列.md]

### 四象限上下文分析

追踪单条知识的“采纳”存在工程难题：知识库返回“软内容”，Agent 不会显式标注引用来源，也没有 A/B 对照组。团队因此采用关联分析——分析使用了某能力的会话，其代码采纳率表现如何；以使用频率为横轴、关联采纳率为纵轴做散点分布，阈值用动态中位数。

案例二即典型：调用率稳定在 43.2%、命中率正常，但四象限揭示了被频繁召回而采纳率仅 20%~30% 的低效知识——被“用”了但没有真正“有用”。团队从四个视角追踪上下文：SPEC 模板用采纳率反推质量（补必填项后显著提升）；经验知识库以“可操作性”为质量标准，零结果查询 Top 20 作为补缺输入；物料组件库区分“没调用 MCP”与“命中率低”；Skills 会话采纳率明显高于普通会话。

### 评测驱动决策案例

模型选型：长期凭感觉对比两个主力模型，直到用 60 个真实历史需求系统评测——模型 A 总分 84.9、模型 B 总分 57.0，差距近 28 分；热力图显示差距集中在组件文档不完善的场景，把“感觉 A 更好”变成“B 在哪类场景吃力”的可操作结论。^[raw/articles/拒绝感觉有效用数据证明-ai-coding-的真实团队价值天猫ai-coding实践系列.md]

复杂度矩阵是评测集设计核心：业务复杂度（L1 标准化/L2 有联动/L3 复杂交互）× 组件成熟度（C1 文档完善/C2 部分/C3 缺失），组合出九象限能力地图——绿区适合 AI 独立完成，黄区需人机协作，红区不推荐。一维 pageType 分类无法区分“同为表单页，组件库完善时良好、需自定义组件时下降”。调优闭环案例：L2-C2 象限早期仅 55 分，失败集中在“表单联动”类需求，优化 SPEC 模板 + Prompt + 知识库后显著提升。

### 结果指标与采纳率口径

结果指标回答“最终上线的代码中有多少来自 AI”。以 (repo_project, branch) 为关联键，将 AI 编码平台任务数据与迭代/需求系统打通：出码后实时上报 Diff，发布记录 T+1 同步，定时任务匹配计算。核心指标为需求覆盖率（渗透程度）、代码采纳率（产出质量）、Token 成本（ROI 与运营策略效果）。

采纳率口径有三个工程难点：格式差异会误判，采用规范化比对（去注释、合并空白、统一风格后逐行比对）；发布记录通常只存最后一次 commit，需找到其后的 Merge Commit 才能获得完整变更；同分支多次出码时，将同 (repo_project, branch) 下所有 AI Diff 记录合并后再比对。Token 聚合采用“允许重复计算”模式，各维度汇总值不等于实际总消耗但更符合业务分析需要。

## 实践启示

1. 追踪终点要从“IDE 内接受补全”延伸到“代码合并上线”——接受不等于有用。
2. “能跑通”不等于“能力可靠”：碰巧正确但过程漏洞百出的 Agent 比完全不工作的更危险。
3. 知识被“用”不等于“有用”：整体漏斗健康时仍可能存在高频低效条目，四象限分析是定位手段。
4. SPEC 模板的结构化约束越强，AI 输出质量越高：补必填项比泛泛改 Prompt 更可验证。
5. 离线评测定位方向，在线埋点和结果指标验证实际效果，缺一层就会盲调。
6. 度量的目的是赋能而非考核：数据让调优决策变成团队可讨论、可对齐的问题，也让知识积累有了复利的可能。
