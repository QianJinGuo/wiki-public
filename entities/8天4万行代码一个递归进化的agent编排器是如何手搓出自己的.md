# 8天，4万行代码：一个递归进化的agent编排器是如何“手搓”出自己的?

核心创新在于编排器本身就是一个真正的 AI 智能体，能监控多智能体会话、路由审查反馈并仅在需人类决策时介入，解决了人类注意力瓶颈，推动自改进循环以提升整体效率。 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md]

作者 Prateek (@agent_wrapper) 是 Composio 的 AI 工程师与 Agent Orchestrator 的核心创建者。他主导开发了开源的 AI 智能体编排系统，用它在 8 天内由智能体自身构建出 4 万行 TypeScript 代码，实现 20 倍人类效率跃升，专注多智能体并行、自愈与自改进工程。 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md]

## 我曾试图加快交付速度

当时我手里有一个代码库，一堆待办需求（backlog），但每天的时间根本不够用。于是我开始让 AI 编程智能体 并行运行 ——给每个智能体分配一个任务，让它们写代码，我来审查 PR、合并，然后循环。刚开始是两三个，然后是五个，最后增加到了十个。 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md]

智能体的速度很快，但 问题出在我身上 。我跟不上它们的节奏。我成了那个检查 CI（持续集成）是否通过、阅读审查意见、把报错信息复制回对话框的人。我从“写代码的人”变成了“给写代码的机器当保姆的人”。这根本无法规模化。 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md]

于是，我写了一些 Bash 脚本来自动化协调工作——大约 2,500 行代码，用于管理 tmux 会话、git worktree 和标签页切换。每个智能体都有自己独立的 tmux 会话和工作树。编排器可以启动它们，偷看它们在做什么，转发 CI 失败信息，并让我只需说一句“带我去 PR  #1121  的标签页”就能在会话间跳转。这勉强能用。 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md]

接着，我让智能体们去处理这些 Bash 脚本本身。它们构建了正式编排器的 V1 版本 。V1 管理着构建 V2 的智能体。从那时起，V2 就一直在自我改进。 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md]

### 从 Bash 脚本到自我改进系统

成果如下： 40,000 行 TypeScript 代码，17 个插件，3,288 个测试用例 ——在 8 天内构建完成，且大部分是由该系统编排的智能体编写的。每一条提交（commit）都有 git trailer 标注是哪个 AI 模型编写的。人类做了什么，智能体做了什么，清清楚楚。 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md]

我们已经将其开源： Agent Orchestrator  [1]  。

核心逻辑在于： 编排器本身就是一个 AI 智能体。它不是一个仪表板，不是一个定时任务（cron job），也不是一个轮询 GitHub 的脚本。 它是一个智能体 ——它读取你的代码库，理解你的需求，决定如何将功能拆解为可并行的任务，将任务分配给编程智能体，并监控进度。 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md]

当 CI 失败时，它会将失败信息注入智能体会话——智能体读取日志并修复它。当审查意见出现时，它会将其路由到带有上下文的正确智能体会话。无需人工充当“搬运工”。这就是它与所有“并行运行智能体”方案的不同之处： 管理智能体的东西本身就是智能的。 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md]

## 深度分析

### 递归进化机制的设计

这套系统的递归不是营销修辞，而是一条可追溯的 bootstrap 链路：作者先手写约 2,500 行 Bash 脚本管理 tmux 会话与 git worktree，再让智能体把脚本重写为正式编排器的 V1，然后 V1 管理构建 V2 的智能体——被构建的东西正是管理其自身构建的东西 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:30-47]。递归的关键在于人在循环中的位置发生了迁移：作者不再写功能代码，只保留架构决策（插件槽位、配置模式、会话生命周期）、跨智能体冲突裁决和判断性取舍，全部 4 万行实现与 3,288 个测试由智能体完成，且"每一行代码都经过了 PR" ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:159-197]。这与 [[concepts/ai-self-improvement-bootstrapping]] 描述的自我改进起点一致：先造一个粗糙的脚手架，让系统从第一天起就在自己的轨道上迭代。

### AI 辅助大规模生成的质量控制

8 天产出 4 万行代码的前提，是把质量控制也变成了机器流程而非人工把关。PR 提交后由 Cursor Bugbot 自动行内审查，智能体读取评论、修复、再推送，Bugbot 重审——700 条自动审查评论中，智能体立即修复约 68%，解释设计意图约 7%，其余推迟到未来 PR ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:84-97]。CI 侧的自愈通过 YAML reactions 实现：`ci_failed` 与 `changes_requested` 事件自动 spawn 带上下文的修复智能体，9 个分支的 41 次 CI 失败全部由智能体自行修正，典型如 PR #125 经历 12 轮"失败→诊断→修复"循环零人工交付 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:99-157]。这本质上是 [[concepts/verifier-driven-development]] 的工程化落地：审查与 CI 是自动化的 verifier，智能体在生成与验证之间闭环，人只处理升级上来的决策。另一个容易被忽略的细节是活动检测——编排器不信任智能体自我报告，而是直接解析 Claude Code 的 JSONL 会话事件文件来判断其真实状态 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:199-213]。

### 编排器架构分层

编排器被设计为 8 个可替换插件槽位，覆盖一个会话从 Issue 到合并的完整生命周期：Tracker（拉取 GitHub/Linear issue）、Workspace（隔离 worktree）、Runtime（tmux 或进程）、Agent（Claude Code/Aider 等编程智能体）、Terminal（实时观察）、SCM（创建 PR）、Reactions（事件驱动的自动重启）、Notifier（仅在需要人类判断时 ping） ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:107-139]。分层的价值在于解耦：换运行时、换任务追踪器、换模型都不触及核心逻辑，这使编排层成为可复用资产而非一次性脚本。模型分工同样体现了编排思想——Opus 4.6 承担复杂架构与跨包集成，Sonnet 4.5 承担插件实现、测试与文档等走量任务，722+ 个提交通过 git trailer 标注作者模型，人机贡献清晰可审计 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:64-82]。

### 交付速度与代码质量的张力

"8 天 4 万行"的叙事容易掩盖真实的成本结构：这 8 天里作者实际专注工作约 3 天，靠"睡前设会话、智能体过夜工作、早晨审查合并"的节奏填补空隙，单日最高合并 27 个 PR——但每个 PR 都预先通过了 CI 和自动化审查，人是最后的质量闸门而非全检员 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:64-70]。84.6% 的 CI 首次成功率意味着约 15% 的返工由自动循环消化，速度优势来自并行度与自愈能力，而非降低质量标准 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:99-105]。文中也坦承当前边界：智能体会走偏、过度设计或钻牛角尖，编排器需要在错误方向上浪费 20 分钟之前注入路线修正，跨智能体文件冲突仍需人类裁决 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:173-255]。这些张力点恰好划定了"可自动化"与"必须保留人类判断"的分界线，与 [[concepts/agent-orchestration-patterns]] 中编排层优于单智能体堆能力的论断互相印证。

## 实践启示

1. **先把人的注意力瓶颈变成显式清单。** 作者的转折点是发现自己沦为"给写代码的机器当保姆"——检查 CI、转发报错、复制审查意见。把这些机械动作逐一列出并自动化（CI 失败注入、审查意见路由），是并行智能体从玩具走向产线的第一步 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:30-56]。

2. **用粗糙脚本起步，再让智能体重写它。** 不必一开始就设计完美编排器：2,500 行 Bash 管会话足够撑起 V1，然后让系统参与构建自己的替代品。递归进化的正确姿势是"最小可用的管理工具在前，被管理的智能体紧随其后" ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:34-44]。

3. **给每个环节配自动 verifier，而不是靠人工逐行审查。** 自动代码审查 + CI 自愈 reactions 让 41 次失败零人工修正；个人或小团队复制该模式时，最低配置是"PR 必过 CI + 行内自动审查 + 失败自动 spawn 修复智能体"三件套 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:84-157]。

4. **模型分层分配任务并用 git trailer 记账。** 强模型做架构与集成，快模型做实现与测试，贡献归属写进提交元数据。这不只是省钱——它让效率复盘和回归归因有据可查 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:72-82]。

5. **不要信任智能体的自我报告。** 直接解析会话事件文件（如 Claude Code 的 JSONL）判断智能体是生成中、等待工具还是空闲，是编排器调度正确性的前提 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:199-213]。

6. **保存会话信号用于改进下一轮。** 多数配置在会话结束后丢弃信号，而自我改进系统（ao-52）记录哪些提示词产出干净 PR、哪些模式引发冲突，让"智能体构建→编排器观察→调整管理→更好构建"的复利循环转动起来——这正是 [[concepts/agent-self-improvement-loops]] 的实操版本 ^[raw/articles/8天4万行代码一个递归进化的agent编排器是如何手搓出自己的.md:233-241]。
