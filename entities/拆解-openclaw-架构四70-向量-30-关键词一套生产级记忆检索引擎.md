SQLite？只是一个派生的加速层。你把 SQLite 文件删了，系统会从 Markdown 文件自动重建索引。数据不会丢一个字。 ^[raw/articles/拆解-openclaw-架构四70-向量-30-关键词一套生产级记忆检索引擎.md]

这个设计选择在数据库出身的工程师看来简直是"开历史倒车"，但在 AI Agent 的场景下，它有自己的道理。 ^[raw/articles/拆解-openclaw-架构四70-向量-30-关键词一套生产级记忆检索引擎.md]

传统 RAG 把数据藏在不透明的向量数据库里。你知道数据"在里面"，但想看看具体存了什么？要写查询；想修改一条记录？要写代码；想追踪某条记忆是什么时候、因为什么事件被存进来的？祝你好运。 ^[raw/articles/拆解-openclaw-架构四70-向量-30-关键词一套生产级记忆检索引擎.md]

OpenClaw 的 Markdown 文件呢？人类可读，  cat  一下就能看；Git 可版本化，谁改了什么一目了然；  grep  可搜索，不用等索引构建；任何编辑器可编辑，vim、VS Code、甚至 iPhone 备忘录都行。 ^[raw/articles/拆解-openclaw-架构四70-向量-30-关键词一套生产级记忆检索引擎.md]

你想想，一个 Agent 替你管日程、写文档、回消息，时间长了它积累的"记忆"里会有你的偏好、你的决策模式、你跟谁聊了什么。这些信息如果藏在一个二进制的向量数据库里，你连看都看不到，更别说审计和修改。但如果它就是一堆 Markdown 文件，放在你能直接访问的目录下，安全感就完全不同了。 ^[raw/articles/拆解-openclaw-架构四70-向量-30-关键词一套生产级记忆检索引擎.md]

## 深度分析

### 「Memory as Documentation」：可审计性压倒查询性能的设计哲学

OpenClaw 最反直觉的决定是把所有记忆做成明文 Markdown 文件，让 SQLite 退居派生加速层——删掉索引文件后系统可以从 Markdown 全量重建，数据零丢失。作者指出这套架构的深层逻辑在于：Agent 记忆里沉淀的是用户的偏好、决策模式和社交脉络，这类信息一旦锁进二进制向量库就不可审计、不可修正；而 Markdown + Git + grep 让人类可以直接查看、版本化、编辑每一份记忆。传统 RAG 追求查询性能，OpenClaw 则把可审计性放在第一位。最有说服力的旁证是向量数据库厂商 Milvus/Zilliz 主动把这套「文件优先、数据库只是加速层」的架构提取成 memsearch 库推广——连卖向量数据库的公司都认可「不是所有场景都需要向量库」。^[raw/articles/拆解-openclaw-架构四70-向量-30-关键词一套生产级记忆检索引擎.md]

这个 tradeoff 也有代价：明文文件存放在可预测路径下没有静态加密，文件之间没有显式关系映射（文件 A 和文件 B 提到的同一个「项目 X」不会自动关联），写入没有事务保证。本地个人场景可以接受，一旦部署到共享服务器就是安全隐患。[[concepts/agent-memory-architecture|Agent 记忆架构]] 的选型本质上是「信任模型」的选型：你信任谁来看这份记忆，决定了你选文件还是选数据库。^[raw/articles/拆解-openclaw-架构四70-向量-30-关键词一套生产级记忆检索引擎.md]

### 混合检索的工程细节：union、加权融合与候选倍增

70/30 的向量与 BM25 加权只是表层公式，真正体现 IR 功力的是四个细节决策。其一，两路检索结果取 union 而非 intersection——记忆场景下漏掉一条相关记忆的代价远大于多返回几条弱相关结果，union 保住了召回率。其二，BM25 排名通过倒数公式映射到 0-1 区间，使其能与向量余弦分数直接加权融合。其三，candidateMultiplier 为 4：要返回 10 条结果，每路先各取 40 条候选，给融合排序留足选材空间。其四，拒绝 RRF 选加权求和，因为 RRF 会抹平分数量级差异——cosine 0.98 的「几乎完全匹配」信号在 RRF 里被稀释成排名第 1，而加权求和保留原始量级且权重显式可配。^[raw/articles/拆解-openclaw-架构四70-向量-30-关键词一套生产级记忆检索引擎.md]

这四个决策每一个都对应信息检索领域的经典问题，拼在一起说明该系统出自有搜索系统背景的工程师之手，而非框架作者的随手拼凑。对任何要做 [[concepts/retrieval-augmented-generation-rag|RAG 检索增强生成]] 的团队来说，这套混合检索管线（分块→双路召回→加权融合→后处理）是可直接参考的及格线以上的设计模板。^[raw/articles/拆解-openclaw-架构四70-向量-30-关键词一套生产级记忆检索引擎.md]

### 时间衰减与 MMR：默认关闭的后处理透露的场景自觉

检索管线末端有两个可选项：指数时间衰减（30 天半衰期，今天 100%、30 天前 50%、90 天前 12.5%）和 MMR 去重（Jaccard 相似度，lambda 0.7，相关性与多样性七三开）。两者默认都关闭——这个默认值本身就是信号：衰减对日常助理型 Agent 有用（近期对话更重要），但对知识库型 Agent 会适得其反（一年前的技术文档可能比昨天的闲聊更值钱）。关键例外是长期类文件不衰减：MEMORY.md 和非日期命名的笔记保持原始分数，「我喜欢用 vim」这类偏好不因时间贬值。这与 [[concepts/memory-consolidation-decay|记忆固化与衰减]] 的研究结论一致——衰减必须区分信息类型，不能一刀切。^[raw/articles/拆解-openclaw-架构四70-向量-30-关键词一套生产级记忆检索引擎.md]

### 记忆冲刷与安全边界：群聊不加载 MEMORY.md

两个横切机制值得单独看。压缩前记忆冲刷：当 session 逼近上下文阈值时，系统在压缩前插入一个静默 turn，指示模型把关键信息写入当日日志文件，再开始有损压缩——这为「上下文丢失」和「记忆持久化」之间架了桥，形成对话→冲刷→索引→召回→重入上下文的闭环。安全侧：MEMORY.md 存的是长期敏感偏好，群聊场景下刻意不加载，防止群成员或注入攻击触及私人记忆——这是把权限控制做进了加载层而非应用层。[[concepts/context-window-economics|上下文窗口经济学]] 视角下，每次会话启动的 8 个记忆文件要消耗 4000-10000 tokens 的「阅读作业」，这笔记忆税是「记得住」的固定成本。^[raw/articles/拆解-openclaw-架构四70-向量-30-关键词一套生产级记忆检索引擎.md]

## 实践启示

1. **用「真相源 + 派生索引」两层结构替代单一数据库存储**：让人类可读的文件（Markdown）做唯一真相源，把向量索引、FTS 等做成可随时删除重建的加速层。判断标准：删掉索引层后系统能否自动无损重建。
2. **混合检索默认 union、拒绝 RRF、权重显式可配**：双路召回取并集保召回率；用加权求和而非 RRF 以保留分数量级信号；把 70/30 这类权重暴露成配置项，让不同场景（语义优先 vs 精确优先）可调。
3. **融合前做候选倍增**：按最终返回条数的 4 倍让每路各自取候选，给融合排序留选材空间，避免融合阶段「无米下锅」。
4. **时间衰减必须按记忆类型区分并默认关闭**：日期型日志可衰减，偏好/事实型长期记忆不衰减；先明确你的 Agent 是助理型还是知识库型，再决定是否开启。
5. **把「文件不存在」与「出错」区分为不同返回状态**：记忆读取对缺失文件返回空文本而非 ENOENT 错误，省掉调用方一整套错误分支——优雅降级应成为 Agent 工具设计的一等公民。
6. **敏感记忆的权限控制要做在加载层**：如 MEMORY.md 群聊不加载、QMD 后端按聊天渠道配置访问作用域——上下文组装时过滤，比事后在应用层防泄露更可靠。
