过去一段时间，随着工作中 AI Coding 的占比越来越高，我逐渐感觉到当前 AI Coding 的协作范式已经不适合我了。 ^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md]

当前主流的 AI 开发过程，仍然是人与一个 Agent 围绕同一个任务持续协作。但我在日常工作中，已经习惯于同时操控多个 Agent 并行执行任务，在关键节点做 Review，并对最终结果进行验收和整合。 ^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md]

这篇文章想讨论的，是 AI 编程协作范式的转移：人与 AI 该如何分工，多个 Agent 之间又该如何协作。 ^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md]

当单 Agent 协作开始不够用

AI IDE 本身的能力越来越强，但它提供的协作模式，还是以单线程为主。我通常是在和一个 Agent 持续协作：我提需求，它读取上下文、改动多个文件、执行命令，再返回结果，等我确认后进入下一轮。这种方式虽然能正常工作，但我的大量时间都消耗在"等它返回、看它改了什么、决定要不要继续"这条链路里。只要任务还在这条链上推进，人就没有真正从执行流程里抽离出来。 ^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md]

于是，我开始尝试更加高效的协作模式，比如在 AI IDE 中开多个聊天窗口，在同一个工作空间指派 Agent 相对独立的开发任务，这样我就能把时间用在理解需求、拆解和分发任务、Review 已有代码、检查 Diff，以及对最终结果做验收和整合。 ^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md]

这是我找到的比较理想的方式。但当我真正开始这样工作后，发现现有工具并没有为这种模式做好准备。^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md]


OpenCode 的 Web 模式给了我最接近的雏形^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md]


明确了这种工作方式之后，我开始寻找能适配它的 Coding 工具。在用过的工具里，OpenCode 的 Web 模式最接近我的理想，它让我看到了一种有别于 AI IDE 的交互方式：Agent 先执行一段时间，我在关键节点回来看改动、给反馈、做验收。 ^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md]

但对照我真正需要的能力：

- 能承接多个 Agent 并行工作

- Review 取代代码编写成为工作流中心

- 能帮助我观测多个 Agent 的工作过程

OpenCode 对多 Agent 并行的支持还不够，本质上还是单 Agent 工作流。所以，我开始设计自己的工具。 ^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md]

## 深度分析

### 单 Agent 轮转链路是新的吞吐瓶颈

作者的核心观察是：AI IDE 能力在变强，但协作模式仍是单线程——人提需求、Agent 执行、人确认、再下一轮。人没有被代码拖住，而是被"等它返回、看它改了什么、决定要不要继续"这条决策链路拖住。当 AI 承担的任务链路越长，这条串行确认链的空转成本就越高。真正的解法不是让单 Agent 更快，而是把人从执行流程里抽出来，转向多 Agent 并行 + 关键节点介入的模式。^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md:32-38]

### 以 Review 为中心重构工作界面

一旦并行 Agent 达到三四个以上，代码编辑器就不再是人的主操作面。作者的实际工作重心移向：理解需求、拆解分发任务、看 Diff、验收整合。这意味着 Review 从"终点验收动作"变成"持续判断的主界面"——不仅要能看结果，还要能就地把反馈发回对应 Agent 触发返工，整个循环不离开 Review 界面。这是对 IDE 交互形态的根本性倒置：不是"编辑器 + AI 助手"，而是"控制台 + 多执行单元"。^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md:100-151]

### 共享工作区与机制化边界：约束即放大器

默认 git worktree 隔离预设了"Agent 之间不需要配合"，把协作需求全部后置到合并阶段，而合并期解决冲突的成本远高于执行期及时纠偏。作者选择默认共享工作区，但配套一套机制而非依赖 Agent 自觉：用结构化 spec 定义边界（allowedPaths 划定修改范围）、用轻量文件 claim 暴露占用事实（不阻塞但可见）、用 Observer Agent 做运行时仲裁（发现冲突提示避让或上报人工）、用人工确认点兜底关键决策（批准 spec 与批准执行计划）。这印证了 [[concepts/harness-engineering-framework|Harness Engineering]] 的洞察：约束一旦被编码，就能同时作用于所有 Agent 和任务——"通过 prompt 提醒不要越界"不可靠，让越界行为可被检测、可被拦截才可靠。隔离并未被抛弃，高风险重构和实验性改动仍按任务粒度切到 worktree，两种策略可在同一执行计划中并存。^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md:83-98] ^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md:163-190] ^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md:204-212]

### 观测层是移交管理职责的前提

单个 Agent 时盯输出就够，多个 Agent 并行时需要的是"从执行细节中提炼的态势感知"而非更多终端窗口。作者设计了四个观测视角——Agent 仪表盘（产出/卡住/负载均衡）、模块视图（工作分区重叠即需协调）、依赖视图（上游改动自动高亮下游影响面）、冲突面板（直接/依赖/模块三类冲突集中呈现）——共同回答三个问题：现在有没有问题、问题在哪、我需要介入吗。更关键的设计决策是：这些信号沉淀为统一的结构化"环境事实层"，人类界面和未来的 Observer Agent 消费同一份数据，避免"UI 显示一种状态、Agent 依据另一种状态行动"的分裂。可观测因此不只是协作基础设施，也是人逐步向 Agent 移交管理职责的前提。^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md:100-130] ^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md:194-203]

## 实践启示

1. 当单 Agent 协作的等待-确认链路占据你的时间时，瓶颈已经从 Agent 能力转移到协作模式本身——优先考虑并行开多个 Agent 处理独立任务，而不是继续优化单个会话。^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md:32-38]
2. 派发并行任务前先让规划 Agent 产出结构化 spec（目标、范围、验收标准、任务拆解），人工批准 spec 和执行计划两个确认点后再分发——与 [[concepts/specification-driven-agent-development|Specification-Driven Development]] 的做法一致，比直接拆任务扔给 Agent 更可控。^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md:87-88]
3. 多 Agent 共享仓库时，给每个 Agent 明确的 allowedPaths 和轻量文件 claim，让占用情况对所有参与者可见；依赖 prompt 自觉"不要越界"不可靠，要用可检测、可拦截的机制约束。^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md:90-94] ^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md:176-184]
4. 把 Review 界面当作主操作面而非终点检查：看 Diff 的同时就能把反馈发回对应 Agent 触发返工，避免"看完再切回去重新描述问题"的上下文切换损耗。^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md:132-140]
5. 混用不同 CLI Agent 按任务难度分配是更经济的策略：核心模块用最强模型，测试文档用轻量 Agent；某个 Agent 撞限额时其他 Agent 接力，能力降级好过任务中断。^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md:142-147]
6. 默认共享工作区 + 机制化协调，只对高风险重构、实验性改动切换 worktree 隔离——因为执行期的及时纠偏成本远低于合并期的冲突收拾。^[raw/articles/从聊天窗口到多-agent-控制台一次-ai-编程协作范式的转移.md:163-190]
