## 深度分析

### 强制知识库匹配：受控生成而非自由生成

这套系统最关键的设计决策，是把 LLM 的角色从「生成者」收窄为「匹配者」。知识库并非模型生成，而是人工对各业务线（评价、物流、下单、逆向、支付等）历史舆情梳理打标、逐步积累出的标准分类体系；匹配规则规定 LLM 只能从已有类别中选取，不可自创新标签。^[raw/articles/ai工作流在淘宝交易舆情巡检上的探索与实践.md] 这本质是用「受控生成」替代「自由生成」：概率性输出被约束在人工边界内，换来分类结果可控、一致、可解释，出问题可追溯到具体条目而非黑箱猜测。这与 [[concepts/harness-engineering-framework|Harness Engineering]] 用外部脚手架约束模型行为的理念一脉相承，也印证了 [[entities/knowledge-base-construction|知识库建设]] 作为 LLM 落地地基的地位。

### 七环节闭环的工程取舍

「采集 → 清洗 → AI判断 → 预警 → 分发 → 归因 → 复盘」七个环节并非齐头并进：前四环优先做实——采集复用淘内吐槽吧、清洗在魔兔平台业务初筛之外叠加人工关键词二次捞取防遗漏、预警按自定义规则与波动阈值触发；归因和复盘则「还在持续建设中」。^[raw/articles/ai工作流在淘宝交易舆情巡检上的探索与实践.md] 先让「发现问题 → 快速响应」这条最短价值路径跑通，再补齐长周期闭环。清洗的人工兜底也值得注意：即便有 AI，团队仍不信任单一数据通道，用低成本规则对冲漏报，是典型的工程冗余设计。

### 三阶段迭代：预置打标+语义匹配对纯语义聚类的教训

阶段一批量投喂让模型「自由发挥」，数据量增大后暴露上下文超限（舆情被截断丢弃）和结果对不上（输出归类数与输入条数不一致，排查成本极高）；阶段二改为单条投喂，稳定性提升，但概率性本质导致输出不一致——「不支持暗黑模式」与「无法使用暗黑模式」这类同类问题被归入不同标签，聚类噪音严重，统计不可用。^[raw/articles/ai工作流在淘宝交易舆情巡检上的探索与实践.md] 阶段三确立「预置打标 + 语义匹配」：任务从「自由归类」收缩为「判断输入最接近知识库哪个类别」，边界可控、结果一致、体系可迭代。核心教训：聚类并非不能做，而是不该放前台当分类器——最终方案把它移入闭环学习，仅对未匹配舆情池定期聚类发现潜在新类别，且须人工审核后才入库。聚类从「输出决策」降级为「辅助发现新类别」，正是两代方案的分水岭。

### AI 辅助定位：提升业务信任

原文的判断相当清醒：AI 是辅助决策的工具而非替代人的黑箱——AI 负责发现问题、聚合信息、提供建议，最终决策权始终交给业务同学。技术落地的最后一公里往往不是技术问题，而是信任问题：再精准的模型，业务不信任、不使用，就只是实验室里的玩具。^[raw/articles/ai工作流在淘宝交易舆情巡检上的探索与实践.md] 信任设计体现在多处：分类体系由业务定义而非算法强加、预警附带可核查的反馈摘要、看板支持自助下钻。团队也坦承准确率仍有提升空间——不夸大能力的姿态本身就是信任建设的一部分。

## 实践启示

1. **用受控匹配替代自由生成**：当输出空间可枚举时，不要让 LLM 自由创造标签；先人工构建分类体系，再把模型任务收缩为「在既有类别中选择」，一致性即大幅缓解。^[raw/articles/ai工作流在淘宝交易舆情巡检上的探索与实践.md]
2. **警惕批量投喂的隐性失败**：批量调用会以「条数对不上」的方式丢数据且排查成本高；单条投喂 + 结构化精简是更可靠的默认做法。^[raw/articles/ai工作流在淘宝交易舆情巡检上的探索与实践.md]
3. **聚类适合做发现，不适合做分类**：概率性噪音决定了语义聚类更适合放在闭环学习中辅助人工发现新类别，而非直接产出分类结果。^[raw/articles/ai工作流在淘宝交易舆情巡检上的探索与实践.md]
4. **关键数据通路保留人工冗余**：AI 清洗之外叠加人工关键词二次捞取，用低成本手段对冲漏报，高风险路径不宜去掉人工兜底。^[raw/articles/ai工作流在淘宝交易舆情巡检上的探索与实践.md]
5. **闭环学习是知识库的自我进化机制**：未匹配舆情不丢弃，定期聚类 → 人工审核 → 更新知识库，形成「知识库丰富 → 匹配率提升 → 未匹配减少」的正循环。^[raw/articles/ai工作流在淘宝交易舆情巡检上的探索与实践.md]
6. **信任是最后一公里的真问题**：预警附带可核查证据、看板支持自助下钻、决策权留给业务同学——采纳率取决于使用者是否省事，而非模型指标本身。^[raw/articles/ai工作流在淘宝交易舆情巡检上的探索与实践.md]
