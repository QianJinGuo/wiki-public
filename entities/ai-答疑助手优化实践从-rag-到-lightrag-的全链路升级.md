为什么意图识别是核心问题

2025 年，Andrej Karpathy 公开表示他更倾向于用^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md]

Context Engineering（上下文工程）^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md]

来替代 Prompt Engineering 这个说法。Shopify CEO Tobi Lutke 的定义更为精确："上下文工程是为任务提供所有必要上下文，使 LLM 有能力合理解决问题的艺术。" ^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md]

这个观点转变指向一个核心洞察：
LLM 应用的质量瓶颈，往往不在模型本身的能力，而在你喂给它的上下文是否足够好。^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md]

模型拿到了正确的、完整的、结构化的上下文，它就能给出好答案；拿到了碎片化的、不相关的上下文，再强的模型也无能为力。 ^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md]

## 深度分析

1. **RAG 的质量瓶颈在"检索端"，不在"生成端"**。本文的经验与 Karpathy 的 Context Engineering 判断一致：LLM 应用的质量瓶颈往往不在模型本身的能力，而在喂给模型的上下文是否足够好。答疑系统在优化提示词后，短板迅速转移到检索侧——用户口语化表达、同义词不匹配（用户说"灰度"而文档写"分组发布"）与上下文缺失，使向量召回不稳定。因此系统建设的重心应从调提示词转向上下文工程：理解问题结构、规划信息维度、主动组装上下文。^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md:59-83]
2. **CoT 意图识别的本质是把"查询改写"升级为"解题规划"**。传统 query rewriting 只是语义层面的同义替换，产出的是"平面"查询且串行执行；本文的方案让轻量模型（qwen-turbo-latest，为低延迟选型）先推理出解决问题的步骤，再沿每一步生成多组查询并行召回，一次性产出十几条覆盖不同维度的查询。召回结果因此天然具有逻辑递进关系——模型拿到的是"解题思路"而非零散片段。这实际上已具备 Agentic RAG 中"自主规划检索策略"的雏形。^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md:86-113]
3. **GraphRAG 与 LightRAG 的取舍核心是"社区机制的收益 vs 成本"**。GraphRAG 用 Leiden 算法做社区发现并生成社区摘要，兑现了跨文档关联推理与全局鸟瞰的质量承诺，但也带来四个工程困境：索引构建成本极高（依赖 GPT-4 级模型抽实体）、不支持增量更新（全局社区结构牵一发动全身）、查询延迟分钟级、对抽取质量高度敏感。LightRAG 的"做减法"哲学——砍掉社区机制，用 R(·)/P(·)/D(·) 三函数的图索引+向量混合方案替代——把查询延迟从分钟级降到秒级，索引构建快数倍，并使增量更新天然可行（新文档只需抽取→合并→补键值对三步局部操作）。作者实测 80% 以上的提问是具体技术问题，LightRAG 的双层检索已足够覆盖。^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md:200-232]^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md:282-297]
4. **评测 Agent 的"过度自信"是 LLM 自评的系统性风险**。用 Agent 自动评测回答质量时发现显著的乐观偏差：判定"需改进"的，人工几乎都确认是 Bad Case（精准率高）；判定"优秀"的，人工仍有相当比例标为"坏"（召回率低）。模型在评估自身或同类模型输出时，在证据不足时无法意识到自己"不知道"。推论：任何 LLM 应用都不能完全依赖模型自评，人工校验环节不可或缺；对齐多维标注体系、用更精细的评分维度约束乐观倾向是可行的缓解路径。^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md:333-345]
5. **知识表示从"碎片"到"结构"是检索升级的本质**。传统向量 RAG 中知识以碎片形态存在：切块物理切断上下文、无法跨文档关联推理、同一概念散落多篇文档而系统不知它们指向同一实体。从 GraphRAG 到 LightRAG 的演进，本质是知识表示从扁平向量空间升级为实体-关系图谱，让关联显式可查；而 Agentic RAG（Adaptive/Self-Reflective/Corrective RAG）与 MiniRAG 则代表检索从"一次性查找"走向"多轮迭代优化"与小模型端侧落地的新方向。^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md:133-152]^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md:299-314]

## 实践启示

1. **把意图识别从"过一层模型"升级为 CoT 查询分解 + 并行召回**：意图识别环节用轻量低延迟模型识别意图 → 生成解题思维过程 → 按步骤生成多组查询 → 并行执行向量召回并汇总去重。相比单次 query rewriting，召回覆盖面显著提升，且召回结果自带逻辑递进结构。^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md:86-113]
2. **选型决策：GraphRAG 适合离线深分析，LightRAG 适合在线答疑**：需实时响应、知识库频繁更新的在线场景选 LightRAG（秒级延迟、增量更新、token 消耗大幅减少）；对回答质量有极致要求且能承担高成本的离线分析场景才考虑 GraphRAG。落地前先统计自己场景中"全局鸟瞰型"提问的占比，再决定社区机制是否值得引入。^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md:297-298]
3. **把"增量更新"作为检索架构选型的一票否决项**：知识库每天都在变的系统，任何需要全量重建索引的方案都不可接受。LightRAG 因无社区层级依赖，新文档只需 R(·)→D(·)→P(·) 三步局部操作即可完成更新，耗时和 API 调用量远小于全量重建。评估任何 RAG 方案时先实测"新增一篇文档要多少成本"。^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md:271-282]
4. **评测体系从二分类升级为三维度标注**：只有"好/坏"两个标签无法区分 Bad Case 的根因。引入问题质量、回答质量、问题成因三个维度后，每个 Bad Case 都能对症下药：幻觉强化提示词约束、召回不足调检索策略、知识缺失推动补录、超出能力引导转人工。评测是让优化"从玄学变成工程"的前提。^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md:315-332]
5. **人工校验必须保留在评测闭环中**：评测 Agent 只能用作辅助——它的高精准率意味着其"需改进"判断可信，但其"优秀"判断召回率低、系统性偏乐观。可将其定位为"粗筛 + 可疑案例优先推送人工"，并通过对齐多维标注体系来约束其乐观倾向，而非直接采信其评分。^[raw/articles/ai-答疑助手优化实践从-rag-到-lightrag-的全链路升级.md:333-345]
