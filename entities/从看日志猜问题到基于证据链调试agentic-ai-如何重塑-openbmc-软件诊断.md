# 字节 STE：OpenBMC 证据链 Agentic 调试

## 深度分析

字节跳动 STE 固件团队在 OSFC2026 分享的 OpenBMC Agentic 调试方案：不让 LLM 直接读海量日志猜根因（上下文成本高 + 结论不可验证），而是先用确定性程序分析构建可验证证据链，再让 Agent 在受约束的证据空间中完成根因解释、验证建议与修复方向生成。LLM 的位置被重定义为证据解释器、假设组织者与行动建议生成器，事实来源是程序分析——这套分工回答了基础设施工程的关键问题：AI 应如何被可靠地使用，既不是替代工程师，也不是在日志里自由发挥。 ^[raw/articles/从看日志猜问题到基于证据链调试agentic-ai-如何重塑-openbmc-软件诊断.md]

### 日志到程序足迹：文本相似 ≠ 因果相关

OpenBMC 调试的第一痛点不是没有日志，而是日志太多：服务日志、systemd journal、D-Bus 调用记录、传感器状态变化混杂在一起，最后一条错误日志不一定是根因。传统链路是复制关键字搜源码、手动定位函数与调用者、凭经验判断异常路径。方案的关键突破是把运行时日志从「文本线索」转换为「程序足迹」：一条日志字符串可能在多个源码位置发出，或经过格式化与运行时拼接，因此反向映射到源码函数时不能选文本最相似项，而要结合模块、时间顺序、相邻日志、服务上下文与调用图可达性共同评分。

### 路径重建：对比正常路径找分叉点

定位到源码锚点只是第一步，根因分析还要回答「异常为什么走到这里、正常应走向哪里」。系统从异常函数出发沿真实调用关系向上下游扩展，识别关键节点、异常节点、事件节点与可能缺失的恢复节点；对 OpenBMC 这类事件驱动系统，还需纳入 D-Bus 调用、property 变化、signal、systemd service 与异步回调。方法上的核心差异是做差分：不只看异常路径发生了什么，还对比正常路径本应发生什么——某个恢复动作没执行、某个状态没更新、某个 fallback 没触发，这些路径差异是比单条错误日志更有价值的根因线索。

### 证据压缩与 Agent 的能力边界

Evidence Compressor 不是普通摘要工具，而是面向因果价值的结构化裁剪模块——「给模型更多上下文」并不总是更好，完整日志与源码会带来成本并让模型被噪声误导。Agent 的边界被显式限定：可以解释证据链、组织根因假设、对候选根因排序并给出验证步骤，但不能虚构不存在的函数调用关系、不能把文本相似的日志当根因证据、不能在证据不足时输出确定性结论。最终 RCA 报告要求包含现象摘要、日志匹配、源码锚点、调用链、路径差异、验证步骤与修复建议，每个结论可回溯到证据；证据不足时明确标注「不确定」与待补充采集的信息。长期演进路径是从 RCA 走向闭环修复：修复建议 → 补丁生成 → 自动验证 → CI/CD 回归 → 可回滚的可控部署。

## 实践启示

1. 把 LLM 定位为证据解释器而非事实来源：确定性的程序分析（调用图、路径重建、评分定位）先完成事实抽取，Agent 只在边界清晰的证据空间内推理，结论才可验证、可审计。
2. 反向映射日志到源码时用多信号评分（模块 + 时序 + 相邻日志 + 服务上下文 + 调用图可达性），警惕「选文本最相似项」这一直觉默认。
3. 根因分析优先做正常/异常路径差分：缺失的恢复动作、未更新的状态、未触发的 fallback 往往比任何一条错误日志更接近根因。
4. 上下文不是越多越好：用面向因果价值的结构化裁剪（证据包）替代原始日志堆叠，防止模型被噪声误导，也压低成本。
5. 显式写出 Agent「可以/不应该」清单，并在 RCA 输出规范中强制「证据不足 → 标注不确定 + 列出待采集信息」，把不可验证的猜测挡在输出之外。
6. 基础设施软件（固件、BMC 这类底层组件）的智能化改造，可复用「程序分析保真 + Agent 解释」模板，而不必让模型直接面对海量遥测。
