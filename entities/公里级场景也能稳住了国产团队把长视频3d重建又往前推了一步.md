# 公里级场景也能稳住了，国产团队把长视频3D重建又往前推了一步

**来源**: 机器之心

**发布日期**: 2026-05-06^[raw/articles/公里级场景也能稳住了国产团队把长视频3d重建又往前推了一步.md]

**原文链接**: https://mp.weixin.qq.com/s/Yi8AMQ3BxcTCLUDlzvLlcg ^[raw/articles/公里级场景也能稳住了国产团队把长视频3d重建又往前推了一步.md]

## 摘要

浙江大学、地平线机器人与之江实验室发布长视频 3D 重建工作 Scal3R（arXiv 2604.08542），可处理超万帧、几千米的超大规模场景重建，输出精确相机位姿与点云，真实验证场景为浙大紫金港校区。^[raw/articles/公里级场景也能稳住了国产团队把长视频3d重建又往前推了一步.md]

核心主张是：推理时要处理超长序列，训练时也应该让模型见过超长序列——作者借助 test-time training 设计全局上下文记忆模块（GCM）与全局上下文同步机制（GCS），把训练、推理与跨 chunk 更新放进同一流程，评测中明显优于最接近的对照 VGGT-Long。^[raw/articles/公里级场景也能稳住了国产团队把长视频3d重建又往前推了一步.md]

## 核心要点

- **痛点是漂移不是"看不清"**：序列一拉长轨迹就慢慢歪，误差逐段累积，到公里级大场景被放得非常大。
- **两条既有路线各有代价**：压缩 token 会一起压掉细节与长程依赖；chunk-based 切块 + 跨块对齐实用，但要求每块局部几何都准，否则误差继续放大。
- **真正的错位在训练与测试**：训练喂短序列或局部窗口，测试却要吞几百上千帧，形态错位放大长程漂移——重点是让模型训练时就学会处理长序列。
- **GCM**：由自适应存储单元（Adaptive Memory Units）组成，逐 chunk 用自监督目标更新并跨 chunk 累积上下文，训练与测试共用同一套更新方式。
- **GCS**：用 PyTorch DDP 的 all-reduce 在不同 chunk 之间同步自适应存储单元的自监督梯度。
- **TTT 不是测试期补丁**：训练时直接采样连续长序列，用不同 GPU 分组覆盖不同有效序列长度，让测试行为与训练行为一致。
- **实测与取舍**：KITTI 上 ATE / RTE / RRE 由 VGGT-Long 的 25.94 / 9.67 / 1.71 降到 14.55 / 4.61 / 0.97，Oxford Spires 从 15.46 m 降到 4.45 m，ETH3D、Oxford Spires、VKITTI2 六项指标全优；单张 RTX 4090 可推理，150→990 帧耗时近线性、相对位姿误差稳在 0.07–0.08 m。

## 深度分析

### 漂移累积：长视频 3D 重建的真正敌人

长视频 3D 重建最怕的不是"看不清"：前面几十帧拍得再好，序列一拉长轨迹就开始慢慢歪，一口气吃掉几百上千帧时误差会一段接一段往后累，到公里级大场景被放得非常大——这是时间维度上的误差累积，而非单帧感知失败。^[raw/articles/公里级场景也能稳住了国产团队把长视频3d重建又往前推了一步.md]

街区级短序列还能靠局部几何硬扛，一旦到公里级、上万帧，任何系统性偏差都有足够时间被放大成结构性失败；文章列出的重复纹理、长距离视角变化、稀疏采样、长走廊、回环闭合，都容易让局部预测"看起来合理"，一旦局部块不准，跨块同步与长程约束就失去意义。^[raw/articles/公里级场景也能稳住了国产团队把长视频3d重建又往前推了一步.md]

### 为什么"切块 + 拼回"与事后对齐压不住误差

主流应对有两条路：压缩 token 能把更长序列塞进模型，省了计算却容易把细节和长程依赖一起压掉；chunk-based 路线先切重叠片段各自重建、再做跨块对齐，实用且扩展性好，前提却是每块局部几何预测够准，否则块间误差继续放大。^[raw/articles/公里级场景也能稳住了国产团队把长视频3d重建又往前推了一步.md]

更根本的错位在于：训练通常喂短序列或局部窗口，测试却要求模型吞几百帧甚至上千帧，这会放大长程漂移。所以重点不在"怎么处理长序列"，而在让模型训练时就学会处理长序列，再用同一套机制在测试时稳住局部几何与全局一致性。^[raw/articles/公里级场景也能稳住了国产团队把长视频3d重建又往前推了一步.md]

### Test-time training 买到的是什么

Scal3R 借助 test-time training 把长序列训练、长序列推理与跨 chunk 信息更新放进同一流程。GCM 由若干自适应存储单元（Adaptive Memory Units）组成，是一组轻量、可更新的上下文模块：每处理完一个 chunk 就通过自监督目标更新，既跨 chunk 累积并保留上下文，也让训练与测试阶段共用同一套逐 chunk 更新方式。^[raw/articles/公里级场景也能稳住了国产团队把长视频3d重建又往前推了一步.md]

### GCM 与 GCS 如何咬合，上万帧如何被摊平

处理长序列时，Scal3R 把它切成多个重叠 chunk 分配到不同 GPU 上并行跑，GCS 使用 PyTorch DDP 的 all-reduce 在 chunk 之间同步自适应存储单元的自监督梯度，使训练与推理共用同一套机制。文章把"为什么能稳住"归结为三条：长序列拆成 chunk 来算，把原本随长度平方增长的计算压力摊平成更可控的局部计算，再融合回整段序列；不是简单分块，而是逐 chunk 更新后再同步；训练时就面向长序列，直接采样连续长序列，用不同 GPU 分组覆盖不同有效序列长度。GCM 的边界也很明确：它不替代局部几何预测，只提供可更新的上下文状态把前后 chunk 接起来，前提仍是局部几何可靠；Scal3R 本身建立在 VGGT 的视觉几何能力之上。^[raw/articles/公里级场景也能稳住了国产团队把长视频3d重建又往前推了一步.md]

### 基准证据链，以及它没回答的问题

位姿 baseline 大致三类：SLAM / SfM 在条件合适时很准，但要么需要内参要么慢——COLMAP 平均一次推理要 6614.73 秒；前馈与 streaming 方法更快，但长序列漂移压不住，FastVGGT 还会遇到显存问题。最接近的对照 VGGT-Long 在 KITTI 上 ATE / RTE / RRE 为 25.94 / 9.67 / 1.71，Scal3R 为 14.55 / 4.61 / 0.97；Oxford Spires 上从 15.46 m 降到 4.45 m。^[raw/articles/公里级场景也能稳住了国产团队把长视频3d重建又往前推了一步.md]

轨迹图更直观：KITTI 00 的 ATE 是 4.298 对 8.637，Oxford Keble 04 与 Oxford Quarter 01 分别为 2.448 与 1.624，预测轨迹基本贴住真值。点云评测中 Scal3R 在 ETH3D、Oxford Spires、VKITTI2 六个指标（Chamfer Distance 越低越好、F1 越高越好）全部最优：0.11 / 0.91、0.96 / 0.96、0.40 / 0.91，对应 VGGT-Long 的 0.24 / 0.84、3.41 / 0.80、1.78 / 0.70——差距不只在局部几何更准，也源于位姿更稳：轨迹一旦漂了，拼出的点云通常也会散。^[raw/articles/公里级场景也能稳住了国产团队把长视频3d重建又往前推了一步.md]

定性结果与表格一致：Oxford Keble 04 这类大尺度校园场景中建筑轮廓与庭院结构更完整；FastVGGT、VGGT-Long、TTT3R 则容易出现局部破碎、漂散或结构发糊，原因往往不是某一帧深度错了，而是位姿与局部几何没有一起稳住。资源上 Scal3R 可在单张 RTX 4090 上推理，非吞吐最快而是在精度、稳定性与可扩展性之间取舍；150→990 帧耗时基本线性、相对位姿误差稳在 0.07–0.08 m。文章另给出与 Depth Anything 3（Streaming 模式）的可视化对比，方向与定量结论一致：前馈与 streaming 更快，但漂移压不住。^[raw/articles/公里级场景也能稳住了国产团队把长视频3d重建又往前推了一步.md]

原文并未展开局限：长序列需切成重叠 chunk 并分配到多张 GPU 并行处理，也未给出实时性、在线流式部署或显存占用细节，与 streaming 的比较停留在可视化层面——这些恰是工程选型的关键判据，需回到论文与代码仓库核实。

## 实践启示

1. **先定位误差来源再改层**：若表现为"局部都对、整体慢慢散"，先核对训练与推理的序列长度是否一致，再考虑换 backbone 或加 token。
2. **让训练分布对齐部署分布**：训练采样长度拉到接近部署长度，或用分组覆盖多个有效长度，比事后全局对齐更划算。
3. **记忆要可更新且可同步**：跨块上下文让训练与推理共用一套更新规则，并显式定义同步方式（如 DDP all-reduce）。
4. **记忆不能替代局部几何**：GCM 只负责接续前后 chunk，前提是每块局部预测够准；重复纹理、长走廊、回环闭合处应单独验证。
5. **轨迹与点云一起验收**：同看 ATE 类指标与点云 Chamfer Distance / F1，并给出随序列长度的耗时（如 150→990 帧）与显存占用。
