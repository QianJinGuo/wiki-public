# AgentWorld：多智能体协作评测基准

## 摘要

AgentWorld（arXiv:2609.31590）由 OpenAgents 联合哥伦比亚大学、宾夕法尼亚大学、首尔大学与宾州州立大学构建，是一个面向多智能体协作能力的评测基准：让多个 LLM 驱动的智能体在同一 MMORPG 沙盒中分工、沟通、共享资源并共同完成任务。主任务集上最强模型驱动的团队成功率仅 52.0%，暴露出个体能力与团队协作能力之间的巨大落差。基准以长时程任务、角色不对称与黑盒交互三大设计把「会协作」变成可测量、可归因的能力，并提出 CCE 指标追溯哪些行动与消息真正促成了成功。 ^[raw/articles/agent组队干活最强模型只完成50任务基准评测协作能力.md]

## 核心要点

- **评测环境**：MMORPG 沙盒，100 个人工设计任务 + 100 个增强变体，涵盖战斗、制作、采集、交易、探索、生存、建造与协调八类；单任务需 3–20 个智能体参与，执行预算达数十轮。
- **三大设计支柱**：角色不对称（成员拥有不同技能、物品与初始条件）、黑盒交互（无法读取队友内部推理状态）、多轮执行（开局计划无法覆盖后续变化）。
- **主任务集成功率**：Gemini 3 Flash 52.0%、Claude Haiku 4.5 45.0%、GPT-5 Mini 36.0%、DeepSeek R1-70B 20.0%；增强任务集上进一步跌至 10%–26%。
- **「做到一部分」≠「真正做完」**：Gemini 3 Flash 部分成功率 71.5% 而完整成功率仅 52.0%——中间目标推进不保证最后的资源交接或制作步骤完成。
- **聊天更多未必更好**：GPT-5 Mini 平均每任务发 44.1 条消息仅得 36.0%，Gemini 3 Flash 只发 11.0 条反而 52.0%——消息数量无法替代协作质量。
- **CCE（因果协作有效性）**：从完成的目标往回溯贡献链，成功任务的 CCE = 贡献动作数 ÷ 总动作数（示意轨迹 12/27 ≈ 44.4%）；失败任务按定义记 0。
- **高频失败模式**：重复询问已解决的问题、认错角色或资源接收者、报告错误物品信息、关键步骤尚未完成时提前宣布收工。

## 深度分析

### 评测什么：从系统结构到可验证的能力

「多个 Agent 参与」是一种系统结构，「多个 Agent 有效协作」则是一种需要验证的能力。AgentWorld 把协作放进可执行、可观察的 MMORPG 环境：资源可采集、物品可制作、敌人需应对，智能体的行动既改变环境，也决定队友下一步能做什么。标志性任务是为法师制作魔法杖：伐木工采集木材、木工加工成木棒、法师完成制作，形成一条依赖链——即便每个成员都知道最终目标，团队仍要解决「谁先做、交给谁、什么时候交」，而失败可能发生在任意一次交接：木棒准备好了没有？队友完成的步骤要不要重复做？这使协作从一段听起来合理的对话，变成一串必须真实发生的动作。

### 怎么测：用环境设计隔离协作变量

三大设计让协作难题显性化。角色不对称要求团队根据成员差异安排工作，而非让所有人执行同一套动作；黑盒交互使「我以为队友已经做完了」成为真实的失败来源，智能体只能通过环境观察、聊天和行动结果推断队友进展；多轮执行则要求团队在数十轮中持续更新状态——资源是否到位、队友是否需要支援、原分工是否仍有效。为了屏蔽低层操作的干扰，环境提供 13 个高层 API 工具（如采集、攻击封装了导航与具体执行），让模型把决策集中在「下一步做什么」和「与谁配合」上；程序化规则判定共同目标是否完成。评测并未完全排除规划与工具使用的影响，但让协作问题更可观察、可分析。

### 结果解读：最强团队也只完成一半

在统一提示模板、工具定义与交互协议下，四个模型的团队表现分层明显。三个反直觉信号值得注意：其一，部分成功率（71.5%）远高于完整成功率（52.0%），说明短板不在推进而在收尾——最后的交接与制作步骤经常掉链子；其二，增强任务集上成功率几乎腰斩（52.0%→24.0%、45.0%→26.0%），说明协作能力对任务变化的泛化非常脆弱；其三，有效通信的标准不是消息数量，而是一条消息是否更新了有效信息、消除了分工歧义、并让接收方据此采取行动。需强调：这些结果对应特定模型、提示与执行协议，不能直接外推为所有大模型的普遍上限，但足以把「当个体 Agent 不断增强，团队协作还缺什么」这个问题具体化。

### CCE：给协作过程做因果归因

只看成功率会把「分工顺畅完成」与「大量重复劳动后侥幸完成」打成同一标签。CCE 从最终完成的目标准时间回溯：这次制作依赖哪些材料？材料来自哪次转移？转移又依赖谁的采集或加工？算法借助大模型判断候选动作间的因果依赖，逐步构建行动关系图。计入的贡献不限于最后一步，凡为后续行动提供材料、条件或有效信息的准备动作（包括聊天消息）都可进入贡献链。使用时须守住三条边界：失败任务记 0 是计分约定而非价值判断；跨任务平均 CCE 同时受成功率与成功轨迹内贡献比例影响，应与成功率、部分成功率结合阅读；每任务动作占比不等于全任务汇总的总体占比。CCE 的价值在提供一个可检查的分析视角，它依赖模型判断，不能单独证明系统已具备通用协作能力。

## 实践启示

1. 多智能体系统除了「任务计划」，还必须维护一份持续变化的**团队状态**：谁完成到哪一步、资源在谁手里、下一步交接给谁——论文归纳的失败大多是状态不同步所致。
2. 衡量 Agent 团队要用**完整成功率**而非部分进度：把验收标准设为最终交接完成，并在关键交接点设置显式确认，避免「提前收工」。
3. 不要用消息量衡量协作质量。改进通信机制时应做对照实验：明确的角色分工能否减少误解？共享记忆能否同步进展？集中规划与分布执行各有什么优势？新机制是提高了完成率还是只增加了消息量？
4. 选择或设计协作评测时，优先考察是否同时具备**长时程、角色不对称、黑盒交互**三项；只测单轮或对称角色的「协作」评测容易被对话质量误导。
5. 为协作过程建立 CCE 式归因（从完成目标回溯贡献链），可区分「真协作」与「无效动作堆叠」，为 harness 与编排改进提供定位依据。
6. 外推结论要谨慎：当前数字绑定特定模型、提示、工具接口与执行协议，更丰富的规划、记忆与通信设计仍是开放探索空间。
