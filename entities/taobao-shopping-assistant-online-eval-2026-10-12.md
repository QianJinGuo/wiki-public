# 淘宝AI购物助手在线评测：LLM-as-a-Judge 日级工业化

大淘宝技术（★★★★★ 第一方）购物助手购后场景的**在线评测**完整工程实录：日均百万条会话、多域异构的线上 Agent 场景中把 LLM-as-a-Judge 做到日级全量工业化运行——与美团图灵评测（[[entities/meituan-turing-agent-evaluation-methodology-2026-08-06|离线分层评测方法论]]）互补，本文的不可替代维度是**线上脏数据清洗 + 分布式推理工程 + 日级全量的持续收敛闭环**。^[raw/articles/taobao-shopping-assistant-online-eval-2026-10-12.md]

## 问题定义：为什么离线评测和 AB 实验都不够

离线评测测构造好的数据（query 精心设计/工具返回可控），线上用户表达模糊带情绪、工具返回缺失异常、分布持续漂移——离线通过率达标≠线上体验好；AB 实验粒度太粗（转化率下跌无法定位是路由错了还是回复编造）。**执行成功率 = 路由准确率 × 回复正确率**（三层漏斗复合指标），目标是把质量观测从月度/季度人工抽检变成日级自动观测。^[raw/articles/taobao-shopping-assistant-online-eval-2026-10-12.md]

## 四层数据清洗（学界假设干净输入，本文核心增量）

线上原始日志不是为评测设计的，四层清洗 pipeline 随各域推进依次沉淀：^[raw/articles/taobao-shopping-assistant-online-eval-2026-10-12.md]
1. **修复数据格式不一致**：各 skill 卡片协议独立、字段各异，逐域对标离线 Prompt 的数据定义修复解析+字段映射；卡片文本数千字拼接超长需截断。
2. **语义对齐**：用户说"已揽收"vs 系统英文枚举值不天然等价更≠"已发货"——Prompt 中显式建立用户语义与系统语义映射，否则 Judge 按字面误判。
3. **屏蔽干扰信号**：tool_calls_json 含工具接口内部生产链路提示词，会被 Judge 误读为 Agent 回复——正则剔除只保留调用参数与返回值，屏蔽后各域准确率均明显提升。
4. **过滤规则精化**：入口过滤过宽导致大量非本域 query 混入（咨询政策≠真实发起操作），按 skill 标识精确过滤——某流程域通过率异常偏低的真因是 Prompt 不适配线上数据而非 Agent 质量差。

## 分布式推理工程：数仓与推理平台解耦

"数据归数据、推理归推理"：推理平台只做 LLM 推理，清洗/拼接/过滤与解析/归一化/聚合全在数仓 SQL——改 Prompt 不动数据逻辑，改过滤不重跑推理。按域拆独立 workflow（避免短板效应/故障扩散/迭代耦合），单域数千到数万条/天、运行 2-3h。工程踩坑：**Check 节点校验 input/output 条数一致**（公共资源池高峰超时丢数；回刷分区是叠加非覆盖，不清空会重复计算）、**token 预检**（超上下文窗口平台静默返回空不报错）、错峰调度+关键域独占资源。^[raw/articles/taobao-shopping-assistant-online-eval-2026-10-12.md]

## CNT 六层漏斗 Rubric 框架（归因基石）

全域统一的六层漏斗，层间短路串联（任一层判 0→后续层 N/A、整体判 0），**RED 恒评不受短路影响**：^[raw/articles/taobao-shopping-assistant-online-eval-2026-10-12.md]
- **CTX 上下文门控**：证据不足整条标不可评不进分母——"诚实跳过优于强行评分"（唯一产生 N/A 的层）
- **OOSR 越界拒答**：query 不该由当前 skill 承接时是否正确拒答
- **OOC 能力边界诚实**：范围内但超能力时是否诚实说明而非编造
- **TCC 工具执行链路**：工具/参数/链路自洽
- **CNT 内容文本**：正确性/完整性/表达，域差异最大层（时效域防凭空"已签收"、检索域逐条校验时间/商品/属性/状态/店铺/逻辑组合、服务规则域防规则被反向弱化或编造）
- **RED 安全红线**：内部信息外泄/隐私/敏感词/违规引导/编造政策五条独立核查

**用户型产品特性设计**：模式判定与诚实兜底放行（工具返回空时忠实兜底+引导=产品预期行为，不扣分）；意图码驱动评测路径分流（某正向意图命中即 CTX 硬退出判通过）；卡片结构化数据盲区兜底（留空恒 N/A+"严禁假设可读取卡片数据"+"严禁因看不到而判 0"）。Rubric 以 Markdown+YAML 版本元数据存代码仓库，数十次迭代全有 changelog，在线 Prompt 直接从 Rubric 文件生成（文档与 Prompt 不两套）。框架统一+分域子项码（各域十几个子项）并存。^[raw/articles/taobao-shopping-assistant-online-eval-2026-10-12.md]

## Judge 模型与 Prompt 工程

模型选型：指令遵循+结构化输出优先（Judge 任务本质是"按 Rubric 做分类判定"不是生成）；轻量模型在多条件复合判定/边界 case/跨轮一致性上明显不如大模型——难度在"按规则做复杂判断"非语言理解；分阶段策略（先大模型+Prompt 验天花板并沉淀人标数据，后 SFT 蒸馏小模型降本）；temperature=0.1 梯度实验定值（0 会偶发僵死，高了同 case 多次结果不一致）。Prompt 幻觉压制/时间锚点（"明天到达"类表述 Judge 无法验证）/跨轮隔离防维度串味。^[raw/articles/taobao-shopping-assistant-online-eval-2026-10-12.md]

## 持续收敛闭环与归因

每轮迭代：抽样打标→Judge-Human 一致性校验→归因分析→优化 Prompt/Rubric→发车→重抽样；数科管"怎么评"（pipeline/Prompt/指标），测试产品管"评什么"（标准/严格程度）。评测归因可区分**数据层/Prompt 层/Rubric 层/Agent 真实质量**四类问题并驱动定点修复验证——核心结论：**评测可信度的瓶颈不在 Judge 模型本身，而在数据质量和评测标准的持续校准**。^[raw/articles/taobao-shopping-assistant-online-eval-2026-10-12.md]

## 深度分析

### 第一性问题：喂进去的东西对不对，而非判得准不准

把 LLM-as-a-Judge 推到日均百万条会话的量级，最先撞墙的不是模型能力而是输入质量。学界评测默认输入是为评测构造的干净样本：query 意图明确、工具返回可控、字段语义与 rubric 同构；线上日志三条全不成立——各 skill 卡片协议各自一套字段，用户口语（"已揽收"）与系统英文枚举值之间没有天然等价关系，tool_calls_json 里还夹着工具接口内部的生产链路提示词。任何一类噪声都会让 Judge 在"读懂"之前就已经读错：格式决定它能否解析，语义对齐决定它按字面判还是按意图判，干扰屏蔽决定它把谁当成 Agent 的输出，过滤精化决定分母里站着谁。

最有信息量的是那条反例：某流程域通过率异常偏低，真因是 Prompt 不适配线上数据而非 Agent 质量差。这说明**通过率是受测量装置影响的读数，不是 Agent 的固有属性**——在证明"读数可信"之前，任何分数都不能直接进决策。可操作的形式是把每层清洗做成可开关的变量做对照，用准确率增量证明它值得存在（文中"屏蔽后各域准确率均明显提升"即此种证据形态）；这正是 [[concepts/data-quality-framework|数据质量框架]] 在评测语境的落地。

### 六层漏斗把"分数"变成"可归因的证据"

标量分数只能回答"好不好"，不能回答"哪一层坏了"，而后者才是能驱动修复的信息。CNT 六层漏斗把"执行成功率 = 路由准确率 × 回复正确率"这个乘法假设翻译成一条短路串联的判定链：任一层判 0 则后续层 N/A、整体判 0。短路本身就是归因机制——第一个失败的层直接给出责任归属：路由错了就不必再判内容，因为内容再准确也送错了人。层序即因果序。

三个细节各自承担不同职责：CTX 是唯一产生 N/A 的层，把证据不足的样本整体移出分母，避免不可评样本稀释通过率（诚实跳过优于强行评分）；RED 恒评、不受短路影响，保证"前面全过"无法掩盖安全违规；意图码驱动的路径分流让"正确拒答"与"内容答错"落在不同判定路径上，防止把产品预期行为记成失败。分域子项码再把 CNT 层内部拆到可执行粒度——时效域防凭空"已签收"、检索域逐条校验时间与商品属性、服务规则域防规则被反向弱化，三者需要的修复动作完全不同。这样 rubric 就从打分表变成了 [[concepts/evaluation-harness-design|评测 harness]] 的判定树。

### Judge 偏差、Rubric 漂移与闭环的自检

在线 Judge 有两类系统性风险：模型侧偏差（宽松倾向、被长文本与自信措辞带走、把幻觉当事实、跨轮维度串味）与标准侧漂移（rubric 经数十次迭代后，同一段对话在不同版本下得分不可比）。文章把两者都工程化处理：模型侧靠指令遵循+结构化输出优先的选型、temperature=0.1（0 会偶发僵死，高则同 case 结果漂移）、幻觉压制与时间锚点（"明天到达"类表述 Judge 无法核验，必须显式告知）、跨轮隔离防维度串味；标准侧把 rubric 以 Markdown+YAML 版本元数据入库、每次迭代留 changelog，并让在线 Prompt 直接从 rubric 文件生成，等价于把"标准"本身纳入版本控制。

漂移的真正探测器是每轮的 Judge-Human 一致性抽检。它同时防两种误读：把 Judge 变严读成 Agent 变差，把 rubric 放水的分数上涨当成绩。配合数据层/Prompt 层/Rubric 层/Agent 真实质量四类归因，闭环的目标不是"让分数涨"而是"让分数可解释"。这也解释了那句结论——瓶颈不在 Judge 模型本身，而在数据质量与评测标准的持续校准。

### 什么能迁移，什么不能

可迁移的是骨架：漏斗式 rubric（短路+门控+恒评红线）、rubric-as-code、数据面与推理面解耦、按域拆独立 workflow，以及"抽样打标→一致性校验→归因→改标准→重抽样"的闭环节律。这些与业务形态无关，任何具备结构化信号（意图码、工具调用、卡片）的 agent 都能照抄。

不可迁移的同样清楚：CTX 门控与意图码分流依赖助手已有的强结构化信号，纯开放域对话没有等价的"证据充分性"判据；卡片盲区兜底是特定 UI 形态的补丁；日均百万条的成本模型要求数仓与推理平台同时到位；"数科管怎么评、测试产品管评什么"是组织安排而非技术方案。另需注意这是第一方工程复盘：它交付的是可复用模式与踩坑清单，未披露绝对一致性数值，选型时应视其为方法论模板而非效果基准——离线受控场景仍宜先用 [[entities/meituan-turing-agent-evaluation-methodology-2026-08-06|美团图灵评测方法论]] 建分层基线，再用本文的在线闭环做分布漂移监测。

## 实践启示

1. **先修数据，再调 Judge。** 逐域完成格式修复、语义对齐、干扰屏蔽、过滤精化，并把每层做成可开关对照，用准确率增量决定去留；清洗层是评测能力的组成部分，不是前置杂活。
2. **用漏斗替代标量。** 每层独立子项码、层间短路、RED 恒评不短路、CTX 单独承担 N/A 并移出分母，让"第一个失败的层"直接输出责任归属。
3. **把 rubric 当代码管理。** Markdown+YAML 带版本元数据入仓，改动留 changelog，在线 Prompt 由 rubric 文件生成，从根上杜绝文档与 Prompt 双份漂移。
4. **数据面与推理面解耦。** 清洗/拼接/过滤与解析/归一化/聚合留在数仓 SQL，推理平台只负责 LLM 调用；改 Prompt 不动数据逻辑，改过滤不必重跑推理，按域拆 workflow 限制故障半径。
5. **三道工程护栏必装。** Check 节点校验 input/output 条数一致（防资源池高峰超时丢数）、token 预检（超窗平台静默返回空而不报错）、回刷分区用覆盖而非叠加（否则通过率失真）。
6. **闭环必做一致性抽检与四类归因。** 抽样打标→Judge-Human 一致性→数据/Prompt/Rubric/Agent 归因→定点修复→重抽样；缺这一步，分数变动无法区分"模型变差"与"尺子变了"，同时要明确 owner 分工（怎么评 / 评什么）。
