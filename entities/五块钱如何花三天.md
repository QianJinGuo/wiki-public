# 五块钱如何花三天...

## 摘要

horsley 是腾讯应用开发高级工程师，这篇文章的起点是额度收紧之后，团队怎样更稳定、更可持续地使用 Agent。他给出的判断是：Token 成本管理的第一步不是让每个人更克制，而是让浪费变得可见——大量消耗并不发生在难题上，而是消失在 IDE 里的黑盒绕路中。真正的解法同样不是几个省 token 的小技巧，而是把可观测、经验沉淀、模型分层与工具治理做成平台能力，让省 token 从个人技巧变成系统能力。^[raw/articles/五块钱如何花三天.md]

## 核心要点

- **真问题是浪费不可见**：从外部只看得到结果，看不到 agent 有没有选错模型、反复读旧上下文、工具失败后重试，或因为环境问题绕远路。
- **四类典型浪费**：任务与模型不匹配、上下文越来越厚、工具与 MCP 输出太吵、失败后一轮轮重来；单次看都不大，但每天反复发生就会成为账单上的大头。
- **值得花的钱和该治理的钱要分开**：复杂设计、关键判断、疑难排障、探索新 workflow 换来的是真实进展；该治理的是模型错配、上下文膨胀、工具噪音和失败重试这些低质量消耗。
- **靠个人自觉控成本不可持续**：谁知道该用便宜模型、谁记得哪个 prompt 稳、谁的机器工具链更顺，换个人、换台机器、换一轮会话，经验就容易归零。
- **平台至少要提供四件事**：过程可见（tool call、失败重试、token 花费位置）、经验可沉淀（记录任务适合什么模型 / prompt / skill）、实验可回放（在同一状态下比较不同方案）、环境可统一（减少本地差异带来的绕路）。
- **输出也是上下文**：caveman 的经验说明少寒暄、少复述、结论优先，可以减少后续的语言垃圾。
- **工具输出不该原样喂给模型**：RTK 的经验是先过滤、聚合、截断、去重，再交给模型。
- **最终共识**：先把不同浪费拆开看，再承认只靠个人兜底不可持续，最后把可观测、经验沉淀、模型分层和工具治理做成平台能力——这样 Token 成本管理才不是一场临时省钱运动，而是一次真正的工程化治理。

## 深度分析

### 一、四类 Token 黑盒与「只看结果」的观测盲区

文章把 Token 浪费归纳成四类：任务和模型不匹配（低复杂度任务也默认上顶级模型）、上下文越来越厚（长对话里旧信息、工具输出、历史判断不断累积）、工具和 MCP 太吵（日志、测试、命令输出里大量噪音被原样塞进上下文）、失败反复重来（依赖缺失、参数错误、工具失败导致 agent 一轮轮尝试）。它们共同的特征是单次金额都不大，但每天反复发生。^[raw/articles/五块钱如何花三天.md]

更麻烦的是观测位置。在 IDE 的 vibe coding 场景里，人只看到结果，看不到过程：开销发生在 tool call 的往返、失败的 retry、上下文的重新装载上，而账单只呈现一个总数。这就是「看不到过程、只看结果」的盲区——缺少过程可见性时，任何关于节省的建议都只能落回个人直觉。^[raw/articles/五块钱如何花三天.md]

顺着这一点往下推，控制点其实只有两处：一是让每一步消耗可归因（哪个任务、哪次工具调用、哪个模型花了多少），二是把「本可以避免的部分」与「必须付出的部分」区分开。前者是度量问题，后者是价值判断问题——这也正是单纯分析账单不足以指导行动的原因。

### 二、从「省 Token 技巧」到「系统化治理」

horsley 明确说，自己要讲的不只是几个省 token 的小技巧，而是额度收紧后团队怎样更稳定、更可持续地使用 Agent。技巧针对的是一次性的消耗，治理改变的则是消耗产生的机制。^[raw/articles/五块钱如何花三天.md]

系统化治理至少包含四个要素，四者缺一不可：**预算**——给任务、角色或会话设定消耗上限，让「用多少」成为设计输入；**配额**——在组织层面分配额度，把稀缺性显性化；**归因**——把消耗落到具体的任务、模型、工具与人的组合上，而不是一张总账单；**可观测性**——暴露 tool call、retry 和上下文膨胀的位置，让前三个要素有数据基础。

文章中的四点平台要求，正是可观测性与归因在平台层的具体形态：可回放让方案比较有对照组，环境统一则直接消灭了一整类「绕远路」。当这些成为默认能力，成本控制就不再依赖某个人的记忆和自觉，而变成团队可复用的基础设施。

### 三、为什么 Agent 场景让传统成本管理失效

文章指出，现在很多节省方式都靠个人经验：谁知道该用便宜模型，谁记得哪个 prompt 稳，谁的机器工具链更顺；但换个人、换机器、换一轮会话，经验就容易归零，团队不能长期靠个人自觉控成本。^[raw/articles/五块钱如何花三天.md]

更根本的原因在于计量单位变了。传统软件成本与代码行数、工时、机时近似线性相关，而 agent 的 token 消耗与代码行数、任务难度都脱钩：同一个结果可能五轮走完，也可能五十轮才走完，差别来自模型选择、上下文厚度、工具噪音和失败率。当「输入规模」而不是「产出规模」决定账单时，按人力或按产出分摊成本的旧方法就失去了基准，成本必须按过程而不是按结果来度量。

这也解释了 agent 成本为什么天然是长尾的：少数难题值得花钱，大量日常任务却在低质量消耗上漏损。若不把两者拆开，压缩预算只会误伤真正需要算力的探索，而漏损依旧照常发生。

### 四、治理的经济学：度量本身也有成本

文章的取舍很明确——复杂设计、关键判断、疑难排障、探索新 workflow，这些 token 花得值，因为它们换来真实进展；真正该治理的是模型错配、上下文膨胀、工具噪音和失败重试这些低质量消耗。^[raw/articles/五块钱如何花三天.md]

由此得到一个不太直觉的结论：治理不是「花得越少越好」，而是在「度量的成本」与「漏损的规模」之间取舍。埋点、trace、评审都要占用人和 token，只有当可见的漏损显著大于观测开销时，投入才划算。因此合理的路径是先按任务类型与角色归因，找出漏损最集中的一两个口子，再谈降本目标。

把预算前置为设计约束，而不是事后审计，是这套经济学里最关键的一步。事后审计只能追责，改变不了 agent 的决策；而把预算写进 workflow——给子任务指定模型档位、给上下文设上限、给工具输出设过滤规则——成本就成了 harness 的一部分，而不是月末才被发现的意外。

### 五、与 Harness / 上下文工程的关系

文章的落脚点是一句判断：真正有效的 token 优化，不靠人临场克制，而要做进 workflow。^[raw/articles/五块钱如何花三天.md]

这恰好是 harness 工程与上下文工程的成本面。上下文预算是其中最直接的一环：每轮把多少历史、多少工具输出带进 prompt，直接决定了重复计费的规模；渐进式披露把「先给索引、按需取正文」变成默认动作，让信息只在被需要时才付费；缓存命中率则决定重复前缀是复用还是重算——命中率每下降一档，成本曲线上就会多出一段陡坡。三者共同说明，成本不是模型参数的属性，而是上下文调度策略的函数。

也正因如此，工具侧治理（过滤、聚合、截断、去重）与输出侧治理（少寒暄、少复述、结论优先）在机制上是同一件事：减少进入后续上下文的无效字节。RTK 与 caveman 这两个例子，正好分别从输入和输出两端验证了这一点。^[raw/articles/五块钱如何花三天.md]

## 实践启示

1. **先装可见性，再谈省钱**。在提出任何降本目标之前，确保能回答「这次任务的钱花在哪一步、哪个模型、哪次重试上」。
2. **把「值得花」和「该治理」分账**。为探索性、高判断密度的任务保留高模型预算，对日常任务做明确的模型分层。
3. **给上下文设预算**。限制历史轮数与工具输出体积，默认过滤、聚合、截断、去重，而不是把原始输出原样塞进 prompt。
4. **让预算成为设计约束**。把模型档位、上下文上限、工具输出规则写进 workflow 与 skill，而不是留给人临场克制。
5. **按任务与角色归因**。用归因数据找出漏损最集中的口子，把治理资源先投到那里，而不是平均用力。
6. **把经验沉淀成平台能力**。记录「这类任务适合什么模型、prompt、skill」，让下一轮会话不必从零试错。
