传统的软件开发流程中，我们会先写需求文档、设计文档，再进行编码。但在 AI 编程时代，尽管工具越来越强大，从 PRD 到可直接上线的代码，自动化流程仍然不够顺畅。 ^[raw/articles/从-prd-到代码ralph-驱动的自治-ai-智能体执行循环.md]

Ralph 正是为了解决这一问题而设计。它基于 Geoffrey Huntley 提出的 Ralph 循环模式  [1]  ，通过不断启动 AI 编码工具（Amp 或 Claude Code），逐条处理 PRD 中的任务，直到所有事项完成为止。 ^[raw/articles/从-prd-到代码ralph-驱动的自治-ai-智能体执行循环.md]

在上一篇文章  简单就是美！Claude Code Ralph循环机制详解  中，我们已经系统了解了 Ralph 如何接管重复性工作，并保证任务可靠完成。 ^[raw/articles/从-prd-到代码ralph-驱动的自治-ai-智能体执行循环.md]

在本文中，我将带你看看 Ralph 是如何实现 自动化开发 的，包括它的核心原理、完整流程、最佳实践，以及在实际项目中的应用效果。 ^[raw/articles/从-prd-到代码ralph-驱动的自治-ai-智能体执行循环.md]

## 核心原理

### 架构设计：Bash 循环 + AI 实例

Ralph 的架构其实很简单。核心是一个 Bash 循环脚本：每轮迭代启动一个新的 AI 实例，读取 PRD 数据，只处理一个明确的任务，然后进入下一轮。 ^[raw/articles/从-prd-到代码ralph-驱动的自治-ai-智能体执行循环.md]

创建 PRD

    ↓  
ralph.sh（Bash 循环）  
    ↓  
启动 AI 实例 → 读取 prd.json → 选择未完成任务  ^[raw/articles/从-prd-到代码ralph-驱动的自治-ai-智能体执行循环.md]

    ↓  
实现单个任务 → 运行质量检查 → 提交代码 → 更新 AGENTS.md / CLAUDE.md  ^[raw/articles/从-prd-到代码ralph-驱动的自治-ai-智能体执行循环.md]

    ↓  
更新 prd.json → 将经验写入 progress.txt → 进入下一轮  ^[raw/articles/从-prd-到代码ralph-驱动的自治-ai-智能体执行循环.md]

    ↓  
所有任务完成 → 输出 <promise>COMPLETE</promise> ^[raw/articles/从-prd-到代码ralph-驱动的自治-ai-智能体执行循环.md]

这种设计的关键在于： 每一轮迭代都使用全新的上下文窗口。^[raw/articles/从-prd-到代码ralph-驱动的自治-ai-智能体执行循环.md]


AI 不依赖之前的对话记忆，而是通过外部存储（ Git 历史 、  progress.txt  和  prd.json  ）来获取状态。这样既避免了上下文不断累积带来的限制，也能确保每次迭代都基于最新、可审计的项目状态。 ^[raw/articles/从-prd-到代码ralph-驱动的自治-ai-智能体执行循环.md]

### 核心概念

每次迭代 = 全新 AI 实例

在 Ralph 的流程里，每轮都会启动一个新的 AI 实例（Amp 或 Claude Code），不沿用之前的对话记录，上下文都是全新的。 ^[raw/articles/从-prd-到代码ralph-驱动的自治-ai-智能体执行循环.md]

需要保留的状态，都放在外部：

- •
  Git 历史
  ：记录开发过程中的变动和约定

- •
  progress.txt
  ：保存当前进度和关键经验

- •
  prd.json
  ：任务列表及完成情况

小任务原则

每个 PRD 里的任务最好一次就能做完。任务拆得不够细，模型还没写完，上下文就快满了，后面的代码质量肯定会受影响。 ^[raw/articles/从-prd-到代码ralph-驱动的自治-ai-智能体执行循环.md]

比较合适的任务例子（一次迭代能完成）：

- • 添加一个数据库列并编写迁移

- • 在现有页面中新增一个 UI 组件

- • 修改一段已有的服务端逻辑

- • 给列表页加一个筛选下拉框

明显偏大的任务（需要继续拆分）：

- • 实现一个完整的仪表板

- • 新增一整套认证/登录体系

- • 对现有 API 做整体重构

## 深度分析

### 新上下文架构：外部状态为何胜过对话记忆

Ralph 最反直觉的设计选择，是每一轮迭代都抛弃上下文、启动全新 AI 实例，而不是让一个会话越聊越长。表面上看这是浪费——每次都要重新"认识"项目——但实际上它解决了长会话模式下的三个顽疾：

- **上下文膨胀的不可逆性**：对话式记忆只增不减，历史轮次中的错误尝试、废弃方案、无效讨论会持续占据窗口，稀释模型对当前任务的注意力。外部状态（Git 历史、progress.txt、prd.json）则是可整理、可裁剪、可验证的——每轮新实例读到的永远是蒸馏后的结论，而非原始过程的泥沙。
- **状态的可审计性**：对话记忆对人是黑箱，"AI 之前到底知道什么"无法事后核查。Git 提交、任务清单、经验笔记都是磁盘上的真实文件，出错时可以精确定位是哪一轮写入的状态有误。
- **故障隔离**：某轮实例跑偏或产出低质量代码时，污染范围被限制在那一次迭代内。下一轮从干净上下文出发，读取的是经过质量检查与提交的确定状态，而不是被污染的对话尾巴。

这实质上把"记忆"从模型内部转移到了工程化的外部存储——与 [[concepts/context-management-agent-systems|上下文管理]] 中"外部化优于内化"的思路一致。

### 小任务原则与上下文窗口经济学

Ralph 把任务粒度当作一等工程参数，而不是随意的需求切分。其经济学逻辑是：**上下文窗口是每轮迭代中刚性的、且随进度递减的预算**。任务拆得越粗，窗口内留给"读代码—写代码—调试—修复"的余量越小，后段产出质量的衰减就越明显。

文中的例子给出了清晰的粒度标尺：加一列数据库字段、在现有页面塞一个 UI 组件、改一段服务端逻辑，属于一次迭代可以干净完成的量级；而"完整仪表板""整套认证体系""整体 API 重构"这类任务，本质上是多个独立决策的打包，强行塞进单轮必然导致中途上下文告急、实现粗糙。

更深的含义是：任务拆分质量直接决定了循环能否收敛。粒度合适的任务形成"实现 → 检查 → 提交"的短反馈环，错误在当轮被捕获；粒度过大的任务则把多个反馈环折叠成一个，中途失败时既不知道哪部分有问题，也没有可提交的中间态可以止损。

### 信任的转移：从逐步验证到迭代收敛

传统自动化对 AI 的用法是"每一步都要人确认"，本质上是把 AI 当作需要监督的执行器。Ralph 代表了另一种信任模型：**不盯每一步的对错，而是相信反馈循环会把系统拉回正轨**。类型检查、自动化测试、CI 组成的反馈层，取代了人工逐步审查，成为质量的主要守门人。

这种信任转移的成立有三个前提：反馈信号必须及时（错误在当轮被发现，而不是几轮之后）；外部状态必须真实（prd.json 的 passes 标记、Git 提交不能撒谎）；迭代次数必须有上限（max_iterations 默认 10，防止无限重试的成本失控）。三者齐备时，单步的失败不再致命——收敛性替代了正确性，成为系统层面的质量属性。这与 [[concepts/harness-loop-architecture|Harness Loop 架构]] 把验证内建进循环的思路一脉相承。

### 工作流优先 vs 概念优先的采纳路径

文章的展开顺序本身就是一种采纳策略的示范：先讲 Bash 循环这个极简架构，再讲 PRD → prd.json → ralph.sh 的三步工作流，最后才是安装方式与实战。这种"先能跑起来、再理解为什么"的路径，与先灌输理论再动手的传统教学相反。

对循环类工具而言，这个顺序是刻意且必要的：Ralph 的概念（新上下文、外部状态、小任务）只有在一轮轮迭代实际跑过之后才有体感——progress.txt 里积累的经验、Git 历史中的原子提交，都是概念的具体化身。概念先行者容易在抽象层面认同却在实践层卡壳；工作流先行者则在使用中自然撞见这些概念。这也是 [[concepts/loop-engineering-methodology|Loop Engineering 方法论]] 强调"从最小可运行循环开始"的原因。

## 实践启示

1. **把状态写进文件，而不是指望会话**：任何跨迭代需要保留的东西——进度、经验、约定——都应该落在 Git 历史、progress.txt 或任务清单这样的外部文件里。可持久化、可审计的状态，比对话记忆可靠得多。
2. **用"一次迭代能否干净完成"作为任务拆分的验收标准**：写下任务时问一句——模型能否在窗口耗尽前完成实现加质量检查？如果答案犹豫，就继续拆。"实现整套认证系统"不是任务，是一张任务清单。
3. **先搭反馈层，再开循环**：类型检查、测试、CI 是循环的刹车系统。没有可靠的反馈信号就启动自治循环，等于放任错误跨迭代累积——先确保 `npm run typecheck` 和 `npm test` 能在当轮给出明确的是非判断。
4. **持续维护 AGENTS.md / CLAUDE.md 作为机构记忆**：每轮迭代发现的代码模式、常见陷阱、关键上下文，都应该沉淀进 AI 编码工具自动读取的说明文件。这既是给下一轮实例的交接文档，也是给后续人类开发者的入场指南。
5. **为循环设预算上限并保留逃生通道**：max_iterations 这类硬上限防止成本失控；当循环卡住时，手动查看未完成任务、运行质量检查定位问题、修复后重启，比放任其空转更经济。
6. **按场景选型，自治循环不是万能锤**：功能迭代、小模块开发、有清晰验收标准的原型适合交给循环；探索性开发、大规模重构、安全关键代码、深度性能优化仍然需要人的判断在场。
