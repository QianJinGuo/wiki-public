# 从 Coder 到 Designer：电商团队数据研发的 Harness Engineering 实践

阿里技术（白林林）分享的电商团队数据研发 AI 化实践，目标是让 AI 像资深数研一样思考，且比人类更稳定、更可追溯、越用越准。项目围绕「数据研发效率提升」和「数据价值交付」两个命题，调研发现两个共性问题：横向拓展能力不足（已有平台能力换业务接入只能发挥约 30%）、数据资产沉淀不足（NL2SQL 准确度强依赖语义层资产质量且缺乏统一标准）。问题的本质是「数据研发的知识是碎片化的，流程是非标准化的」，解法是知识工程（解决「AI 凭什么能做对」）+ Harness Engineering（解决「AI 如何稳定运行」）双轮驱动。^[raw/articles/从-coder-到-designer-电商团队数据研发的-harness-engineering-实践.md]

方案复用兄弟团队 NL2SQL 约 60% 已有能力，自建业务域特有的数据资产、预定义 SQL 模板、业务语义知识库，在大促场景完成落地。语义层走 NL2DSL2SQL 路线：先将自然语言映射到标准化的指标-维度语义，再从语义生成 SQL；指标治理遵循「先治理再录入」原则，计划通过「标准名称+别名映射+语义边界」规范体系解决同义词混用导致的 RAG 召回偏差，并构建资产防腐双循环机制（上线前数仓小组拦截语义重复资产，上线后定期资产健康度评估清理冗余）。^[raw/articles/从-coder-到-designer-电商团队数据研发的-harness-engineering-实践.md]

## 知识工程：让 AI「有据可依」

建设三层架构的知识体系：方法论层（Spec 指导需求分析、Plan 规范技术方案、Task 定义执行标准，形成「文档即接口」的多 Agent 协同机制，实现 SPEC→PLAN→SQL 链式生成）、协作机制（文档状态机驱动 8 阶段研发流程，AGENTS.md 记录协作规范、Skills 引擎执行核心操作、Knowledge 库沉淀研发经验）、执行原则（基于数研经验初始化，通过需求调试持续优化）。质量保障有三层安全网：流程标准化（配置文件和技能清单固定流程）、质量把关（技术规范+人工复核双重保险）、知识管理（业务经验和调优方案系统化沉淀）。知识消费的核心是「研发即沉淀」——SPEC、PLAN、SQL、验证报告自动归档到 Archival Memory，踩过的坑记录到 anti-patterns.md，从「人可用」转型到「AI 可食」的资产格式。^[raw/articles/从-coder-到-designer-电商团队数据研发的-harness-engineering-实践.md]

## Harness Engineering：让 AI「稳定可控」

Harness Design 的核心目标不是让模型更聪明，而是通过结构化控制而非算法优化，确保 AI 在复杂任务中稳定、安全、可回溯地运行：分离关注点（决策与执行分离、知识检索与代码生成分离）、施加约束（Gate 机制、规范校验、强制审批）、管理上下文（控制信息输入量）、管理熵值（持续「整理」和「矫正」防止行为漂移）。与传统 CI/CD Pipeline 相比，Harness 需要额外处理的核心挑战是 AI 的不确定性——传统 Pipeline 每步是确定性的，AI Agent 每步都可能产生意料之外的输出。^[raw/articles/从-coder-到-designer-电商团队数据研发的-harness-engineering-实践.md]

团队构建了 7 Agent 协同工作流（老架、小需、小语、小检等角色），采用顺序协作模式（Agent 按预定义顺序执行，形成严格流水线）和反馈循环模式（下游发现问题可回滚到上游环节）的组合，关键节点人工 Gate 审批——「AI 做执行，人做决策」。稳定性工程针对幻觉：技能幻觉检测 Hook（技能执行后自动对比声称结果与实际系统状态）、执行结果强制校验（关键操作必须产出可验证产物）、日志必看原则；空间隔离（独立 Workspace、`{domain}_{date}_{seq}` 命名规范、MCP/Skill 加载路径优先级）；配置治理（自动化 Git 备份、agents.md 同步机制、模板化重新配置）。^[raw/articles/从-coder-到-designer-电商团队数据研发的-harness-engineering-实践.md]

## 自动化自我迭代：心跳机制

心跳机制分三层：执行监控（定期回顾执行历史、成功率、失败原因、用户修正记录）→ 模式识别（识别反复出现的问题模式，如某类指标 RAG 召回准确率持续偏低）→ 自动优化（优化 Prompt 模板、补充知识条目、调整工作流参数）。最关键的一点是人工修正 Agent 行为时产生的反馈会被自动捕获并写回知识库和规则配置——实现「以 Agent 养 Agent」，通过人对大模型的反馈实现大模型的「经验升级」。^[raw/articles/从-coder-到-designer-电商团队数据研发的-harness-engineering-实践.md]

## 演进方向：从 Coder 到 Designer

最终愿景是实现「只做选择，不做配置」：数研同学的角色从「写代码的人」转变为「做设计的人」，人专注于需求理解、方案选型、质量决策，AI 负责资产检索、代码生成、环境部署、数据验证等一切可自动化的执行工作。知识工程确保 AI「做对事」，Harness Engineering 确保 AI「稳定做事」，两者协同构成数据研发 AI 化的完整技术底座；从 NL2SQL 到 ChatBI 的延伸则把这套能力从「服务数研同学」拓展到「服务业务用户」。^[raw/articles/从-coder-到-designer-电商团队数据研发的-harness-engineering-实践.md]

## 深度分析

### 为什么知识工程必须先于 Harness Engineering

文章给出的双轮驱动结构里，两个轮子并非平级并列：知识工程回答「AI 凭什么能做对」，Harness Engineering 回答「AI 如何稳定运行」——前者定义正确的目标，后者保证过程不出格。从实践顺序上看，先有结构化知识（语义层资产、指标定义、SQL 模板、anti-patterns）再谈管控才有意义：没有「让 AI 有据可依」的依据，Gate 机制和幻觉检测 Hook 只能验证 AI 没做错事，却无法验证它做的是对的事。文章的调研结论也印证了这一点——NL2SQL 准确度强依赖语义层资产质量，即使模型能力到位，「成交金额/GMV/交易额」同义词混用仍会直接导致 RAG 召回偏差和出码错误。这也解释了团队为什么采取「先治理再录入」的指标治理原则：知识资产的准入标准是整个体系的前置条件，而 Harness 是在其上运行的保障层。这一「知识护城河优先于管控框架」的判断与 [[concepts/harness-engineering-framework|Harness Engineering 框架]] 中「模型之上是外部系统」的定位互为补充。

### 心跳机制：组织级自动化的雏形

心跳机制常被读作单个 Agent 的自省能力，但从组织视角看，它更接近一种自动化运营流程：第一层执行监控（成功率、失败原因、用户修正记录）相当于组织的质量看板；第二层模式识别（某类指标 RAG 召回持续偏低、某业务域返工率高）相当于把日常运维中「老师傅的直觉」形式化为可检测的信号；第三层自动优化（改 Prompt、补知识条目、调工作流参数）则把改进行动本身交给系统执行。其中最有杠杆的设计是人工反馈的自动回写——数研同学每次修正 Agent 行为，都会被捕获进知识库和规则配置，实现「以 Agent 养 Agent」的经验升级。这实质上把「人教 AI」从一次性纠偏变成了持续的组织资产积累：员工离职时经验不再流失，反而沉淀为系统约束。它对应了 [[concepts/agent-self-improvement-loops|Agent 自我改进闭环]] 的执行—评估—优化—再执行循环，也是知识工程「研发即沉淀」原则在管控层的自然延伸。

### Coder→Designer 转变对数据工程师意味着什么

「只做选择，不做配置」的愿景常被简化为「AI 替代写代码」，但更准确的读法是角色重心的迁移而非岗位消失。数据工程师的工作被拆成两类：可自动化的执行（资产检索、代码生成、环境部署、数据验证）交给 AI 流水线；不可自动化（或不应自动化）的判断（需求理解、方案选型、质量决策）保留在人手中，由人工 Gate 审批把关。技能栈因此需要重构：原来核心能力是 SQL 与建模编码，现在需要补齐的是语义资产设计能力（定义指标的 DWD 表达式、上游依赖、取值范围——从「人可用」到「AI 可食」的资产格式转换）、知识库运营能力（anti-patterns 沉淀、指标命名规范治理）和 AI 行为调优能力（读日志、识别幻觉、通过反馈驱动经验升级）。文章中 7 Agent 工作流的「老架」这类编排角色，某种程度上就是 Designer 岗位的具象化——数研同学从流水线上的工人变成流水线的设计者。这与 [[entities/alibaba-data-rd-harness-engineering-nl2sql|阿里数据研发 Harness 工程]] 实践中的角色演进趋势一致。

### 在 Harness Engineering 框架中的定位

文章虽以数据研发为场景，但其方案几乎是 [[concepts/harness-engineering-framework|Harness Engineering 框架]] 全要素的一个领域实例：分离关注点对应决策与执行、知识检索与代码生成的拆分；施加约束对应 Gate 机制、规范校验与强制审批；管理上下文对应按需开放技能、控制各 Agent 信息输入；管理熵值对应防止长程任务中的行为漂移。空间隔离（独立 Workspace、`{domain}_{date}_{seq}` 命名规范、MCP/Skill 加载路径优先级）和配置治理（Git 备份、agents.md 同步、模板化恢复）则覆盖了工程化落地的运维面。文章最独特的问题意识在于点明 AI 与传统 CI/CD Pipeline 的本质区别：传统 Pipeline 每步是确定性的，而 AI Agent 每步都可能产生意料之外的输出——这解释了为什么技能幻觉检测 Hook 要对比「声称结果」与「实际系统状态」，也把 [[concepts/context-engineering|上下文工程]] 与稳定性工程统一到了同一套管控框架之下。

## 实践启示

1. **先建知识层，再上管控层。** 没有结构化的语义资产和指标定义，任何 Gate 与检测机制都无从验证「做的是对的事」；启动类似项目时，把语义资产治理（标准名称+别名映射+语义边界）排在 Multi-Agent 编排之前。
2. **把人工修正设计为可捕获的反馈流。** 每次数研同学纠正 Agent 行为时，强制要求变更写回知识库与规则配置，而不是口头沟通后即弃——这是「经验升级」闭环能否成立的分水岭。
3. **用「AI 可食」标准重定义数据资产。** 资产不只给人看懂，还必须定义 DWD 表达式、上游依赖、取值范围等机器可校验字段；传统「人可用」格式的资产在接入 AI 前需要系统性改造。
4. **幻觉防控靠产物校验而非文本确认。** 关键操作必须产出可验证产物（文件、数据、状态变更），Agent 的文本回复一律不作为完成依据；配幻觉检测 Hook 对比声称结果与实际系统状态，并坚持日志必看原则。
5. **人工 Gate 是数据场景的必选项。** 在准确性要求极高的数据研发中，「AI 做执行，人做决策」不是过渡方案而是终局设计——关键决策点（SPEC 审核、技术方案、SQL 质量回滚决策）始终保留人工审批。
6. **平台化复用从第一天就预留接缝。** 语义层分层设计（业务规则库、元数据知识库、SQL 规范库）保持架构稳定、只替换业务域知识，其他团队接入时复用整套工作流与管控框架——这正是兄弟团队 60% 能力复用策略的反向输出。
