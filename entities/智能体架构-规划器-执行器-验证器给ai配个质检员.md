你有没有遇到过这种场景：你写了一个自动化脚本，去调用某个第三方API，结果API突然挂掉，返回了一堆乱码。你的脚本呢？它像个老实人一样，把这堆乱码原封不动地塞进下一步计算，最后给你一个莫名其妙的答案。 ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md]

这其实就是很多AI智能体的通病： 它们太“天真”了，只会按计划执行，却不会“质疑”结果的正确性。 上篇文章我们聊了规划架构，让AI学会了“先想后做”。但如果它规划好了，执行时却遭遇了“不可抗力”——比如API宕机、数据为空、格式错误——它照样会傻乎乎地往下走，最终产出一堆垃圾。 ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md]

怎么办？答案是：给AI配个“质检员”。

今天，我们要深入探讨 规划器 → 执行器 → 验证器（PEV） 架构。它在前面的规划-执行模式上，增加了一个关键角色： 验证器 。这个角色就像一个严格的测试工程师，每执行一步，都会检查结果是否正确。如果发现错误，它会立刻叫停，并触发“重新规划”流程，直到问题解决为止。 ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md]

我们将从零开始，先构建一个“傻白甜”的规划-执行智能体，看着它如何在错误面前“装死”。然后，我们再为它配上“质检员”，看看它如何起死回生，优雅地完成任务。 ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md]

## 为什么要给AI配个“质检员”？

在深入代码之前，我们先来拆解一下PEV架构的核心思想。它的灵感其实来自于我们软件工程里最朴素的道理： 写完代码要测试，测试通过才能上线 。 ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md]

### 什么是PEV架构？

你可以把它想象成一个严格的餐厅后厨：

   ：主厨接到订单后，制定出做菜的步骤：“先去冷库拿牛肉，再去备菜区拿土豆，然后开始烹饪。” ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md]

- 执行器（Execution）
   ：切配师傅拿着清单去执行，比如去冷库拿牛肉。^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md]

验证器（Verification）
   ：
   质检员
   接过牛肉，仔细检查：“这肉是牛肉吗？新鲜吗？符合标准吗？” ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md]

## 深度分析

1. **验证的本质是把“错误传播”截断在每一步**。规划-执行架构的致命弱点不在于规划错了，而在于错误会静默传播：执行器拿到 API 返回的乱码或错误消息后原样塞进下一步计算，最终合成一个“看似合理实则荒谬”的答案。PEV 在每一步执行后插入验证关卡，等于给数据流加装了断路器——错误一旦出现就立刻被路由器捕获，而不是等到最终答案才暴露 ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md:56-62]。这和软件工程里“写完代码要测试，测试通过才能上线”的朴素道理同构，只是把测试从交付前的单点检查变成了流水线上的逐点检查 ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md:50-54]。

2. **重新规划的信息增益是 PEV 真正的智能来源**。验证失败并不只是“叫停”，路由器会把失败信息踢回规划器，规划器带着上一次的失败上下文重新制定计划——实战中它自动改用了不同的搜索词（"苹果公司全球员工人数 2023"）来规避 API 故障。这说明 PEV 的自我修正能力来自一个闭环：验证器提供“哪里错了”的信号，规划器负责“怎么绕开”，二者缺一不可。没有验证器的规划器是在盲飞，没有重新规划的验证器只是报警器 ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md:419-453]。

3. **验证器是一个“分级判断”问题，而非简单的成败二值**。原文明确指出设计难点在于让验证器区分“小问题”和“关键故障”——把无效数据一律判失败会导致过度重规划，把关键故障判通过则失去意义。实战实现用了结构化输出（is_successful + reasoning 的 Pydantic 模型）来强制 LLM 给出可审计的判断理由，这个 reasoning 字段既是调试的抓手，也是重新规划时规划器能“知道上次为何失败”的信息通道 ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md:139-146,289-296]。

4. **PEV 的代价结构决定了它的适用边界**。每一次工具调用后都要多一次 LLM 验证调用，使 PEV 成为文中所有架构里速度最慢、成本最高的模式。但它的收益是“免疫系统”式的：系统从错误中恢复而非崩溃。因此正确的选型逻辑是按错误代价而非按架构优雅程度来选——金融、医疗等错误代价巨大的场景，和高精度要求的法律、科研任务，多花的延迟和 token 是便宜的风险对冲；而错误可以容忍、可批量重跑的场景则不必上 PEV ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md:117-137]。

5. **鲁棒性可以被量化评估，且应纳入智能体评测维度**。文中用“LLM 作为评委”给两个智能体分别打 task_completion_score 和 error_handling_score：基线 P-E 智能体的错误处理分极低（完全没识别出错误），PEV 接近满分。这个方法论值得推广——评估智能体不能只看“一切顺利时的表现”，还要专门构造故障注入（如故意设计 flaky tool）来测量恢复能力 ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md:456-502]。

## 实践启示

1. **为不稳定的工具调用加验证关卡**：只要智能体依赖外部 API（搜索、数据库、第三方服务），就在每步执行后加一个验证器节点，用结构化输出（如 `is_successful: bool` + `reasoning: str`）判断结果是有效数据还是错误消息，禁止把错误消息当数据继续合成 ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md:289-296]。

2. **验证失败要回传给规划器，而不是终止流程**：把失败原因写进状态，触发重新规划，让规划器基于失败上下文换思路（换关键词、换数据源、换工具）。只报警不重规划的架构只完成了一半 ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md:419-441]。

3. **用故障注入测试智能体**：仿照文中 flaky_web_search 的做法，故意让某个工具对特定查询返回错误，对比有无验证器时的最终答案质量和 error_handling_score，量化验证你的智能体到底“抗不抗造” ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md:193-215,456-482]。

4. **按错误代价决定是否上 PEV**：金融、医疗、法律、科研等安全关键或高精度场景优先采用；而延迟敏感、可容忍偶发失败的轻量任务，用普通规划-执行即可，避免为用不到的鲁棒性支付双倍 LLM 调用成本 ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md:117-146]。

5. **给验证器设计“分级”而非二值的判断标准**：在验证器 prompt 中明确区分可重试故障（API 限流、超时）、需换路故障（数据不存在）和不可恢复故障，并设置重试上限（如状态中的 retries 计数），防止验证-重规划循环无限打转烧钱 ^[raw/articles/智能体架构-规划器-执行器-验证器给ai配个质检员.md:139-146,298-302]。
