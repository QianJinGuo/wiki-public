# 模型好不好用，谁说了算？从榜单崇拜到自建评测

阿里云开发者社区文章（作者李俊霖/鲸羚）从 Humanity's Last Exam（HLE）的命运切入，系统梳理了四代模型评测方法论的兴衰，并用古德哈特定律（Goodhart's Law）解释为什么所有公开评测最终都会失真：HLE 发布时最强模型正确率不到 10%，但仅一年半后公开榜单口径下榜首已涨到 50% 以上——"这不是 HLE 的失败，而是所有评测的命运"。文章的核心主张是：公开榜单只能给出行业坐标，无法保证模型在你的业务场景上好用，最务实的做法是用自己真实遇到的难题构建测试集来评测模型，这套数据同时还能作为 few-shot 增强模型能力（一鱼两吃）。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md]

## 四代模型评测的命运

第一代是固定考卷（2020 年 GPT-3 之后）：MMLU、GSM8K、HumanEval 等，两个致命问题是背题（公开题目可能进入训练数据，分数测到的是记忆力）和满分（难度固定而模型能力上涨，考卷失去区分度）。第二代是真人盲测（2023 年 UC Berkeley LMSYS 的 Chatbot Arena/LMArena）：用户实时出题、匿名双模型投票、Elo 排名，模型无法背题且能直接知道用户偏好，但一些模型针对人类评估者偏好做了优化（多用列表、控制长度、加表情符号），这些技巧不影响实际能力却能让评估者更倾向投票。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md]

第三代是真实任务（2023 年 10 月普林斯顿 SWE-bench）：从 GitHub 拿真实 issue，模型要读懂代码库、定位问题、写补丁、跑项目测试；判分用 FAIL_TO_PASS（修掉 bug）与 PASS_TO_PASS（不把别的功能改坏）两类测试，但测的是 GitHub 开源项目的 issue，"它测的是真实任务，但不一定是你的真实任务"。第四代是 Agent 全链路（2025 年起）：OpenAI 的 BrowseComp（1,266 道"难找但容易验证"的网页检索题，模型必须自己规划搜索词、打开网页、交叉验证）与 Terminal-Bench（真实终端、Docker 沙箱、指令-环境-参考解法-测试脚本），代价是"贵"——一次完整链路评测的成本是固定考卷的几十倍，成本高导致样本量小、结果不稳定，且工具版本、网页状态、终端环境一变结果就可能不一样。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md]

## 古德哈特定律：指标失真的机制

1975 年英国经济学家 Charles Goodhart 论货币政策时写道："任何稳定的统计规律，一旦被拿来当控制目标，就会开始崩塌。"人类学家 Marilyn Strathern 改写成更流行的版本："当一项指标成为目标时，它就不再是一项好的指标了。"四代评测看似各不相同（选择题、盲测、真实任务、Agent 工作流），背后都是古德哈特定律的不同显影：评测分数只是模型"好不好用"的替身，近似指标用久了就会失真。这为 LLM 评测基准全景 中"基准饱和与评测军备竞赛"的现象提供了统一解释框架。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md]

## 怎么规避古德哈特定律：自建评测

规避最直接的办法不是再找一张更难的卷子，而是用自己真实题目来评测模型：公开榜单给行业坐标，自己的测试集才能告诉你模型能不能进流程。作者实践了具体的收集方法：有意识收集自己遇到的、模型难以解决的问题作为测试集，用 AI 写了一个 Chrome 插件，在表格输入后自动把数据同步成 jsonl（每行 {"prompt": 输入, "completion": 期望输出}），这套数据可直接交给大部分市面上的模型平台做评测，也能换个格式当 few-shot 使用。文章还与 [[concepts/agent-evaluation-benchmark-frameworks|智能体评测框架]] 的趋势呼应：评测正从"模型怎么回答"走向"系统能不能办事"，而自建评测集是应对 代码生成评测 这类高成本评测不可复现问题的务实解。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md]

总结而言：AI 模型公开榜单只能给出行业坐标，无法保证模型在具体业务场景上的效率；最务实的做法是用自己真实遇到的难题构建测试集评测模型，这套数据同时还能作为 few-shot 增强模型能力。HLE 的组织者之一 Dan Hendrycks 正是五年前 MMLU 论文的第一作者——"同一个人，出的第一张卷子已经被遗弃，于是他出了第二张更难的试卷，然而在可以预见的未来，第二张试卷也会被淘汰"，这个循环是评测方法论演进的真实写照。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md]

## 深度分析

### 四代评测的演化方向：从"考卷"走向"现场"

把四代评测放在一起看，演化方向其实非常清晰：每一代都在试图离"真实使用场景"更近一步。固定考卷问的是"模型记住了什么"，真人盲测问的是"人更喜欢谁"，SWE-bench 问的是"模型能不能在真实代码库里修好一个 bug"，到 Agent 全链路则变成"系统能不能从头到尾把事办成"。但每往前走一步，评测的执行成本和复现难度也随之上升——BrowseComp 要求模型自己规划搜索词、打开网页、交叉验证线索，Terminal-Bench 则要在 Docker 沙箱里真实执行命令，这类评测一次完整链路的成本是固定考卷的几十倍。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md:138-148] 真实性与可评测性之间存在结构性张力：越真实的评测越贵、越难复现，越便宜的评测越早失真——这是评测本身的困境，不是设计缺陷。

### 古德哈特定律不是bug，而是评测的宿命

HLE 的故事最能说明问题：发布时最强模型正确率不到 10%，被认为足够撑很多年，但仅一年半后公开榜单口径下榜首已涨到 50% 以上。更讽刺的是，HLE 的核心组织者 Dan Hendrycks 正是五年前 MMLU 论文的第一作者——他出的第一张卷子已被遗弃，而他亲手出的第二张更难的卷子，在可预见的未来同样会被淘汰。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md:34-42] 文章由此得出的判断相当冷峻：这不是 HLE 设计失误，而是所有公开评测的共同命运。机制上，"好不好用"本就难以直接测量，行业只能用可观测的近似指标替代；而任何近似指标一旦成为优化目标，被测者就会围着指标行动（比如针对 Arena 评估者的偏好多用列表、控制长度、加表情符号），指标与真实能力之间的相关性随之衰减。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md:44-50]

### 换更难的卷子是在同一条死路上加速

面对基准饱和，行业的第一反应通常是"出一张更难的卷子"，HLE 正是这一思路的产物。但文章指出了固定考卷的两个结构性死穴：其一是背题——题目公开后可能进入训练数据，高分测到的可能是记忆力而非解题能力；其二是满分——题目难度固定而模型能力持续上涨，最终所有人都接近满分，考卷失去区分度。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md:74-89] 换更难的考卷只是把失真的时间点往后推，并没有改变"指标成为目标后必然崩塌"的机制。这个观察对实践者的含义是：不要指望任何公开基准能长期可靠地回答"这个模型好不好"，榜单分数的保质期应当被主动假设为有限。

### 公开榜单给坐标，自建测试集才能给决策

文章给出的出路不是寻找更好的公开基准，而是换一个问题框架：公开榜单只能告诉你模型大概在行业里什么位置，却无法保证它处理你的任务效率更高——"它测的是真实任务，但不一定是你的真实任务"。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md:152-160] 这个区分很关键：榜单回答的是"谁更强"（相对排序），业务决策需要的是"它对我够不够用"（绝对门槛）。因此自建评测不是补充动作，而是把评测对象从"模型的一般能力"切换到"我的任务分布"——只有用自己真实遇到的难题构建测试集，结果才直接对应"能不能进流程"这个决策。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md:194-196]

### 评测数据的复用价值：一鱼两吃

自建测试集还有一个容易被忽略的副产物：收集成本其实是投资而非开销。数据集里的每条 {prompt, completion} 记录，本身就是你对模型输出的期望示例——出新模型时拿来当测试集，日常工作中换个格式就能直接当 few-shot 示例增强模型能力，一份收集两处受益。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md:184-190] 作者自己用 AI 写了一个 Chrome 插件来降低收集摩擦：在表格里输入，数据自动同步成 jsonl 格式，可直接交给市面上大部分模型平台做评测。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md:166-182] 关键在于：收集动作嵌入日常工作流的摩擦越低，测试集越能随真实问题自然生长。

## 实践启示

1. **把公开榜单当地图，不当判官。** 榜单分数只能用于快速圈定候选模型的大致梯队（行业坐标），任何"选型决策"都必须以自有测试集的结果为准，榜单排名与业务表现之间不存在可依赖的传递关系。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md:152-160]

2. **从今天开始积累"模型做不好"的案例库。** 每当遇到模型解决不好的真实问题，有意识地记录下来（输入 + 期望输出），日积月累就是最贴合自己业务的测试集——它比任何公开基准都更能回答"这个模型能不能进我的流程"。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md:162-166]

3. **把收集摩擦降到接近零。** 仿照作者的做法，用工具把收集动作嵌入日常输入流程（例如表格输入自动落成 jsonl），保证测试集随真实问题持续生长，而不是靠一次性突击整理。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md:166-182]

4. **一份评测数据按两种用途设计格式。** 按 {prompt, completion} 结构存储评测案例，使其既能直接交付模型平台做评测，又能一键转换为 few-shot 示例注入日常 prompt，最大化单次收集的回报。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md:184-190]

5. **给任何基准分数设定"保质期"预期。** 记住 HLE 的教训：再难的公开基准也会在一年半左右的周期内被针对性优化侵蚀，引用任何榜单数据时都应确认其时效，超过一个模型迭代周期的分数基本不再可信。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md:34-42]

6. **评估 Agent 类模型时预留成本与方差余量。** 全链路评测的成本是固定考卷的几十倍、且环境一变结果就可能不同，因此小样本 Agent 评测的排名波动可能只是统计涨落——重要选型应增加样本量或多次复测，而非相信单次榜单。^[raw/articles/模型好不好用谁说了算从榜单崇拜到自建评测.md:144-148]
