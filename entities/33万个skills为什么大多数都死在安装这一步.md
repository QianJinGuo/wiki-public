## 深度分析

### 下载不等于安装：57.5% 零安装与 Top100 占 50.4% 的头部集中

把 23,269,103 次总下载摊到 33,760 个 skill 上，表面看是一片繁荣；但拆到中位数层面，下载中位数 198、安装中位数 0、点赞中位数 0——绝大多数 skill 只是「被路过了」，从未「被留下」。57.5% 的 skill 零安装、75.2% 的 skill 零点赞，说明曝光环节与采用环节是两个几乎断开的漏斗。同时 Top100 skill 吃掉了 50.4% 的安装量，形成典型的头部集中结构：流量并没有平均分配给供给，而是向极少数能穿過安装这道门的头部收敛。供给过剩 + 头部虹吸，意味着后来者靠「多上架一个泛功能」几乎不可能获得采用。

### 安装效率（每千下载安装数）比热度更有解释力

按类别看强弱，不能只看供给规模或下载量，更有解释力的指标是每千次下载对应多少安装。开发/编程以约 9.99% 的安装效率居首——它不是「供给多所以卷死了」，而是「供给大、安装也强」的主航道；自动化/工作流、办公/文档、搜索/研究、图像/音视频构成 6.5%–8% 的稳定装机层。反观电商/营销（3.80%）、本地生活（3.01%）、教育/学习（2.69%），下载不少但承接极弱。这个指标把「看起来热闹」和「真正被用起来」区分开了：热度是流量侧的故事，安装效率才是产品侧的成绩单。

### 头部公式：零配置门槛 + 一句话讲清 + 高频 + 接现有生态

看 Top skill（如 Summarize、Github、AgentBrowser、Weather 等），它们跨赛道但共性高度一致：零配置门槛（不需要 API Key、不填参数、无前置设置）、一句话讲清用途（不读文档也能懂）、解决高频问题（反复依赖而非偶尔一用）、接入用户已有的生态（GitHub、浏览器、文档）。这四条共同把「判断成本」压到最低——用户当下做的不是深度比较，而是快速决定值不值得装、装完能不能立刻用。头部 skill 的真正共性不是功能最多，而是让用户最不需要思考。

### 配置成本的结构性差异：无需 API Key 平均 11.4 安装 vs 需要 3.5

文中一组对比最具杀伤力：无需 API Key 的 skill 平均安装数约 11.4，需要 API Key 的只有约 3.5，相差三倍以上。这不是小波动，而是结构性差异——用户面对一个 skill 时，真正的决策不是「这东西厉不厉害」，而是「能不能立刻装、要不要先去找 key、配账号、填参数」。配置成本本身就是转化门槛，而且是在用户还没体验到任何价值之前就征收的「预付成本」。对无依赖、零配置设计的强调（参见 [[concepts/skill-engineering-principles|Skill Engineering 原则]] 与 [[entities/agent-skills-no-dependency-design-philosophy|Agent Skills 无依赖设计]]）在这组数据里得到了量化验证。

### 形态结论：越像一个明确动作，越不像一个小型操作系统

高转化黑马（Canvas 32.2% 转化、Ordercli/Blucli/Eightctl 12%–13%、FoodOrder 12.3%）的共同点不是大而全，而是场景窄、动作具体、无需学习、价值立即可感知。相反，「多功能大而全」的 skill 像一个小型操作系统，用户不知道从哪开始用，反而在安装前就放弃了。这与第四节的四个成立特征一致：输入明确、输出明确、结果可验证、离现有流程近。由此得到一个反直觉的形态结论——skill 不是越像操作系统越容易成功，而是越像一个明确的动作越容易被安装；谁更接近流程入口，谁更容易获得采用。

## 实践启示

1. **用安装效率（每千下载安装数）评估赛道，而不是下载量或供给数。** 选方向时先看该类别的承接能力：开发/编程与自动化/工作流是主航道，电商/营销、教育/学习供给饱和且承接弱，进入前先回答「用户为什么把它装成默认入口」。

2. **把「零配置」当作发布门槛，而不是优化项。** 无需 API Key 与需要 API Key 的平均安装数相差三倍以上；能内置默认值、免密钥、开箱即用的部分，全部前置。任何要求用户先去申请 key、填参数的设计，都是在转化漏斗最顶端加一道闸门。

3. **一句话测试：如果简介需要读文档才能懂，就还没做好。** 头部 skill 的共性是判断成本最低——输入明确、输出明确、结果可验证。写简介时先自问：用户不读任何文档，能否在一句话内知道给什么、得到什么、对不对。

4. **做窄而具体的动作，不做小操作系统。** 高转化黑马证明了「场景窄 + 动作具体 + 价值立即可感知」胜过「多功能大而全」。第一版只解决一个高频动作，接入用户已有的 GitHub、浏览器、文档生态，而不是要求用户学新范式。

5. **离现有流程越近越好：缩短原有流程，而不是重新发明流程。** 代码、搜索、文档、转写、导出、同步这类方向跑得出来，是因为用户把一个旧动作更快做完了。产品定位时优先找现有任务链里的摩擦点，而不是创造新概念。

6. **警惕「价值到达太晚」的赛道形态。** 电商/营销与金融/分析的问题不是价值不存在，而是结果验证周期长、切口不够锋利——用户会下载、会看看，但不装成默认入口。若必须做这类方向，应先把验证周期切短，让第一次调用就能感知价值。
