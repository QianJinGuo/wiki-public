当他们面向"信徒"推销 Agentic Coding 时，就会拿这个误解当卖点。这些信徒把 Agentic Coding 当作新一代的外包，他们幻想着工程师只需要当管理者，写好 Spec 文档，然后扔给一群 Agent 去干活。但这套逻辑能成立，前提是"描述工作"比"亲自做工作"更便宜，而事实并非如此。 ^[raw/articles/别再幻想用-spec-替代写代码.md]

当他们面向"怀疑者"推销 Agentic Coding 时，就会拿这个误解当挡箭牌。怀疑者担心 Agentic Coding 会产出无法维护的垃圾代码，而他们的反驳是：先写 Spec 再生成代码，这个过程会倒逼质量提升，促进更好的工程实践。 ^[raw/articles/别再幻想用-spec-替代写代码.md]

## 深度分析

### 为什么自然语言规格消除不了歧义

规格写成散文之所以注定失败，根源不在"写得还不够细"，而在于描述精度与可执行约束之间存在无法消除的落差。Dijkstra 的窄接口论证给出了结构性解释：沿某条接口切开一项工作并不能把它变成两半——跨接口的协作本身要额外付出工作量，且接口一变，两侧成本会一起上涨，这正是工程上偏好窄接口的原因。自然语言是极宽的接口：它把压力转嫁给机器，却并不因此减轻人的负担。数学史是同一结论的旁证：从口头描述与图形演示，到浅尝符号化又退回修辞风格，直到 Vieta、Descartes、Leibniz、Boole 建立形式符号系统，推理才变得可累积、可检查。

Symphony 的 SPEC.md 演示了这个收敛过程：逐条罗列字段并标注类型与可空性，把并发额度写成 `available_slots = max(max_concurrent_agents - running_count, 0)`，把重试退避写成 `min(10000 × 2^(attempt-1), agent.max_retry_backoff_ms)`，甚至直接给出语言无关的 `start_service()` 参考实现。当"精确到足以可靠生成实现"成为硬要求时，文档会自发向代码收敛——它没有绕开编程，只是换了层皮。^[raw/articles/别再幻想用-spec-替代写代码.md]

### 形式化规格 vs 散文规格：验证成本只是被转移

YAML 是更有说服力的对照样本：规范极其详尽、被广泛采用，还配有一致性测试套件，可绝大多数实现仍无法完全符合。这说明"符合规格"本身有成本，且一致性套件只覆盖被认为可测的那部分——剩下的是读者理解、生成者推断与评审者经验。形式化路线（类型系统、契约测试、可执行/可判定规格）能把验证成本从"人读"搬到"机器跑"，代价是规格必须被表达成具备机械语义的形式；散文规格则把成本摊回到人身上，而这类成本在组织里通常不可见、不计入交付周期，于是被系统性低估。

判断一份规格是否已经越界，有个简单的规模信号：Symphony 的规格长度达到配套 Elixir 实现代码量的六分之一。继续朝这个方向膨胀，就会重演 Borges 笔下那张与帝国等大的地图——精确到每一个点，却既搬不动也无人使用。

### "Spec 通过 ≠ 代码正确"：实测暴露的验证缺口

作者按 README 让 Claude Code 用 Haskell 重新实现 Symphony，问题分两层暴露：一是若干真实 bug，需反复追加提示才修掉；二是更隐蔽的情形——编译与运行都不报错，codex agent 却在空转，对一个极简的 Linear 工单毫无推进。这正是验证缺口的典型形态：语法通过与无异常运行都不等于目标语义达成，规格的完整度也替代不了端到端行为判据。缺的是独立于生成者、能对"业务目标是否达成"下判决的验证环。

作者拒绝"换门更主流的语言会更好"的宽慰也值得记录：若 agent 只在自己训练分布内的高频语言上可靠，恰恰说明它无法可靠泛化——而"从规格生成正确实现"这一承诺正建立在泛化能力之上。同一逻辑也界定了[[entities/openai-symphony-codex-orchestration-linear-control-plane|Symphony 这套 Linear 控制平面]]的工程语义：编排器的价值来自运行时状态与工单闭环，而非文档措辞。

### 规格漂移与代码漂移的对称性

SDD 的常规叙事假设规格是稳定的上游、代码是易腐的下游，"先写规格"因此天然带来秩序。Symphony 给出了相反的画面：为了让规格精确到能产出可用实现，它必须在配置字段、重试语义、并发限制这些细节上与实现同步演化，于是获得了与代码相同的腐化速率——规格漂移(spec drift)与代码漂移是对称的，换载体不会让它消失。

对称性带来一个必须显式回答的问题：谁是真源？规格为源，就要检测代码偏离并回正；代码为源，就要反向重生成规格；两侧都可改，就必须有裁决规则加一份契约测试来锁定语义。缺少同步机制时两侧会同时漂移，而且比单一代码库更难察觉——没人把规格当运行物来校验。相关讨论可对照[[entities/openspec-四步法深度复盘-流程完整不等于代码正确|OpenSpec 四步法复盘：流程完整 ≠ 代码正确]]与[[entities/from-spec-driven-to-environment-verification-driven-ai-coding-wu-zuoyan-2026|从 Spec 驱动转向环境与验证驱动]]：流程跑通与代码正确是两件事，判据最终落在环境与验证上。

### 定位之争：spec 是 harness 的约束件，不是代码的替代品

必须区分两类主张。作为生成过程的约束件，Symphony 那份文档是有效的：固定接口、固定状态字段、固定失败语义，让 agent 少猜——这正是 [[concepts/harness-engineering-framework|Harness Engineering]] 中"把隐性约束显式化"的做法。但把它包装成"代码的替代品"来销售，就会诱发两种典型失败：其一，把规格当成更便宜的工作，交付压力下没人肯做深思考，产出的是"看起来像规格"的句子堆砌——那段 linear_graphql 契约就是标本，条目齐全却无连贯性与目的感；其二，跳过验收闭环，把"文档齐备"误当作"实现正确"。

由此可划出适用边界。收益最大的场景：接口稳定、需求可枚举、变更频率低、且已有自动验证环的系统——数据管道 schema、协议实现、CLI 契约、大规模迁移脚本。收益为负的场景：探索性产品逻辑、隐性知识密集、需求每天都在变的早期阶段；此时 spec-first 要先付写规格的成本，再付双向同步的成本，吞吐必然下降。作者的结论很直接：规格从来不是为了省时间而存在的，若目标只是缩短交付周期，直接写代码再补文档通常更快。这与[[entities/spec-driven-development-cognitive-framework|Spec-Driven AI 编程半年实战]]的判断一致——有损管道与"Control 过多"才是真正的陷阱。

## 实践启示

1. **先明确规格要买什么，别买"省时间"。** 规格能买到约束、共识与可验证边界，买不到被跳过的思考。若目标是缩短交付周期，直接写代码再回溯文档往往更快；把规格当作"外挂的思考替代品"，只会得到 AI 味的伪规格。
2. **不要让生成者批改自己的卷子。** 验收必须由独立判据完成：端到端行为测试、真实工单能否被推进、关键路径的失败语义是否符合预期。"编译通过 / 无异常 / 文档齐备"都不是正确性证据，还需专门覆盖"表面成功但空转"这一档失效。
3. **把规格收窄到可接受实现空间。** 只写接口、状态字段、不变量、失败与重试语义、边界条件，不要抄写实现步骤。规格一旦开始复述控制流，它就已经是代码，而且是一份无法被编译器与测试直接校验的代码。
4. **可机械检查的部分一律形式化。** schema、类型、契约测试、一致性用例能承担的就别留给散文；散文只保留判断、权衡与取舍。验证成本要么被机器吃掉，要么被人情价低估，后者会在半年后以返工的形式收账。
5. **主动检测规格与代码的双向漂移。** 每次改动代码或规格时同步另一侧，把差异当 bug 而非文档债；明确谁是真源、冲突由什么规则裁决。缺少这条机制时，两侧会同时腐化且无人察觉。
6. **对 AI 生成的规格施加与代码同等的审查强度。** 深思熟虑不是默认前提：当组织奖励交付速度而非清晰度时，产出的规格天然是"看起来像规格"的句子堆砌。对规格做和代码一样的 review、同样的准入标准，是这条链条上最便宜的一道闸门。
