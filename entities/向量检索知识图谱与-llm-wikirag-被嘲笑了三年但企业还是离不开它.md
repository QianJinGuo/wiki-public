# 向量检索、知识图谱与 LLM Wiki：RAG 被嘲笑了三年，但企业还是离不开它

RAG在网上已经死过很多遍了，谁用谁Low，但是实际上很多的企业知识库仍然在使用，并且依然是主流选择方案。 ^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]

但是，这些论调会把很多人带偏，尤其是对知识库和RAG没有体系化认知的同学。^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]


这里我们首先要理解一个问题：在AI时代，知识库为啥变得如此被需要？^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]


大模型在回答问题时，它只知道公域知识，并不知道我们私域的知识，在这种情况下它就容易出现幻觉，胡乱编造一些看似正确的答案给我们。 ^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]

为了缓解这个问题，我们可以给大模型外挂一个知识库，让大模型在回答问题时能够参考可信的知识来源。^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]


但新的问题又出现了。

企业知识库中的内容往往很庞大，而大模型的上下文窗口是有限制的，就不可能把所有的知识一次性全部提供给模型。 ^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]

因此，在回答问题之前，需要先从海量知识中找到与当前问题最相关的信息，再把这些信息作为上下文给到大模型参考回答。 ^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]

这种解决方案，我们称之为RAG，即知识检索增强生成  ** 。  **^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]


如果给它下一个定义的话：  ** RAG 是一种通过动态检索外部知识，并将检索结果作为上下文提供给大模型，从而提升回答准确性、时效性和可解释性的系统架构范式。  ** ^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]

在理解了这些知识后，我们在看前面的问题，RAG真的会死掉吗？^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]


答案肯定是不会的，因为 RAG 并不是某一种具体的技术，而是一种检索 + 生成的架构范式。只要大模型无法穷尽所有私有知识、实时信息和动态变化的数据，检索的价值就不会消失： ^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]

只不过，这几年年RAG 内部采用的技术在不断的演进。^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]


从最早的关键词检索，到向量检索；从单路召回，到混合检索；从传统 RAG，到 Graph RAG、Agentic RAG，本质上都是在不断提升信息获取和知识利用的效率。 ^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]

接下来，我们就展开讨论下RAG体系下有哪些检索技术：^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]


##  全文检索

全文检索在RAG检索策略中非常常用，可以说是元老级别的存在，其实现以Elasticsearch为代表，在企业内部文档搜索、电商商品搜索、法律案例检索、专利查重等场景的背后都有它们的身影： ^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]

它的大致原理是，对用户输入的问题进行分词，然后通过倒排索引找到包含这些关键词的文档，在根据BM25算法计算出每个文档的相关性得分，然后返回排序后的结果。 ^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]

## 深度分析

### RAG 是架构范式，而不是某一项具体技术

文章最核心的论点是：RAG 不会死，因为它不是一种可被"淘汰"的具体技术，而是"检索 + 生成"的架构范式。只要大模型无法穷尽私有知识、实时信息和动态变化的数据，检索环节的价值就不会消失^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]。所谓"RAG 已死"的舆论，唱衰的其实是某一代具体实现（如朴素向量召回），而非范式本身——过去几年从关键词检索到向量检索、从单路召回再到混合检索与 Agentic RAG，变的都是范式内部的实现层^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]。这也解释了为何唱衰声持续三年，企业知识库却依然把 RAG 当主流方案。参见 [[entities/rag-vs-llm-wiki-enterprise-knowledge-base]] 的路线比较。

### 三种检索技术能力边界互补，而非互相替代

文章用同一组"差旅报销/离职流程"文档讲清了边界：全文检索靠分词、倒排索引加 BM25 打分，解决"关键词是否匹配"，在条款编号、产品型号等精确查找场景又快又准，但召回不了"员工解除劳动合同办理规范"这种语义相近、关键词不同的文档^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]。向量检索恰好相反：用 Embedding 把文本映射到语义空间，以余弦相似度等度量召回语义相近片段，容忍同义改写与口语化提问，却在精确匹配编号和专有名词上不可靠^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]。由于用户问题往往同时包含语义意图与关键词/业务术语，混合检索不是锦上添花，而是必然组合^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]。

### 向量检索"不招人待见却不得不用"的根源在工程细节

文章点出一个常被忽略的事实：向量检索的效果高度依赖一系列没有最优解的工程决策——chunk 切得太短则语义不完整，切得太长又引入无关内容稀释向量表达；Embedding 模型质量、片段上下文完整性、召回数量设置同样显著影响效果^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]。固定长度 + overlap、正则表达式、父子分段、大模型语义分段等策略并存且各有取舍，正是它"广受诟病又不得不用"的原因^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]。其短板不在原理，而是把大量调优负担转移给了使用者的工程侧。

### 知识图谱补上多跳推理，LLM Wiki 重新思考知识组织

当问题从单点匹配升级为"关系 + 多跳推理"（如"诺兰导演过哪些由莱昂纳多主演的电影"），检索召回的文本片段无法串联实体关系，此时需要知识图谱：以"实体 + 关系"三元组编织结构化网络，查询时把自然语言转成 Cypher 等图查询，取关系路径交集得答案^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]。但图数据库只负责存储与查询关系，推理仍需额外领域规则建模，且实体识别、关系抽取、本体设计、实体消歧的构建与维护成本都很高^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]。另一端，Karpathy 的 LLM Wiki（参见 [[concepts/karpathy-llm-wiki-v2]]）换了条路：人供原料、模型自动维护结构化 Wiki，查询时先读 Index.md 索引再渐进展开页面——与 Skills 的渐进式披露机制一致^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]。但 Index.md 会随知识库膨胀直至超出上下文限制，届时仍需关键词/向量检索兜底，且该方案目前仅适合个人知识库、企业场景尚不完善^[raw/articles/向量检索知识图谱与-llm-wikirag-被嘲笑了三年但企业还是离不开它.md]。多跳场景还可参考 [[entities/graphrag-needed-aws-9-rag-comparison-2026]] 与 [[concepts/wikilink-knowledge-graph]]。

## 实践启示

1. **按查询类型选检索通道，而非押注单一技术。** 精确查找（编号、型号、专有名词）交给全文检索/BM25；同义改写、口语化提问交给向量检索；多实体多跳问题才引入知识图谱或 Graph RAG。混合检索应作为企业知识库的默认起点。
2. **把 chunk 策略当作首要调优对象。** 切分粒度直接决定向量表达质量：过短丢语义、过长混噪声。建议从固定长度 + overlap 起步，再用父子分段或语义分段针对高价值文档迭代，并用真实查询集持续评估——分块没有最优解，只有场景适配。
3. **对"RAG 已死"类论调保持体系化判断。** 区分范式与实现层：某一代向量召回效果差，不代表要抛弃 RAG，而可能意味着应升级到混合检索或 Agentic RAG，避免被舆论带偏而推翻仍在创造价值的基础设施。
4. **引入知识图谱前先核算构建与维护成本。** 实体识别、关系抽取、本体设计、实体消歧与后续规则更新都是持续投入，只有"关系明确、结构稳定、确需多跳推理"的场景才值得上图谱；且图数据库本身不做推理，推理逻辑需另行建模。
5. **LLM Wiki 先在个人知识库试点，企业场景保持观望。** "人供原料、模型维护 Wiki + Index.md 索引渐进展开"轻量易上手，但需预留索引膨胀问题：知识量增长后 Index.md 会逼近上下文上限，届时仍需关键词/向量检索兜底。
6. **所有检索演进共享同一目标函数。** 无论全文、向量、图谱还是新范式，衡量的始终是"能否把最准确、最可信、最相关的知识交给大模型"——以此设计评测标准，比追逐技术名词更可靠。
