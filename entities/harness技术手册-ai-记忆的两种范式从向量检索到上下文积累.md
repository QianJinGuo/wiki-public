GitHub 上，450 多个仓库被标记为"智能体记忆"，460 多个仓库被标记为"上下文管理"。表面看，这是一个工具泛滥的领域——人们可能预期会看到几十个功能相似、只是接口不同的产品。但深入其中会发现，这里存在着两种根本不同的技术范式，而业界尚未清晰地区分它们。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

第一种范式被称为 记忆后端 。这类系统从对话中提取事实片段，将其编码后存入向量数据库，在需要时检索相关内容。它们的工作模式类似于自动化的笔记系统：将信息归档存储，并在查询时召回。核心问题是："AI 应该记住什么？" ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

第二种范式是 上下文基底 。这类系统不追求"提取"或"编码"，而是维护结构化、人类可读的上下文文件，这些文件在多次会话中持续积累。AI 直接读取这些文件，在其框架内工作，并将输出写回其中。核心问题是："AI 应该在什么上下文中工作？" ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

当前生态中，绝大多数工具和关注度集中在记忆后端。但真正能够扩展到持续多会话、多项目协作的架构，正在上下文基底这一侧涌现。技术社区的话语体系，也开始向这一方向迁移。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

本文将沿着这条分界线展开，首先深入记忆后端的技术实现，随后剖析上下文基底的设计哲学，最终呈现两种范式在工程实践中的本质差异。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

## 阵营 1：记忆后端的技术谱系

阵营 1 的核心思路是将记忆视为独立的后端服务。LLM 负责生成内容，记忆系统负责存储和检索。这一阵营的代表性工具在架构设计上呈现出明显的分层特征。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

Mem0（5.31 万星） 是当前采用率最高的类别领导者。它定义了四项基本操作：添加、搜索、更新、删除。系统从对话中提取事实，将其存储在三个层级——用户级、会话级、代理级，并通过混合检索实现快速召回。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

Mem0 的集成复杂度极低，提供 Python 和 TypeScript 两种 SDK，可与任意技术栈对接。然而其局限性同样明显：记忆以扁平条目存储，条目之间不存在关联关系。每次提取都需要调用一次 LLM，提取质量完全依赖于提示词的设计。更关键的是，记忆一旦存储便不再演化——一月的事实与四月的事实并列存放，系统无法识别后者可能已经取代前者。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

MemPalace（4.62 万星） 选择了截然不同的路径。它采用本地优先策略，以原话形式存储对话内容，而非提取后的事实摘要。其组织架构模仿物理空间：翼楼对应实体，房间对应主题，抽屉存储原始内容，检索由 ChromaDB 完成。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

在基准测试中，MemPalace 的数据表现突出：仅凭原始语义搜索即可在 LongMemEval 评测上达到 96.6% 的检索召回率，混合管线可达 98.4%，若加入 LLM 重排序则超过 99%。这一方案的核心局限在于线性扩展——存储量随对话量同步增长，无压缩、无合成。若需求是"找回三周前说过的某句话"，这是最优工具；若需求是"概括五个项目的当前状态"，则并非合适选择。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

Supermemory（2.18 万星） 明确将自身定位为"记忆不是 RAG"。其核心差异在于引入时间感知：当用户声明"我刚搬到旧金山"，系统会自动将旧城市信息标记为过期。过期事实会被自动遗忘，用户画像由稳定事实与近期活动组合而成，检索延迟约为 50 毫秒。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

## 深度分析

### "记住什么"与"在什么上下文中工作"：两种提问方式的深层分野

两种范式的差异并不在于技术实现细节，而在于它们对 AI 记忆提出的根本问题不同。记忆后端把问题定义为"AI 应该记住什么"，记忆因此成为被动的存储客体——用户从不直接接触记忆层，只能信任系统在对的时刻召回对的事情。上下文基底则把问题重构为"AI 应该在什么上下文中工作"，上下文从后台服务变成了 Agent 工作的第一现场，读写循环围绕它展开。前者对应信息检索的延伸，后者对应可积累、可成长的协作伙伴，这一设计哲学的转变是理解整个生态分化的钥匙。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

### 真相源的让步：向量数据库公司把自家产品放到了下游

MemSearch 的设计揭示了一个耐人寻味的信号：作为 Milvus 背后的 Zilliz 团队的产品，它采用 Markdown 优先架构，记忆以人类可读、可编辑、可版本控制的文件形式存储，Milvus 只是从文件派生的"影子索引"，支持完全重建。这意味着一家向量数据库公司承认：真相源不在自己的数据库里，而在普通文件中。当基础设施厂商在自己最擅长的领域做出实质性让步，说明"文件作为真相源 + 向量作为访问层"的分层在工程实践中已经具备说服力。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

### 记忆需要"代谢"机制：从永久存储到可演化状态

阵营 1 的大多数工具把事实视为永久存在，而 Supermemory 的自动过期、Zep 的时间戳、Thoth 的置信度衰减和 OpenClaw 的三阶段"梦境"整合，共同指向一个不同命题：记忆必须是活的。OpenClaw 用六重信号评分（相关性、频率、查询多样性、近期性、整合性、概念丰富性）和三重阈值（最低分 0.8、回忆次数 3、独立查询数 3）决定哪些条目晋升为"持久真相"，执行合并非复制策略。这与 [[concepts/memory-consolidation-decay|记忆整合与衰减]] 的思路一致——没有遗忘与晋升机制的记忆系统，会像只有书架没有整理的图书馆，信息越多检索越难。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

### 召回率悖论：98% 的检索分数解决不了"理解"的问题

MemPalace 在 LongMemEval 上达到 96.6%-99% 的检索召回率，堪称惊艳；但文章明确指出，它无法回答"概括五个项目的当前状态"这类合成性问题。阵营 1 工具的共同循环——提取、存储、检索、注入——解决的是事实召回，擅长回答"是什么"，却难以回应"为什么"和"接下来应该怎样"。这说明高召回率与高理解力是两个正交目标：[[concepts/rag-retrieval-augmented-generation|RAG]] 类方案在单次交互准确性上表现优异，但跨会话、跨项目的复合增益只能来自信息的可累积性，而非检索精度的持续提升。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

## 实践启示

1. **先判断任务形态，再选范式。** 一次性事实查询、用户偏好配置类需求，记忆后端/RAG 方案效率更高；跨会话延续、多项目并行、知识需要持续沉淀的长期协作，应优先考虑上下文基底的文件中心化架构。两种范式是场景互补而非技术替代。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

2. **让上下文文件成为真相源，向量索引只做访问层。** 借鉴 MemSearch 的设计：记忆用 Markdown 存储，人类可读、可编辑、可版本控制，向量索引作为可重建的派生物。这样调试时可以直接查看和修正 Agent 掌握的信息，避免记忆黑箱。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

3. **为记忆系统设计淘汰与晋升机制，而不是只做追加。** Mem0 的教训在于一月的事实与四月的事实并列存放，系统无法识别取代关系。至少要引入时间感知（如 Supermemory 的自动过期）或定期的整合流程（如 OpenClaw 的梦境机制），让过时信息退出、频繁访问的信息晋升。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

4. **不要把检索召回率当作记忆系统的唯一 KPI。** LongMemEval 上 99% 的召回率不能说明系统能合成跨项目的状态概括。评估记忆能力时应补充合成性问题（"概括当前状态"、"基于长期观察提出建议"），这类问题才能暴露系统是否具备理解层。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

5. **警惕上下文基底的隐性门槛。** 完整形态的阵营 2 方案（如 Thoth 要求为个人上下文搭建 10 种实体、67 种关系的知识图谱，TrustGraph 依赖 Cassandra 加 Qdrant 的重型架构）对个人用户成本不低。起步时用纯 Markdown 文件 + 读-写循环即可获得大部分复合收益，图谱化可以在上下文规模真正扩大后再引入。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]

6. **与 [[concepts/context-engineering|上下文工程]] 的主流叙事对齐。** Zep 从"记忆"重述为"上下文工程"是最清晰的市场定位迁移信号；构建新系统时，用"上下文管理/上下文工程"框架来设计读写循环和评估口径，比"记忆数据库"框架更容易与生态工具衔接。 ^[raw/articles/harness技术手册-ai-记忆的两种范式从向量检索到上下文积累.md]
