## 百万上下文窗口的双面性

在与 Claude Code 用户的大量交流中，一个主题反复出现：百万级 token 上下文窗口是一把双刃剑。 ^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]

一方面，它让 Claude Code 能够更长时间自主运行，更可靠地处理复杂任务。另一方面，如果对上下文管理不够刻意，也为上下文污染打开了大门。 ^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]

会话管理的重要性前所未有，相关疑问也层出不穷：应该在终端保持一个还是两个会话？每次提示都开启新会话？何时应该使用压缩、回滚或子代理？什么会导致糟糕的压缩结果？ ^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]

其中隐藏着大量细节，几乎都源自上下文窗口的管理方式，这些因素能够真正塑造使用 Claude Code 的体验。 ^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]

## 上下文、压缩与上下文旋转基础

上下文窗口是模型在生成下一个响应时能够"看到"的全部内容。它包括系统提示、迄今为止的对话、所有工具调用及其输出，以及所有被读取的文件。Claude Code 的上下文窗口容量为一百万 token。 ^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]

不幸的是，使用上下文存在轻微成本，通常被称为"上下文旋转"（context rot）。上下文旋转指的是随着上下文增长，模型性能逐渐下降的现象——注意力被分散到更多 token 上，旧的、不相关的内容开始干扰当前任务。对于百万级上下文模型，这种退化通常出现在约 30-40 万 token 区间，但具体阈值高度依赖任务类型，并非固定规则。 ^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]

上下文窗口存在硬性上限，因此当接近窗口末端时，需要将已完成的任务总结为更精简的描述，然后在新上下文窗口中继续工作，这一过程被称为压缩（compaction）。用户也可以手动触发压缩操作。 ^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]

从元认知的角度来看，上下文管理本质上是对认知资源的分配——有限的注意力需要在相关信息和历史信息之间进行权衡。这种权衡在 AI 协作中表现为对会话状态的持续评估：哪些信息仍需保留在工作记忆中，哪些可以编码为长期记忆（压缩后的摘要），哪些已经完全无关可以清除。 ^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]

## 每个对话回合都是分支决策点

假设已经向 Claude Code 发出请求并获得了响应，此时上下文中已积累了一定信息（工具调用、工具输出、指令）。接下来存在多种选择： ^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]

- •
  继续
  （Continue）——在当前会话中发送另一条消息^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]


- •
  回滚
  （/rewind，或按两次 Esc）——跳转到之前的某条消息，从那里重新开始^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]


- •
  清空
  （/clear）——开启新会话，通常附带从已有学习提炼的简要说明^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]


- •
  压缩
  （Compact）——总结当前会话，在摘要基础上继续^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]


- •
  子代理
  （Subagents）——将下一个工作块委托给拥有独立干净上下文的子代理，仅将结果汇总回主会话 ^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]

虽然"继续"是最自然的选择，但其他四种选项的存在正是为了帮助管理上下文。这个决策框架揭示了一个深层模式：与 AI 的协作不是线性的，而是在每个回合都面临着路径选择。这种分支结构要求使用者保持对工作状态的双重觉知——既关注任务本身的进展，也关注承载任务的上下文环境。 ^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]

## 何时开启新会话

新的百万级上下文窗口意味着现在可以更可靠地执行长期任务，例如从零开始构建全栈应用。但这并不意味着不应该开启新会话——即使模型尚未耗尽上下文空间。 ^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]

经验法则：开启新任务时，同时开启新会话。^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md]

## 深度分析

### 上下文旋转：百万窗口的隐性代价

原文指出了百万级上下文最反直觉的一点：窗口变大并没有消除注意力稀释问题，只是把它的阈值推后了。模型性能通常在 30-40 万 token 区间开始退化，且阈值随任务类型浮动，没有通用公式。这意味着"还有剩余空间"不等于"还能可靠工作"——退化是渐进且难以察觉的，等模型明显变笨时再补救已经晚了。^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md:32-45]

更关键的时间点耦合在于：压缩往往在上下文最膨胀的时刻自动触发，也就是模型智力水平的最低点。一个质量差的压缩摘要会在新窗口里持续误导后续工作，错误在此时被"固化"进交接材料。^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md:102-112]

### 回滚优先于纠正：分支式协作的心智模型

原文最有操作价值的洞察是把每个对话回合视为分支决策点：继续、回滚、清空、压缩、子代理五种路径中，"继续"只是默认项而非最优项。当 AI 的探索失败时，直接输入"不对，试试 X"会在错误路径之上继续堆叠上下文；回滚到分叉点、用已获得的有效认知重新提示，得到的是干净的方向修正而非补丁摞补丁。^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md:42-90]

"从此处总结"（summarize from here）进一步把回滚升级为知识保留手段——失败的探索也能产出交接信，只是剥离了无效的中间过程。这实际上把 AI 协作从线性流水线重构为带版本控制的分支树。^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md:88-90]

### 压缩与清空：自动化与控制权的张力

压缩和清空表面相似，实质是两种所有权模型：压缩把"什么重要"的判断权交给模型，省力但有信息丢失风险，可用指令引导方向；清空由用户亲手撰写交接说明（目标、约束、关键文件、已排除方案），成本高但上下文完全可控。原文的结论是没有普适答案——低智力敏感的后续任务（如补文档）可以容忍压缩的信息损耗，高风险任务值得投入手写摘要的成本。^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md:92-100]

糟糕压缩的共同根源是压缩的"向后看"本质：它总结已完成的工作，却无法预测下一步。长调试会话自动压缩后，用户突然要求修复另一个文件的警告，这个未在会话焦点中的事项很可能已被剔除。对策是"前瞻性压缩"——手动触发 /compact 并在指令中写明后续工作方向，用主动引导弥补压缩的短视。^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md:104-112]

### 子代理：用边界控制复杂性的架构模式

子代理机制与软件工程中的事务隔离、沙箱执行、函数作用域同构：为会产生大量中间输出的工作块开辟独立的干净上下文，只把精炼结论汇回主会话。判断标准很朴素——需要再次使用工具的原始输出，还是只需要结论？需要原始输出就留在主会话，只要结论就委托出去。^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md:114-130]

这一模式把"上下文"从被动容纳的资源变成了可主动设计的架构元素：分层会话、子代理边界、预防性压缩，本质上都是在为注意力划定边界。角色也随之转移——使用者从任务执行者演变为任务架构师，负责设计 AI 的工作环境与边界条件。^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md:134-142]

## 实践启示

1. **新任务开新会话，即使窗口未满**。经验法则是任务切换即会话切换；唯一例外是后续任务高度依赖前序认知成果（如为刚实现的代码写文档），此时复用价值大于污染风险。^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md:68-78]
2. **失败探索先回滚再重提示，不要在错误路径上纠正**。用双击 Esc / /rewind 回到分叉点，带上已验证的认知重新给方向；需要保留学习成果时用"从此处总结"生成交接信。^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md:80-90]
3. **不要等自动压缩，主动做前瞻性压缩**。在 30-40 万 token 退化区间之前、于关键节点手动 /compact，并在指令中写明后续工作方向（如"关注 auth 重构，省略测试调试"），避免压缩在模型智力最低点做出偏离需求的摘要。^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md:102-112]
4. **高风险交接用手写 /clear，低敏感任务用 /compact**。清空时亲手写下目标、约束条件、关键文件和已排除方案；文档、整理类任务则可接受压缩的信息损耗换取省力。^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md:92-100]
5. **大中间输出、结论简洁的工作块委托给子代理**。如"按规范验证结果""通读另一代码库总结 auth 流程再实现""基于 git 变更写文档"，只让结论回流主会话。^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md:114-130]
6. **把上下文当作架构资源来设计**：分层会话（每个会话聚焦一个独立工作单元）+ 子代理边界 + 预防性压缩，目标是"越相关越好"而非"越大越好"。^[raw/articles/harness技术手册-会话管理与百万级上下文实战启示.md:134-142]
