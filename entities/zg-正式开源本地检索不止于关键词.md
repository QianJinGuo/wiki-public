# zg 正式开源：本地检索，不止于关键词

## 摘要

zg（zvec-grep）是一套面向人与 Agent 的本地优先检索基础设施，把 Zvec 提供的向量检索与 BM25 能力同 ripgrep 的精确匹配拼在同一条链路上，以 CLI 和 MCP 两种入口交付。它要解决的具体落差是：Agent 的查询已经从「函数名、配置项、报错原文」变成「业务现象、实现意图、知识概念」这类自然语言描述，而后者在代码与文档里往往找不到对应的字面词。zg 的思路是让模糊探索、相关性收敛、精确验证三个阶段各用各的检索方式，并把结果组织成可独立定位的信息单元，从而压掉 Agent 的搜索轮次与上下文消耗。^[raw/articles/zg-正式开源本地检索不止于关键词.md]

## 核心要点

- **四种检索能力并存**：语义（向量）检索、BM25、混合检索（两路候选经 RRF 融合、去重、统一排序）、以及 rg 精确匹配，按问题里是否存在明确关键词、位置或符号来选路。
- **三步上手**：`npm install -g @zvec/zvec-grep` 安装；`zg install` 自动发现本机的 Codex、Claude Code、Cursor、OpenCode 并写好 MCP 配置（可用 `--target codex --yes` 指定目标）；在仓库内执行 `zg index` 建索引；之后用 `zg query --human` 检索，或直接在已连接的 Agent 里提问。
- **同一份索引，两个入口**：CLI 与 MCP 复用同一份本地索引，人建的索引 Agent 直接可用，不需要重复构建与配置。
- **内容覆盖**：代码支持 C/C++、Go、Java、JavaScript/TypeScript、Python、Rust 以及 Vue/Svelte 组件（从组件文件中提取脚本内容）；文档支持 Markdown、纯文本、RST、HTML/XML；数据与文本文件支持 CSV、JSON、TOML、YAML 及其他可识别文本。对能结构解析的语言提取符号、签名与层级，Markdown 按标题与章节切分，其余按通用文本切片。
- **范围可控**：路径、Glob、文件类型与忽略规则可限定检索范围，避免「覆盖面变大即噪声变大」。
- **默认全本地**：文件扫描、内容提取、本地 Embedding、索引与检索都在设备内完成；内置 11 种端侧模型，默认 `local/potion-code-16m-v2` 是 16M 级静态模型，本地缓存约 32 MiB，无需 GPU。远程 Embedding 不会自动启用，须显式授权文本才会离开设备。
- **嵌入式索引**：Zvec 以嵌入式方式在设备内存储向量与 BM25 索引，无需另部署和维护数据库服务。
- **实测口径与状态**：SWE-QA-Bench（20 个真实仓库问答任务）上工具调用减少一半以上、输入 Token 减少近一半、评审得分提升 1.50；BrowseComp-Plus（80 个深度研究问题）上准确率 98.67%→99.00%、输入 Token −37.56%、工具调用 −43.52%、耗时 −38.58%。两组均为同 Agent、同模型、同 Prompt、同环境的配对 A/B，预建索引的一次性开销未计入。项目以 Apache 2.0 开源，官方自述仍处起步阶段。

## 深度分析

### 查询分布变了，关键词检索的失效点不在排序

rg 的能力边界一直很清楚：只要给得出字面锚点，它快、准、穷尽，且结果可逐条验证。问题在于 Agent 拿到的任务描述经常不含这种锚点。原文的两个例子很典型——「恢复主题偏好」在代码里叫 `hydratePreferences`，「访问权限申请流程」在文档里叫「账号授权与审批」。查询词与文本表述没有词汇交集，这不是排序不好，是候选集里根本没有正确答案。^[raw/articles/zg-正式开源本地检索不止于关键词.md]

此时 Agent 的唯一补救是扩大搜索范围，问题随即从「搜不到」变成「搜到太多且无序」。接着是多轮构造查询、执行搜索、读取文件，再从分散的匹配里手工拼上下文——每一轮都是工具调用、响应时间和 Token 的实际支出。真正贵的不是单次查询慢了，而是整个任务被拉长，且结论可能建立在不完整的证据上。所以 zg 的立足点不是「比 rg 更强的搜索」，而是「在 rg 仍是正确解法的场景之外，补上前半段」。^[raw/articles/zg-正式开源本地检索不止于关键词.md]

### 本地优先改写的是成本结构，不只是隐私叙事

把检索搬回设备内通常被当成合规话术，但对 Agent 这类高频检索负载，更直接的影响在成本侧。托管 embedding 的每次查询都要付网络往返、按量计费和数据出口三份代价，而这三份代价会被多轮检索放大：一个任务里几十次工具调用，每次都可能触发一次远端请求。本地索引把边际成本压到接近零，只留下一次性建索引的开销——原文给出的量级是 Django 仓库 3,457 个文件在 Apple M4 Pro 上完整索引不到半分钟，且支持增量更新、可跨查询与跨 Agent 任务复用。成本模型从「按查询付费」变成「按语料付费」，这是两种不同的预算逻辑。^[raw/articles/zg-正式开源本地检索不止于关键词.md]

把远程能力做成「必须显式授权」而非「可选配置」，是这份设计里更值得记的一笔。它把数据流向从一条需要用户相信的承诺，改成一道需要用户点确认的闸门：默认路径上没有代码或内部文档出网，需要更强模型时才由使用者主动打开。对处理未公开代码的团队，这比任何精度数字都更接近能否采用的门槛。^[raw/articles/zg-正式开源本地检索不止于关键词.md]

### 能力上限与证据强度：读它没说什么

默认的 16M 静态模型，官方措辞是取得「接近」远程 `qwen/qwen3.7-text-embedding` 的任务效果，而不是达到或超过。这是诚实的表述，也划出了天花板：模型容量决定了它在长文档、多语言与领域术语上的上限。原文只说本地模型「无法满足检索质量、多语言覆盖或设备资源条件时」可切远程，反过来说明这三项正是本地路径的已知弱项。^[raw/articles/zg-正式开源本地检索不止于关键词.md]

证据层面同样要打折。两个 benchmark 都是自建自评，协议与复现代码放在自家仓库，未见第三方复现。SWE-QA-Bench 只有 20 个任务，1.50 分的评审提升在这个样本量上很难谈统计显著；BrowseComp-Plus 的准确率从 98.67% 到 99.00% 已贴近天花板，说明该场景下 zg 的价值主要落在 37.56% 的 Token 与 43.52% 的调用节省，而不是答得更对。还有一处信息缺口：原文有一张同类工具的能力对比表（参考资料中列出的对标项目是 Semble、qmd、CodeGraph），但抓取到的正文只剩图例（✅/❌ 与 High/Medium/Poor 的定级说明），没有具体行，因此无法据此判断 zg 在格式覆盖、属性过滤、Embedding 模型配置等维度上相对同类的真实位置。^[raw/articles/zg-正式开源本地检索不止于关键词.md]

### 对 Agent harness 的含义：检索是一个路由问题

zg 的四个优化点里，最不像「检索」的其实是第一个：通过 MCP 工具描述与使用指引，帮 Agent 判断该用哪种检索方式，并在信息充分时停止搜索。这等于承认了一件事——对 Agent 而言，检索效果的上限由「选对工具」和「知道何时停」共同决定，不单由索引质量决定。工具描述在这里不是文档，而是策略：模型读到什么描述，就按什么方式检索。^[raw/articles/zg-正式开源本地检索不止于关键词.md]

第二个值得抄的设计是返回单位。zg 按代码符号、文档章节切出可独立定位的信息单元，保留文件路径与来源位置，默认只回紧凑的排序结果加有限预览，需要时再读全文。这等于把「先读整个文件再自己找」的负担从模型侧挪到索引侧：harness 交付的是地址，不是内容。再配合 rg 作为最终验证手段——语义给候选、混合排序做收敛、精确匹配出证据——一条链路才闭合。三种能力不是替代关系，而是同一条流水线上的不同工位。^[raw/articles/zg-正式开源本地检索不止于关键词.md]

## 实践启示

1. **先看查询分布，再看 benchmark 分数**。语料里关键词命中率高的场景，rg 依然是最优解；只有当「知道要什么、不知道该搜什么词」的任务占比上来，建索引才划算。
2. **把检索路由写进工具描述**。明确「有符号或关键词用精确匹配、只有意图描述用混合检索、证据足够就停止」，往往比调 top-k 更省 Token。
3. **返回可定位单元而非整个文件**，结果先预览、按需展开。上下文预算是最稀缺资源，检索层是第一道闸门。
4. **本地优先的判据不是「能不能本地跑」，而是「默认路径是否出网」**。把远程能力设计成显式授权，敏感语料的团队才敢真正采用。
5. **对自评 benchmark 折价**。看配对 A/B 的相对变化（Token、调用次数、耗时）比看绝对准确率可靠，尤其当基线已接近天花板时。
6. **建索引成本要摊到复用次数上算账**。单次任务不值，跨查询、跨 Agent 复用时才成立——这正是「同一份索引给 CLI 和 MCP 共用」的实际价值。
