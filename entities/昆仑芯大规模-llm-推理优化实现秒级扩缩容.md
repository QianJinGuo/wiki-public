在实际业务运行中，大模型推理服务会面临明显的流量波动，不同时段的请求量差异很大。如果不能快速扩容，就会出现两种问题：要么峰值时服务响应慢、甚至超时，影响用户体验；要么为了应对峰值长期预留大量资源，造成资源闲置浪费。所以我们需要具备快速弹性扩缩容的能力。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md]

但对于大模型推理而言，快速扩容存在一些现实瓶颈，从 0 到完全拉起一个大模型服务，动辄数分钟。我们以 Qwen3-235B 为例，把 521 秒冷启动耗时拆解开：69% 的时间耗在权重加载，磁盘 I/O 是最大瓶颈，传统的加载路径往往比较低效；15% 是一些编译开销；5% 是 CUDA Graph 初始化延迟。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md]

针对前面的问题，我们对大模型冷启动的过程做出了一些优化：主要包括权重传输优化、编译缓存复用、特定场景的 CUDA Graph 延迟捕获策略，以及启动加速优化，对大模型冷启动的完整流程做了性能提升。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md]

首先来看权重传输优化。

我们知道，模型权重是冷启动中最大的耗时项，传统方式是从磁盘加载，速度慢。我们的思路是，如果集群中已经有其他节点在运行相同的模型，我们能否直接从这些运行中的节点同步权重，而不是每次都从磁盘读取？ ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md]

基于这个思路，我们设计了自适应权重传输引擎。它主要包含三个关键点：^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md]


- 第一，利用 NVLink 和 RDMA 这样的高速网络，直接在节点间传输权重，完全绕开磁盘；

- 第二，我们设计了并行传输架构，接收端会为每一块 GPU 都建立独立的 RDMA 连接，这样可以充分利用多网卡的带宽，实现并行传输；

- 第三，这个引擎能够智能地判断传输场景，如果是在同一台机器内部，就使用 NVLink，如果是在不同机器之间，就使用 RDMA，自动选择最优的传输路径。

通过这些优化，我们成功将 Qwen3-235B 模型的 348 GB 权重传输时间缩短到了约 2 秒，极大地突破了磁盘 I/O 的瓶颈。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md]

接下来是编译缓存复用。

我们发现，在跨节点部署时，每个新节点启动都会重复大量的编译工作，这造成了大量的时间和资源浪费。我们的解决方案是，将这些编译产生的中间状态，比如 Inductor 优化缓存、DeepGEMM 算子、Triton 内核等，进行统一的缓存和管理。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md]

当一个新节点启动时，它会首先检查是否有匹配的缓存可用，如果有，就直接通过 RDMA 高速网络从缓存节点同步过来，无需重复编译。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md]

为了保证缓存的一致性和命中率，我们采用了一致性哈希等技术来管理缓存节点，从而实现 100% 的缓存命中率，在扩容场景下可以完全消除重复编译的开销，确保了所有推理引擎实例的一致性。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md]

第三项优化是针对 CUDA Graph 的。^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md]


传统的 CUDA Graph 是在启动时一次性捕获所有计算图，这非常耗时，通常需要 10 到 60 秒。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md]

我们采用了一种 Lazy CUDA Graph 的分阶段捕获策略。具体来说，在实例初始化阶段，我们只捕获最小必要的计算图，确保内存池等核心组件能够正常工作，这样可以大大减少初始化时间和显存占用。当第一个实际的推理请求到达时，我们再一次性捕获剩余的完整计算图。之后 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md]

## 深度分析

### 权重传输引擎：把冷启动瓶颈从磁盘 I/O 重构为网络拓扑问题

自适应权重传输引擎最深一层的含义，是它改变了扩容问题的物理模型：模型权重不再被当作「磁盘上的静态文件」，而被当作「集群内可流动的热数据」。348 GB 权重通过 NVLink/RDMA 节点间直传约 2 秒，意味着有效带宽达到约 170 GB/s 量级——这只有在接收端为每块 GPU 建立独立 RDMA 连接、多网卡并行传输时才可能达成。工程推论是：扩容速度的上限不再由存储介质决定，而由「同模型运行节点之间的网络拓扑质量」决定，容量规划时应把 RDMA 带宽视为与 GPU 数量同级的弹性资源。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md:41-47]

### 编译缓存复用：一致性哈希让编译彻底退出冷启动关键路径

Inductor 优化缓存、DeepGEMM 算子、Triton 内核这类编译产物是确定性的（同模型 + 同配置 → 同产物），天然适合缓存化。用一致性哈希管理缓存节点并做到 100% 命中，等价于把「编译」从每次扩容的成本项变成集群层面的一次性摊销成本。更关键的是编译缓存与权重传输共用 RDMA 通道，新节点启动时间可近似建模为「权重传输时间 + 常数」，扩容耗时的可预测性大幅提升——这对上游调度器设定扩容超时和就绪探针参数是决定性的输入。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md:49-55]

### Lazy CUDA Graph：用首请求延迟置换初始化时间与显存

传统 CUDA Graph 启动时一次性捕获需 10-60 秒；Lazy 策略在初始化阶段只捕获最小必要计算图，把完整捕获推迟到第一个真实请求到达。这是典型的延迟置换：首请求 TTFT 额外承担一次完整捕获开销，换来初始化时间从 10-60 秒降到 1-2 秒、以及更小的显存占用（无需为所有 batch size 预建图，[[entities/vllm|vLLM]] 的内存池等核心组件先保证可用）。它适合资源紧张或对首请求 TTFT 不敏感的场景；对核心在线业务则应选守护实例模式——静默实例只保留 CUDA 上下文、释放权重与 KVCache，唤醒 235B 级模型也只需约 6 秒。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md:57-63,65-73]

### 秒级弹性对 LLM serving 成本模型的影响

Qwen3-235B 守护实例唤醒 4.91 秒、优化率 99.06%；GLM-4.5（668 GB 权重）唤醒 8.23 秒、优化率 98.83%。当扩容从「分钟级预留」变成「秒级按需」，[[concepts/inference-optimization|推理优化]]的收益直接传导到成本曲线：serving 从「按峰值配置静态计费」切换为「按实际流量动态伸缩」——权重不再要求常驻显存，GPU 时长可以真正跟随流量波动回收。对昼夜流量比悬殊的业务，这意味着可以激进缩容到接近零、峰值前预热，代价是引入「预热编排」这一新的运维复杂度。配套的进程层优化（在创建 CUDA 上下文之前执行 Fork，复用父进程已加载的解释器与依赖）则消除了 Spawn 模式数秒级的重复导入开销。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md:93-99,75-79]

## 实践启示

1. **先拆解冷启动耗时再优化**：521 秒被拆为 69% 权重加载 / 15% 编译 / 5% CUDA Graph，按占比排序投入，权重传输（绕开磁盘改走 RDMA）优先级最高。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md:31-33]
2. **同模型运行节点是免费的高速权重源**：扩容前先查询集群中是否已有运行相同模型的节点，有则节点间直传权重，避免重复走磁盘加载路径。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md:37-39]
3. **把编译产物当作一等公民缓存管理**：对 Inductor/DeepGEMM/Triton 产物统一缓存并用一致性哈希保证命中，新节点扩容时完全跳过编译。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md:51-55]
4. **按业务 SLO 选部署模式**：核心在线业务用守护实例模式（首请求几乎零延迟、需预占少量资源）；资源紧张或对 TTFT 不敏感用 Lazy Graph 模式；中等规模低频启动用正常 Graph 模式。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md:83-89]
5. **不要忽略进程启动的隐性成本**：在创建 CUDA 上下文之前执行 Fork，让子进程复用已加载的 Python 解释器与依赖，消除 Spawn 模式数秒级的重复导入。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md:77-79]
6. **弹性能力要写回容量规划**：实测扩容耗时降低 95%、启动提速 10-30 倍后，应重新校准调度器的扩容超时、就绪探针与预热策略，而非沿用分钟级冷启动时代的保守参数。 ^[raw/articles/昆仑芯大规模-llm-推理优化实现秒级扩缩容.md:105-113]
