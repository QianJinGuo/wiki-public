## 摘要

文章指出 AI 基础设施的核心问题已从模型选型转向 Agent Harness（编排基础设施）的构建，而当前 Harness 与传统 Backend 被当作两个独立系统的分层只是过渡形态：Agent 行为的随机性使跨系统调试路径按"Agent 数量的平方乘以后端服务数量"组合级增长，四个 Agent 对五个后端即膨胀为八十条随机路径。作者提出后端可还原为三种基本原语——Worker（连接引擎注册能力的工作进程）、Trigger（声明式触发器）、Function（具稳定标识符的工作单元），Agent 可直接作为 Worker 接入引擎，其工具即函数、记忆即状态、编排即 Trigger 组合，由此 Harness 不再是后端之上的附加层，"Harness 即后端"。统一原语还带来品类折叠（一切答案都是"添加一个 Worker"）与实时发现、实时扩展、实时可观测三大内生产物，并支持沙箱即 Worker 的递归能力。^[raw/articles/2026-05-01-Harness-即后端-当Agent基础设施消解于统一原语-unknown.md]

## 关键要点

- Harness 设计谱系从精简编排（决策权交模型）到重度结构化编排（指令栈、显式交接、确定性流控），本质是模型信任度与逻辑编码强度的取舍
- Agent 调试难度公式：Agent 数量的平方 × 后端服务数量；Agent 随机性是设计本意而非缺陷
- 后端三原语：Worker / Trigger / Function，Function 以稳定标识符（如 orders::validate）寻址，Trigger 把 HTTP、Cron、队列、状态变更等信号声明式绑定到函数
- 品类折叠：队列、沙箱、Cron、可观测性、Agent 全部归结为注册 Function 和 Trigger 的 Worker，语义存在于 Function 而非基础设施
- 统一架构涌现三大实时特性：实时发现（全量函数目录）、实时扩展（运行时注册无需重启）、实时可观测（Trace ID 跨 Worker/语言/队列自动传播），并支持 Worker 创建 Worker 的递归沙箱

## 深度分析

### 被默认的分层预设：Harness 独立于 Backend 只是历史过渡

文章最具穿透力的一步，是审视一个几乎无人质疑的行业预设：Harness 被当作外在于传统 Backend 的附加层，Agent 的循环、工具与记忆归入编排侧，队列、状态管理、HTTP 路由与可观测性归入另一侧。在这一主流架构里，Harness 以独立进程包裹模型，把 Tool Call 翻译成 HTTP 请求去触发后端的队列发布与数据库写入，两个世界各自维护互不关联的重试策略与超时配置。作者判断这种分离并非深思熟虑的架构决策，而是技术演进中的过渡形态——随着 Agent 架构普及，编排逻辑与后端基础设施的边界将逐步消解，融合为统一的后端抽象模型。^[raw/articles/2026-05-01-Harness-即后端-当Agent基础设施消解于统一原语-unknown.md:18-26]

### 随机性是一等公民：调试组合爆炸与确定性范式的冲突

传统跨系统日志关联之所以是常规操作，前提是系统大体确定——相同输入产生相同输出，故障路径可精确复现。Agent 恰恰以破坏这一前提为使命：相同输入理应产生差异化的决策序列。文章给出的调试复杂度公式（Agent 数量的平方 × 后端服务数量）揭示了分层的真实代价：一个 Agent 对五个后端是五条随机路径，四个 Agent 对五个后端就膨胀为八十条，且每新增一个 Agent 都在非线性扩展排查面。关键在于作者拒绝把随机性当作需要驯服的实现缺陷——它是 Agent 的核心价值之源，因此正确的出路不是用约束把 Agent 确定化，而是解构"后端是什么"这一基本问题，让架构主动适应随机范式。^[raw/articles/2026-05-01-Harness-即后端-当Agent基础设施消解于统一原语-unknown.md:28-34]

### 自底向上还原三原语：Agent 成为后端的原生参与者

文章指出，自顶向下拆解后端只会得到不断增长的清单——服务分类、集成方案、架构图、编排代码，那是在罗列现象而非追溯本质；转为自底向上后结构骤然清晰：Worker 负责连接引擎并注册能力，Trigger 声明函数在何种事件下被执行，Function 是以稳定标识符（如 orders::validate）寻址的纯粹工作单元，三者分别承担连接、调度与执行，其余复杂性皆可还原为其组合。这个抽象的真正杠杆在 Trigger 的声明式解耦：HTTP、Cron、队列、状态变更等任何信号都能绑定到同一函数，新增触发条件无需修改函数本体。由此 Agent 无需专属集成层——它直接作为 Worker 接入引擎，工具即函数、记忆即状态、编排即 Trigger 的组合级联，与其他后端组件共享同一执行上下文（参见 [[concepts/agent-backend-unification]]），"Harness 即后端"由是成立。^[raw/articles/2026-05-01-Harness-即后端-当Agent基础设施消解于统一原语-unknown.md:38-48]

### 品类折叠与三大实时特性：统一架构的内生产物而非功能堆叠

统一原语最深远的效果是品类折叠：队列、沙箱、Cron、可观测性、Agent 在传统平台中各居其本体论之下（Broker 语义、路由语义、调度语义、编排语义），统一后全部归结为"注册了 Function 和 Trigger 的进程"，语义从基础设施移入 Function 本身，系统边界从预定义的产品清单变为运行时可无限扩展的注册表。文章强调实时发现、实时扩展、实时可观测三大特性不是叠加组件的结果，而是架构模式本身的内生产物：引擎作为唯一真相源维持能力的实时拓扑，使 Agent 始终看到完整且不过期的能力边界；运行时注册无需重启或修改配置；Trace ID 跨 Worker、跨语言、跨队列自动传播，把"三个独立系统靠时间戳勉强拼接"的调试折叠为一步直达关联日志。递归能力则将模式推向更深层——沙箱本身就是 Worker（参见 [[concepts/agent-sandbox]]），Worker 可以创建 Worker，基础设施从产品品类转变为设计模式。^[raw/articles/2026-05-01-Harness-即后端-当Agent基础设施消解于统一原语-unknown.md:50-76]

值得补充的是，这场统一也重写了 Harness 设计谱系之争：当所有 Agent 都被视为 Worker，精简编排与重度结构化编排不再是两种对立范式，而是同一组原语下注册函数多寡、是否引入审批门控的两种组合方式（参见 [[concepts/agent-harness-engineering-paradigm]]）；"随模型进步移除脚手架"也从系统级重构降维为函数层面的增减调整。Worker 的边界因此是开放的——云端服务、浏览器标签页、边缘传感器、临时沙箱，凡能连接、注册、遵循协议者皆享有同等地位。^[raw/articles/2026-05-01-Harness-即后端-当Agent基础设施消解于统一原语-unknown.md:78-88]

## 实践启示

1. 架构评审时把"添加一个 Worker"设为默认答案：遇到队列、沙箱、Cron、流处理等新需求，先问能否用注册 Function 与 Trigger 的 Worker 实现，再考虑引入独立产品，以品类折叠抑制平台目录式的拼装膨胀。
2. 在引入第 N 个 Agent 前先算调试账：随机路径按 Agent 数量平方 × 后端服务数增长，若 Trace 无法跨 Worker/队列/语言连续传播，扩 Agent 等于放大不可排查的故障面；可观测性必须内建于调用链路，而非事后装配中间件。
3. 把 Agent 的工具建模为以稳定标识符寻址的 Function、记忆建模为共享状态、任务交接建模为 Trigger 级联，让 Agent 作为普通 Worker 接入执行引擎，而不是为它单建一套基础设施层。
4. 利用 Trigger 的声明式解耦：新增 HTTP、Cron、队列、状态变更等触发条件时只加绑定、不改函数本体，使同一工作单元可被多种事件源驱动，避免为每种调用方式编写适配逻辑。
5. 沙箱、临时专用 Agent、并行任务集群优先采用"Worker 创建 Worker"的递归模式：硬件隔离的微虚拟机接入即注册、断开即自动注销，不必为隔离执行单独维护一套沙箱产品栈。
6. 把精简与重度 Harness 之争降维为设计模式选择：模型可信的场景少注册函数、交由模型自主决策；需要管控的场景增加审批门控与条件逻辑。模型升级后的架构简化应体现为函数增减，而非重构两个系统之间的集成接口。
