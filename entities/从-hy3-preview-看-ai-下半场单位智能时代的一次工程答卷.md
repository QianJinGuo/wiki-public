这个判断在当时并不算共识，但此后的一年里，它被几件事一件一件印证了：头部开源和闭源模型的能力差距肉眼可见地在缩小，“模型更强”能撬动的用户感知越来越小；Agent 应用爆发，把一个过去被忽视的变量——单位推理成本——推到了决定生死的位置；越来越多团队发现，在标准 benchmark 上领先的模型，放在真实业务里未必好用、甚至往往更贵。一句话总结：^[raw/articles/从-hy3-preview-看-ai-下半场单位智能时代的一次工程答卷.md]

“benchmark 上的胜负”和“真实世界里的胜负”是两件事。 ^[raw/articles/从-hy3-preview-看-ai-下半场单位智能时代的一次工程答卷.md]

这一点，在最近 Hy3 preview 和 DeepSeek V4 几乎前后脚发布时，又被印证了一次。两家的路径并不完全一样：DeepSeek V4 用 Flash 和 Pro 两个版本覆盖不同层级的需求，Hy3 preview 则用一个不到 300B 的模型主动去找效果、速度、价格之间的平衡点；但它们指向的是同一个共识——^[raw/articles/从-hy3-preview-看-ai-下半场单位智能时代的一次工程答卷.md]

在真实世界里，性价比正在变得比“性能最优”更重要。 ^[raw/articles/从-hy3-preview-看-ai-下半场单位智能时代的一次工程答卷.md]

Agent 的登场，把这套判断从一种预言推成了现实。ChatBot 时代一次对话只消耗几百到几千 token，单位成本是个次要问题；Agent 时代一次任务动辄几十万乃至上百万 token，单位成本就成了决定产业形态的结构性变量。一夜之间，整个行业被迫面对一个新的三角约束——^[raw/articles/从-hy3-preview-看-ai-下半场单位智能时代的一次工程答卷.md]

质量、速度、价格，这三件事不可能同时做到极致。 ^[raw/articles/从-hy3-preview-看-ai-下半场单位智能时代的一次工程答卷.md]

## 深度分析

### 单位智能：Agent 时代的"不可能三角"

文章最有解释力的框架，是把 Agent 时代给模型施加的约束总结为质量、速度、价格三者不可兼得的三角。只追质量意味着最大参数与最长推理链，慢且贵，注定小众；只追速度靠蒸馏，质量崩塌；只压价格靠激进稀疏、量化与批量调度，代价是首 token 延迟拉长。产品化模型必须在三角里主动选一个平衡点并与业务精确匹配——不是做得最好，而是做得最合适。Hy3 preview 的选择很清晰：295B MoE 让激活参数远小于总参数，吞吐友好；质量进入可用区而不追 SOTA；单位 token 成本压到腾讯量级业务可承受的区间，明确站在"日常任务 + 结构化产物"一侧。^[raw/articles/从-hy3-preview-看-ai-下半场单位智能时代的一次工程答卷.md]

### The Second Half 判断的自我兑现

叙事锚点是姚顺雨 2025 年 4 月的 The Second Half：评估要从方法的陪练位转向驱动位。此后一年，开源闭源差距缩小、Agent 爆发把单位推理成本推到生死线、benchmark 领先者落地未必好用，都在为这个判断供证。提出判断的人加入腾讯基模线后交出的第一份作业就是 Hy3 preview，构成"理论 → 学术实证（CL-bench）→ 工程兑现"的闭环——观察一次发布时，"提出者如何用产品回应自己的判断"比 benchmark 档位更有信息量。结合 [[concepts/harness-engineering-framework|Harness Engineering]] 视角看，80 分模型配 90 分 Harness，综合表现可以碾压 95 分但只有裸 API 的竞品。^[raw/articles/从-hy3-preview-看-ai-下半场单位智能时代的一次工程答卷.md]

### 单位推理成本：ChatBot 与 Agent 时代的分水岭

ChatBot 时代一次对话几百到几千 token，单位成本只是次要账目；Agent 时代单任务动辄几十万乃至上百万 token，单位推理成本上升为决定产业形态的结构性变量。作者用 TeachAny 项目佐证：课标转 Markdown、知识点抽取这类低智力密度任务吞 token 极快，用旗舰模型很快撞上成本墙；把日常任务切到 Hy3、复杂推理留给旗舰后，同任务量下速度提升、消耗显著下降。^[raw/articles/从-hy3-preview-看-ai-下半场单位智能时代的一次工程答卷.md]

### 性价比 vs 性能最优：与 [[entities/deepseek-v4|DeepSeek V4]] 的路径对照

两家前后脚发布指向同一共识——真实世界里性价比比性能最优更重要——但路径不同：V4 用 Flash/Pro 双版本分层覆盖；Hy3 用单模型把三角平衡点往中间推，不做版本分层地独立承接场景。选型第一问已从"哪家最强"变成"哪个形态在我的调用分布下单位经济跑得通"。文章也提醒：Hy3 不是能力第一，算力约束短期无解，平衡点对不对要靠 6-12 个月真实业务数据验证。^[raw/articles/从-hy3-preview-看-ai-下半场单位智能时代的一次工程答卷.md]

## 实践启示

1. 按任务复杂度做模型路由：识别、整理、抽取、长文生成等高调用低单值任务切到中型高性价比模型，复杂推理留给旗舰——这比单纯追单模型能力更决定性。
2. 用 TCO 而非榜单选型：企业 Agent 采购里总拥有成本已接近第一决策维度，先算模型在你的调用分布下的单位任务成本。
3. 用 Harness 外推平衡点：Tool Use、上下文工程、缓存复用可在不换模型的前提下改善质量-成本曲线。
4. 把 context 准备当一等工程：竞争焦点正从"谁把模型训得更好"转向"谁能为任务提供最丰富最相关的 context"，沉淀 skill 比堆 prompt 更可持续。
5. 组织效率是算力之外的第二杠杆：Hy3 从架构调整到交付不到 3 个月（传统大厂往往超 6 个月），扁平化与产品需求反向嵌入训练目标直接兑换为迭代速度。
6. 给"过程版本"以耐心：快速迭代的过程版本优于等 12 个月的完美版本，但盯住下一代能否"质量推一格、成本压一格"来验证平衡点。
