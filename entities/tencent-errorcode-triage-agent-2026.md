# 腾讯错误码排查 Agent

腾讯技术工程（careylu，AI Agent 开发工程师）基于智能体编排平台搭建的错误码治理 Agent：将**知识库、代码关系图谱、可观测平台、代码托管平台**四类能力挂载到单个 Agent，自主编排排查流程，分钟级产出根因分析与修复建议。SRE 每天面对去重后数百个错误码告警，人工排查一个错误码需 3～8 小时，大量时间耗在跨系统检索与上下文拼凑上；该 Agent 把治理链路从「小时级排查＋天级修复」压到「分钟级排查＋0.5～2 天修复」。50 条 case 对比中 action_type 与人工标注一致率从 66%（v3）→ 88%（v4），需人工介入率 34% → 12%，硬冲突率 20% → 0%。核心叙事：让 SRE 从「告警搬运工」升级为「修复建议审核员」。^[raw/articles/错误码排查从-38-小时到分钟级agent怎么做到的.md]

## 深度分析

### 1. 单 Agent 选型：渐进式探索场景下上下文完整性 > 职责清晰

文章给出了一个可复用的场景化选型论证。多 Agent 协作（知识库/代码/运行时 Agent 分工＋汇总 Agent 收敛）适合**子任务可独立执行、并行验证**的任务；而错误码排查是典型的渐进式探索——查到 handler 再追上游、日志显示限流后再确认错误码定义，每一步依赖上一步结果，多 Agent 编排的上下文传递损耗大于收益。单 Agent 的代价是 Prompt 复杂、需要明确能力边界，解法是把完整排查流程、工具使用规则和输出约束沉淀到一个 Skill。值得注意的否定性经验：按排查路径拆多个 Skill 也试过，但切换依赖 Agent 自觉、通用规则重复维护，弃用；动态子任务编排增加状态管理成本，非重点。^[raw/articles/错误码排查从-38-小时到分钟级agent怎么做到的.md]

分工口诀「工作流是骨架，Agent 是大脑，四类能力是感官」：编排平台工作流负责入参预处理、条件判断、Agent 调用、结果解析和输出组装（11 节点，含 Start/End）；Agent 负责自主排查并输出 JSON；Skill 承载流程与规则；业务侧提供知识、代码与运行时数据。^[raw/articles/错误码排查从-38-小时到分钟级agent怎么做到的.md]

### 2. 多源证据编排：每类能力有明确的证据职责与调用约束

四类能力不是等价工具列表，而是各自绑定证据职责＋硬约束，防止 Agent 乱试：

| 能力 | 证据职责 | 关键约束 |
|---|---|---|
| 知识库 kb-retriever | 仓库映射、业务架构、API 文档、历史经验 | repo_name 必须从知识库获取，禁止用 service_name 试探仓库 |
| 代码关系图谱 | handler 定位、源码、上下游调用关系 | 仓库只填别名，禁止枚举所有仓库 |
| 可观测平台 | 错误日志、trace、前端洞见 | `today_count` 与 `today_ret_pct` 均非 0 时必须调用；时间窗口用 `error_context.date` |
| 代码托管平台 | 行级 blame、commit、代码搜索兜底 | 按需查询；失败跳过，不参与置信度计算 |

^[raw/articles/错误码排查从-38-小时到分钟级agent怎么做到的.md]

工程细节中最有迁移价值的是**调用预算标定**：代码图谱调用预算从 5 次调到 15 次——5 次容易截断调用链分析，30 次又容易超时，15 次是实测折中。检索路径同样固定：业务仓库查询 → 未命中用 `@<groupName>` 多仓库模式 → 代码托管平台代码搜索兜底，避免逐仓库盲试。这些「预算＋固定路径＋降级跳过」三件套是抑制 Agent 自由发挥的标准手法。^[raw/articles/错误码排查从-38-小时到分钟级agent怎么做到的.md]

### 3. 五步排查＋置信度模型：证据计分而非直觉判断

排查五步（补全错误码语义 → 建立业务上下文 → 定位代码与调用链 → 采集运行时证据 → 补充最近变更）不是机械串行，每步根据已有结果决定路径。语义补全要求 `gcode_meaning` 为空时至少两种方式复核（文档/代码定义/运行时日志），查不到则填 `ErrUnknown_<retcode>`；每条 evidence 标明来源（知识库命中、图谱 context、log、trace、blame），方便人工回查。^[raw/articles/错误码排查从-38-小时到分钟级agent怎么做到的.md]

置信度模型：知识库、代码定位、实际源码、运行时证据各计 1 分，3～4 分 high、2 分 medium、0～1 分 low；错误码含义无法补全时封顶 medium。两条计分哲学值得注意：代码托管变更信息**不计分**（知道谁改了代码推不出根因），可观测日志/trace 参与评分（验证运行时）；分级直接驱动人机协作——high「建议采纳」、medium「参考需确认」、low 仅归档，P0/P1 例外推送。线上近一个月 high 置信度占比约 90%，失败率约 1%（主因工作流 API 限频）。^[raw/articles/错误码排查从-38-小时到分钟级agent怎么做到的.md]

### 4. 交叉验证原则：「代码怎么写 ≠ 现场怎么跑」

静态代码说 A 调用 B，只有结合 trace 才能区分是 A 内部多次串行调用累积超时，还是请求到达 B 后由 B 报错——两种情况责任点和修复动作完全不同。文章的 Redis 超时案例即此：trace 显示 Redis 单次调用不慢，是 handler 内部多次串行调用累积超时，v3 误判为 `handle_cloud_resource`，v4 修正为 `fix_code`/`fix_config`。前后端也需相互验证：后端错误查前端调用方式与错误处理，前端错误核对后端返回结构；前端源码没获取到就明确说明，不能凭后端代码推断；入口函数委托错误处理时要继续追查，不能停在入口。^[raw/articles/错误码排查从-38-小时到分钟级agent怎么做到的.md]

### 5. 稳定输出工程：双路径解析＋输出契约各管一端

11 节点工作流用条件分支处理无效输入、正常解析、解析失败三种情况。Agent 输出可能含 Markdown 代码块、前后说明或缺失字段，不能只靠一次 `json.loads`：**快路径**四层容错（直接解析 → 提取代码块 → 找最后一个对象边界 → 遍历对象起点），任一成功即输出；**慢路径**由 LLM 修复格式并独立提取 9 个字段，非空输入却全默认值时最多重试 3 次。关键设计是**字段独立**：`code_location` 为空不能连带清空已有的 confidence 和 analysis_summary。^[raw/articles/错误码排查从-38-小时到分钟级agent怎么做到的.md]

输出契约与解析兜底配合：一个真实 case 因 Markdown 管道符写成 `\|` 触发 JSON `Invalid \escape`，四层解析全部失败。因此 Skill 明确管道符直接写 `|`、反引号不转义、代码块带语言标签，并在输出前执行 17 项检查（JSON 6 项、Markdown 4 项、字段完整性 7 项）。三个平台级坑：分支输出变量要统一（N4 的 extract_result 需 N4-true 透传为 result）；新增字段要同步三处（LLM 提取字段、Python 形参、节点参数映射）；批处理要考虑平台限频（分钟级/日级配额，脚本需限频感知与重试）。「工作流的坑不一定在代码里，也可能在节点配置里。」^[raw/articles/错误码排查从-38-小时到分钟级agent怎么做到的.md]

### 6. Skill 迭代方法论：对比驱动、案例驱动、规则显式化

5 轮 Prompt 调优的核心不是堆规则，而是判定顺序与边界的显式化。**先排除再判断**：v3 把「加白条件」与「不能加白场景」并列陈述，Agent 倾向先匹配更宽松的加白条件；v4 改为显式三步——先检查禁止加白场景、全部排除后再判断加白条件、最后区分 whitelist 与 whitelist_and_refine。限流类错误优先判 rate_limit_internal/external（30110013 案例：即使 code_type=exception 也不能跳过限流判断）；兜底通用码先 fix_code 细化；超时优先排查代码和配置。**修复建议有边界**：只修改实际触发问题的入口、优先复用已有集中处理表或中间件、新增错误码/抽象层前先评估 ROI；多因场景 action_type 选最快止血动作，其余优化放 steps。^[raw/articles/错误码排查从-38-小时到分钟级agent怎么做到的.md]

评测闭环三层机制：**版本对比**（request_id 对齐 v3/v4 生成迁移矩阵，不只看总一致率）、**回归 case 固化**（保留 6 条 v3 优于 v4 的 case：2 空壳、2 违规加白、2 判断分歧，防基线漂移）、**badcase 反哺 Skill**（具体失败抽象为通用约束：未查运行时证据不得锁定根因、混合多类故障的兜底码不得加白、工具空返回后不得碰运气、不得只搜支持性证据）。评测五维度：最终结果、过程完整性、工具可靠性、证据与边界、效率与稳定性——只看最终答案无法区分「有证据地判断正确」和「碰巧说对」。没有回归评测，Skill 会从「越来越准」变成「越来越厚、越来越慢」。^[raw/articles/错误码排查从-38-小时到分钟级agent怎么做到的.md]

### 7. 可迁移边界

文章明确区分可迁移与不可照搬：可迁移的是**方法**——业务语义、静态代码、运行时证据交叉验证＋工作流承接结构化输出＋badcase/回归评测迭代；不可照搬的是**具体规则**——错误码语义补全方式、action_type 枚举、置信度计分需按业务调整。当前局限：前端错误处理链路追查待深化，15 次图谱调用预算对复杂场景的覆盖待观察；二期计划多错误码批量处理。50 条 case 同时用于调优与回归，不代表对新错误码的泛化效果——这是作者自己标注的评测局限。^[raw/articles/错误码排查从-38-小时到分钟级agent怎么做到的.md]
