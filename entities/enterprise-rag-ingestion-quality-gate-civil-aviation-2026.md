# 企业级 RAG 入库质量门禁：民航规章手册知识库实战

AWS China Blog 记录的一套企业级 RAG 知识库交付案例：为某民航企业信息技术部门（管理数百份多级别规章手册，从公司级《信息安全管理手册》到部门级《运维操作规范》）构建带**入库质量门禁（Quality Gate）**的知识库系统。案例的价值不在于用了哪些云服务，而在于它把「RAG 的可信度」当成一个**入库阶段**而不是**问答阶段**的问题来解决——这是把 RAG 从「能答」推到「敢信」的架构转折点。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

## 问题定义：标准 RAG 只管「存」不管「质」

原系统是 OA 关键词搜索，现场调研梳理出四个痛点：语义缺失（"数据备份要求"搜不到"备份策略"）、深层信息不可及（知识埋在正文表格第三列，关键词搜索无法触达）、多版本混淆（同一手册 v18 与 v22 同时在 OA 流通，员工无法判断哪份生效）、跨文档矛盾积累（二级手册改了安全策略，三级手册仍引用旧版，无人追踪）。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

原型验证阶段暴露出一个更根本的问题：**标准 RAG 只管「存」不管「质」**——文档进来就切块、向量化、写库，既不关心新内容与已有内容是否矛盾，也不追踪版本间到底改了什么。对合规要求极高的行业，这个缺口是致命的：知识库里有矛盾比没有知识库更危险，因为员工会默认信任系统的回答。这个判断是整套系统设计的分水岭，也是本案例相对通用 RAG 教程的核心增量。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

## 系统架构：四模块解耦

系统串联「文档解析 → 入库预审核 → RAG 问答 → 冲突标注」全链路，四个核心模块与 Python 包接口如下。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

| 模块 | 职责 | 解决的问题 |
|---|---|---|
| `doc_parser` | PDF/Word → 带章节定位的结构化段落与表格，`parse_backend=auto` 按文档特征自动选后端 | 深层信息不可检索 |
| `version_diff` | 同名文档新旧版本的语义配对 + 字级 diff + LLM 过滤 | 人工逐页比对费时且易遗漏 |
| `rag_server` | 预审核任务编排、跨文档一致性检测、版本对比报告、语义检索、多轮对话、实时冲突标注、原型 Web UI | 跨文档矛盾无人发现 + 自然语言查询 |
| `llm_chat` | 多后端适配（Bedrock Converse / OpenAI-compatible）、重试、会话管理 | 统一 LLM 接入层 |

接入方式有两种：作为独立知识库平台整体部署，替代企业现有文档管理系统；或把核心模块（版本差异引擎、入库预审核）单独抽出，作为增强组件接入已有 RAG 系统——各模块通过标准 Python 包接口调用，不要求替换现有架构。这种「可整体、可插拔」的交付形态，是模块化设计落到企业存量系统上的关键取舍。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

版本管理策略：同一逻辑文档在知识库中**仅保留一份 active 版本参与 RAG 检索**；新版本入库并确认后旧版本自动标记 inactive——仍可查看和溯源，但不再出现在问答检索结果中。这从根上避免了「新旧版本同时被检索到导致矛盾回答」。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

## 关键设计一：入库质量门禁（Quality Gate）

每次新文档上传时，系统对库中每份已有文档逐一比较，按整体相似度自动分流到两种比较模式：先用 Embedding 快速算出新文档与库中每份文档的整体相似度并降序排列；同名文档**或**相似度 ≥ 阈值（默认 **0.85**）判定为「疑似版本更新」，执行版本对比（章节对齐 + 字级 diff）；其余文档执行跨文档一致性检测（语义配对 + LLM 矛盾判定）；结果渐进式推送至前端，最相关的文档优先呈现。核心分流逻辑只有一行：`is_version = same_filename or similarity >= version_threshold`。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

这个设计的精髓在于**用同一个相似度信号同时解决两类问题**——高相似度归为「版本演化」（需要 diff），低相似度归为「跨文档语义冲突」（需要矛盾判定）。它把「入库该做什么检查」变成了一个由向量空间距离驱动的自动路由，而非人工选择检查项。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

## 关键设计二：版本对比引擎

版本对比模式执行全量 diff，四步流水：章节号对齐（按层级编号如 §10.4.2.3 将新旧段落一一配对）→ 字级 Diff（对配对段落计算精确增删改）→ 表格 Diff（跨页表格先按表头相似度配对，再逐行逐列比较）→ LLM 过滤（剔除纯格式、纯编号类噪音，保留有业务意义的变更）。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

实测样例：旧版 §10.4.2.3「若 UPS 电量消耗较快时，可关闭非关键设备」→ 新版「若预计的恢复时间较长，或 UPS 电量消耗较快时，可关闭非关键设备（如非必要运行的服务器、机房测试设备等），确保重要设备正常供电（如核心交换机、防火墙、各专线路由器以及重要系统的服务器等）」，系统判定为 **substantive**（实质性变更：新增触发条件 + 补充设备清单）。这一步的产物可直接作为《手册修订说明及内容对比清单》初稿——过去人工逐页比对需 3-5 小时/份，现在机器生成 <30 秒。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

## 关键设计三：跨文档一致性检测（两级成本策略）

对相似度较低的文档对，系统把新文档的每个段落与该文档做**段落级语义配对**：先用 Embedding 找出「说的是同一件事但表述不同」的段落对，再交由 LLM 判断属于真正矛盾还是仅措辞差异。API 形态为 `DiffEngine(config={embedding: bge-small-zh-v1.5, llm: GLM-4.7-Flash, diff: {similarity_threshold: 0.80}})` + `engine.pre_review(file)`，返回 `is_safe` 与 `inconsistencies` 列表。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

为控制 LLM 调用成本，采用**规则预过滤 + LLM 判定**两级策略：规则层用正则识别明显的非实质性差异（日期/版本号变化、章节编号重排、修订记录表行）直接放行，跨文档场景另设 `CrossNoiseFilter` 处理层级称谓差异、同义表述等天然非矛盾差异；仅对规则无法确定的候选对调用 LLM，输出分类标签 `inconsistency`（真矛盾）/ `substantive`（实质变更）/ `refinement`（合理细化）/ `metadata`（元数据变动）。实测规则层过滤了 **30%~50%** 的候选对，显著降低推理开销。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

一致性检查的有效性同样有实例佐证：二级手册 §2.3.10.1「考核 80 分以上为合格，补考不及格者不得参加岗位工作」vs 三级手册 §3.7.5.2「考核 80 分合格…可在 1 个月内申请补考一次」，系统判定为 **refinement**（合理细化）——三级手册增加了补考时间窗口约束，未违反上级的 80 分合格线。这说明 LLM 判定的价值不只是「找出矛盾」，更在于**区分真矛盾与规范层级内的合法细化**，避免把正常的下级细化误报成合规风险。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

预审核完成后自动生成结构化审核报告（`review_report` 模块），包含矛盾清单、版本差异摘要、变更分类统计，可直接导出供管理员审阅；管理员确认无误后文档才正式入库。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

## 关键设计四：带冲突标注的 RAG 问答

质量门禁管住了增量入库，但库中已有的历史文档之间可能仍存在遗留冲突（管理员评估后选择放行的情况）。因此系统在问答环节加入**实时冲突检测**：当检索到的段落来自不同文档且存在矛盾描述时，答案中明确标注冲突来源，而不是任选一方或给出模糊回答。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

问答流程四步：语义检索 top-K 相关段落 → 对检索结果做跨文档冲突检测（**Jaccard 2-gram 相似度门控 + LLM 确认**）→ 拼接 context + 冲突提示交 LLM 生成答案 → 返回「答案 + 来源引用 [1][2] + 冲突标记」。检索层（`retriever`）与问答层（`qa_engine`）分离，便于替换检索后端（如本地 FAISS → OpenSearch Serverless）而不影响问答逻辑。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

表格数据采用**双粒度入库**：`table`（保留完整 Markdown 表格，作为上下文与审计证据）+ `table_row`（每行转成「列名=值」的结构化文本，用于精确命中设备、阈值与角色）。例如问「负载均衡器是什么型号」时，行级块比整张资产表更容易召回目标设备，而生成答案时仍可附带整表、文档与页码来源。这是「检索粒度 ≠ 呈现粒度」的一个具体落法。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

## 文档解析工程：中文公文手册的排版陷阱

项目第一个要解决的问题是把 PDF 手册转为机器可理解的结构化数据，而通用解析库在民航管理手册的排版上集体失效，四类特征与后果如下。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

| 排版特征 | 具体表现 | 造成的问题 |
|---|---|---|
| 左侧编号列 | 章节编号（1.1、1.1.2）独立排在最左侧，正文居右 | 按坐标聚行时编号与正文错位拼接 |
| 跨页表格 | 一张表跨 2-3 页，续页重复表头 | 被拆成多个独立表格，整体性丢失 |
| 页眉页脚 | 每页底部的修订日期、文件编号、页码 | 与正文仅差几个像素，容易混入 |
| 空白模板 | 签到表、申请单等无实质内容的表格 | 入库后产生噪音，干扰检索 |

`doc_parser` 采用多后端可切换设计，默认 `parse_backend=auto` 按文档特征自动路由：PyMuPDF（快、依赖少，适合数字文本 PDF）、pdfplumber（精细坐标控制，适合有无边框表格的文档）、Docling/MinerU（深度表格解析，适合扫描件或复杂版式）。设计原则是**通用规则 + 统计自适应优先，配置项兜底**：章节正则覆盖 `1.1.2`、`第六章`、`（一）` 等常见中文公文编号格式；页眉页脚通过出现频率统计自动识别（重复出现在 **30% 以上**页面的行自动剔除）；空白模板表格按空单元格率自动过滤。绝大多数规范类企业文档零配置即可解析，`margin_number_x` 这类坐标配置只服务极端排版。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

## 部署与选型

Embedding 采用 **fastembed（ONNX Runtime）+ BAAI/bge-small-zh-v1.5**，无 torch 依赖，纯 CPU 即可跑完文档解析、向量化与预审核全流程，无需 GPU 即可完成入库侧全部功能验证；需要加速时可上 g4dn/T4。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

问答环节需要 LLM 推理，部署方式取决于区域：海外区域直接调 Amazon Bedrock，无需自备 GPU；**中国区域 Bedrock 不可用**，需在 GPU 实例（如 EC2 g5/A10G）上自建推理服务（llama.cpp + GLM-4.7-Flash）。海外方案为 ECS Fargate + ALB / Bedrock / OpenSearch Serverless / S3 / Aurora PostgreSQL / DynamoDB / Cognito；中国区方案以 EC2 g5.2xlarge 自建 LLM、OpenSearch Service k-NN、Secrets Manager + KMS、Keycloak 替换 Cognito。总体组合是「自定义质量门禁 + 托管基础设施」——自定义 Worker 负责解析、差异识别与人工审核状态，通过审核的内容再写入向量库。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

## 实测效果与可迁移结论

客户团队试用反馈的效率对比：版本对比从人工逐页 3-5 小时/份降到自动生成差异清单 <30 秒；跨文档矛盾从「用户问到时才暴露」变为「入库时主动拦截」；知识库问答从关键词搜索自行翻阅原文变为自然语言提问并附来源引用；合规审计从手写修订说明（易遗漏）变为机器生成检测报告，可直接作为审计证据。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

可迁移到任何企业知识库场景的四条结论：一是**质量门禁应建在入库环节**，用相似度分流把「版本演化」与「跨文档冲突」两类检查自动化，而不是等用户问到才暴露矛盾；二是**规则预过滤 + LLM 判定两级降本**（实测规则层挡掉 30%~50% 候选对），让 LLM 只处理真正需要语义判断的少数派；三是**同一逻辑文档只保留一份 active 版本参与检索**，从根上消除新旧版本互斥答案；四是**问答阶段显式标注冲突而非任选一方**——在合规场景里，暴露不确定性比给出单一自信答案更有价值。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md]

## 深度分析

### 为什么「入库质量门禁」是企业 RAG 的真正分水岭

标准 RAG 的失效模式常被误读为「检索不到」，但在规章类知识库里更常见的是「检索到了、答得很流畅、但答的是作废条款」。这类错误的破坏力不来自模型能力，而来自**用户对系统的默认信任**：关键词搜索至少会让员工翻到原文自己判断，问答式界面则把判断权收走了。门禁的真正作用不是提高准确率数字，而是把「矛盾是否存在于语料中」这个问题，从事后、被动、由用户提问触发的检查，前移成入库时、主动、每份文档必过一次的检查。

这个位移带来三个结构性变化。第一，**成本从不可预算变为可预算**：问答阶段的冲突是长尾事件，可能一年不出现，也可能同一天被十个用户撞上；入库检查则是每次上传固定跑一遍，可以压测、可以估时、可以排进变更流程。第二，**质量从「答案的属性」变成「语料的属性」**：一旦矛盾在入库时被拦截，检索与生成环节就不必再为「可能矛盾」做防御，prompt 与 rerank 的复杂度反而下降。第三，**责任可归属**：报告有清单、有分类、有确认人，出错时能回溯到「哪次入库、谁批的」，这是纯问答系统给不出的东西。

也正因如此，这套系统实质上是**穿着 RAG 外衣的记录管理系统**。文章在落地建议里要求的四条语义——文档 hash 幂等、同一文档族只有一个默认主版本、历史版本可追溯、人工审核决策可审计——没有一条与向量检索有关，全部是档案管理的经典约束。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md:339-343] 这解释了为什么通用 RAG 教程无法覆盖该场景：缺的不是检索技术，而是「权威性」的数据建模。

### 质量门禁的成本结构与误杀风险

门禁的成本不是常数，而是随库容量线性增长的：每次上传都要与库中每份文档比对一遍，Embedding 便宜（CPU 上的 bge-small 即可），昂贵的部分在「候选段落对 → LLM 判定」。规则预过滤挡掉 30%~50% 的候选对，^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md:219] 看似砍半，但剩下的一半仍随文档数增长——从数百份扩到数千份时，单次入库的 LLM 调用量会成为发布流程的实际瓶颈。因此这套架构隐含一个容量假设：语料规模中等、入库事件稀疏。超出这个假设，就得改成增量索引（只比对受影响的章节族）或异步排队，而不是调阈值。

比成本更值得警惕的是**分流器自带的假阴性**。`is_version = same_filename or similarity >= 0.85` 这一行用「文本相似」近似「文档谱系」，两者并不等价：

- 两份不同部门的文件互相抄了同一段条款、只改了一个数字，相似度极高 → 被判为版本更新、走 diff，**永远不会进入跨文档矛盾检测**。而这恰恰是最危险的一类矛盾：措辞几乎一致，员工无从分辨。
- 同一条规则被两种完全不同的措辞表述（如「补考不合格不得上岗」vs「未通过者需重新资格认定」），相似度可能低于配对门槛 → 根本不成为候选对。配对召回率构成整个一致性检测的天花板，而文章没有报告这一指标。

反向的误杀同样有代价。跨文档判定要在 inconsistency 与 refinement 之间划线，而这条线本质上是**规范效力层级的法律判断**：三级手册加一个补考时间窗口属于合法细化，加一条更严的合格线则构成冲突。把这个判断交给小参数模型，误报会消耗审核员的注意力，漏报则直接变成合规风险；更隐蔽的后果是告警疲劳——审核员连续看到几十条「疑似矛盾」后开始批量放行，门禁就退化成了仪式。

人工复核是这条链上真正稀缺的资源。报告生成是秒级的，审核却是 O(变更数) 的：机器把 3-5 小时压到 30 秒，省下的是抄写与逐页翻找，不是判断。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md:252] 因此合理的做法不是「全量同等审核」，而是按文档层级、是否涉及安全与罚则、变更分类（substantive 必审、metadata 抽审）分配人的注意力。

### 合规领域（民航规章）对 RAG 的额外约束

一般企业知识库优化的是「答对率」，规章知识库优化的是「答错时能否被追责」。三条约束由此派生，且都不能靠模型能力解决，只能靠系统设计：

1. **可审计**：审核报告不只是给人看的摘要，而是审计证据——它要能回答「这份文档入库前，系统检查了什么、结论是什么、谁确认的」。这要求报告可导出、可归档、与文档版本绑定，而不是聊天记录里的一段输出。
2. **版本可回溯**：旧版本标记 inactive 而非删除，是为了在「当时按规定执行」的争议里拿得出依据。版本状态因此是合规数据，不是缓存清理策略。
3. **冲突必须显式化**：管理员评估后放行的历史矛盾，仍会在问答时被标注出来。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md:259] 这一条最反直觉，也最关键：合规场景偏好「暴露不确定性」，而不是「给一个自信的单一答案」。冲突标注在此不是体验瑕疵，而是产品功能。

还有一层容易被忽略的差异：规章是有**效力层级**的。上级手册改了下级没改，是执行风险；下级手册比上级更严，往往是允许的细化。所以「refinement 还是 inconsistency」不是语义相似度问题，而是带层级先验的规范推理问题。稳妥的工程做法是把文档层级、发布部门、生效日期作为结构化字段喂进判定 prompt，并规定「无法判定时升级人工」，而不是让模型在二分类上自由裁量——这条边界正是责任所在。相关治理视角可参见 [[concepts/responsible-ai-governance|负责任 AI 治理体系]]。

### 这套架构的适用边界与反例

门禁的价值大致正比于三个因子的乘积：**规章层级深度 × 版本迭代频率 × 单次错误代价**。文章给出的适用行业（民航、金融监管、医疗诊疗规范、制造质量体系）恰好都在这三项上偏高。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md:347-354] 反过来看，以下场景不该照搬：

- **高频变更语料**（日更的运营手册、商品库、工单知识）：每次入库都触发全库比对，门禁从质量保障变成发布瓶颈。此时更合适的是「编译式」维护——让知识在写入时就被整合进既有条目，而不是靠事后比对发现矛盾，参见 [[entities/rag-vs-llm-wiki-enterprise-knowledge-base|RAG vs LLM Wiki 企业知识库选型]]。
- **小体量语料**（几十份以内、单一维护人）：目录与命名规范就能管住版本，建门禁的工程成本加审核开销高于收益。
- **无权威版本概念的语料**（FAQ、社区问答、营销素材）：不存在「哪份生效」的问题，只存在覆盖度与新鲜度问题，门禁检查的对象根本不存在。
- **单文档族/单来源**：跨文档一致性检测没有比较对象，只需版本 diff 一个模块即可。
- **重写式修订**（换作者、重排版、章节结构大改）：0.85 相似度会失效，同名兜底虽能救回路由，但 diff 噪音极大，人工复核量反而上升。

真正的判断标准不是「有没有矛盾」，而是「矛盾被发现得太晚会不会造成不可逆损失」。若答案是肯定的，门禁值得建；若矛盾只是让答案不够好，先把检索与切块做好更划算。

## 实践启示

1. **先做冲突盘点，再决定是否建门禁。** 抽 30~50 份真实文档，用现成 Embedding 做段落级配对，人工核对前 100 个高相似对，得到「矛盾密度 + 版本迭代频率」两个数。密度低且迭代慢的库，投入应优先给解析与检索，而不是门禁。
2. **数据模型先行：文档族、active 版本、hash 幂等、审核留痕。** 这四项是门禁的地基，且与向量库无关，可以先用关系库落地。缺少「同一逻辑文档只有一个主版本」的约束，后面所有 diff 与冲突判定都会失去参照系。^[raw/articles/为民航企业构建带入库质量门禁的-rag-知识库系统.md:339-343]
3. **阈值要校准，不要照抄 0.85。** 用历史版本对做校准集：同族文档的相似度分布下界、异族文档的上界，中间才是可用区间。同时保留「同名必走 diff」的硬规则，并对跨文档路由做抽样验证——专门找那些「措辞几乎相同但分属不同文件」的对，确认它们没被误路由。
4. **审核分级，而不是全量审核。** 按文档层级、是否涉及安全与罚则、变更分类分配人的注意力：substantive 必审、refinement 抽审、metadata 批量放行。考核指标用「审核小时数 + 漏检数」，不要用「拦截条数」——后者会奖励过度报警。
5. **把冲突写进答案契约。** 问答返回体固定包含 `sources` 与 `conflicts` 两个字段，前端必须渲染冲突提示，禁止在生成侧静默择一；被放行的历史冲突要记录决策人与理由，否则「显式化」只是 UI 装饰。
6. **建一个假阴性回归集。** 手工构造 20~30 个已知矛盾对（含改写措辞、跨层级、数值差异三类），每次调整 prompt、阈值或过滤规则后跑一遍召回。只测「拦住了多少」，永远发现不了分流器漏掉的那一类。
