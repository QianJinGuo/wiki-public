## 深度分析

### 三层上报协议：分层失败处理的架构设计

通宵运行中的种种故障最终结晶为一套"三层上报协议"，其核心思路是按失败的可修复性分层，让每层只处理自己够得着的问题：

- **第 1 层：智能体自愈**。CI 失败的输出被自动注回出错智能体的会话，由它读取错误、改代码、重新推送，最多重试 5 次后放弃。这是唯一已实现的一层（由会话 ao-11 构建）。
- **第 2 层：编排器调解**。自愈重试耗尽后上报给编排器会话——它本身也是一个 codex 实例，掌握所有活动会话的全局上下文，可以查看失败者的代码、重新审视方法或推翻思路。已设计、尚未构建。
- **第 3 层：人类介入**。编排器也束手无策时，一条消息发到作者的 Telegram（例如"ao-14 的 CI 连续失败 5 次，错误是类型不匹配"），作者在聊天中回复，响应路由回智能体。这一层正是 ao-12 正在设计的。

协议的关键设计决策是**消息格式统一**：无论从智能体到编排层还是从编排层到人类，走的是同一种格式。接入 OpenClaw 后，三层结构保留，但顶层的独立编排器被 OpenClaw 取代——OpenClaw 不再是通知侧边栏，而是上报协议中的一个对等节点，既有自主解决的能力，也有向人类移交的通道。由于人类本身就在对话里，第 3 层的上报几乎是瞬时的。

这实际上是一种务实的失败处理分层：把"可自动修复的失败"压在最低层消化，把需要全局视野的失败交给编排器，把真正需要判断力的失败留给人类——每一层的边界就是失败复杂度的升级阈值。

### 信息性失败：崩溃如何结晶为需求 backlog

这次通宵最反直觉的发现是：最坏的故障反而是最有价值的产出。几个标志性失败各自暴露了一类系统缺陷：

- **认证崩溃**：作者当天早些时候为了安全加固 gh CLI，把凭据移到独立的系统用户下，意外让 `auth.json` 对 codex 进程不可读——一个子系统的安全改进默默摧毁了另一个子系统的身份验证路径，所有新会话启动即崩。没有测试能捕获它（测试不跑在不同用户下），只有 strace 加 20 分钟排查才定位到原因。
- **集体死亡**：ao-10 到 ao-14 五个会话因为用 `exec`（后台 shell 子进程）而非 `ao spawn`（独立 tmux 会话）生成，shell 会话 600 秒超时后子进程被 SIGTERM 连带杀掉，几小时的智能体工作无任何提交留存。
- **身份重用与重复工作**：AO 顺序复用会话 ID，重生的 ao-11 带着与原来完全不同的任务，彻底打乱了"哪个会话在干什么"；ao-6 和 ao-7 则撞车修同一个 bug，因为重复检测还没被构建。

作者的处理方式值得注意：每一次失败都被记为"心理记录"→ 任务 → 智能体会话。崩溃催生了"崩溃取证"需求，exec 超时催生"会话健康监控"，ID 重用催生"会话身份绑定任务而非顺序数字"。系统通过犯下"具有启发性"的错误来改进——但这些错误之所以有启发性，前提是凌晨 2 点有个人在场观察并诠释它们。失败不会自己写成需求；是人类的注意力把失败转化为 backlog。

### 阶段 2.5 论：系统暴露失败，人类诠释，智能体执行

作者此前提出过三阶段模型（智能体作为工具 → 作为工人 → 作为自我改进系统），并断言阶段 3 是"质的不同"。18 天后他修正了这一判断：质的不同确实存在，但不是"系统变好得更快"，而是**系统开始生成自己的改进待办事项**——这是阶段 2 完全没有的现象（阶段 2 里待办事项完全由人类维护）。

但他同时坦白：需求并没有"自己写自己"。实际的分工是——**系统暴露失败，人类做诠释，智能体做执行**。五个会话默默死亡让"健康监控"的需求变得显而易见，但把它变成任务、排优先级、注回系统的是人。所以当前的形态更接近"阶段 2.5"：距离完全自主（系统检测自身失败并在无人注意的情况下自行生成修复会话）还差一层，而启用那一层的基础设施（上报协议）恰好正由需要它的同一批智能体构建。

这个修正对评估各类"自改进"宣传很有用：判断一个系统处于哪个阶段，看的不是它有没有自动写代码的循环，而是**"改进什么"这个决策由谁做出、依赖谁的注意力**。

### 可见性即安全：自改进系统的安全机制不是阻止改变

面对三层 AI（OpenClaw、AO 编排器、个体智能体）各自不同的模型、上下文和失败模式，作者的恐惧不是科幻式的失控，而是工程复杂性：层间交互产生了他无法预测的涌现行为——auth 崩溃、exec 超时、消息传递失败全都属于此类。

他的结论是对常见"AI 安全"叙事的一个有力反命题：**自改进系统的安全机制不是阻止改变，而是确保可见性**。只要能看到系统对自己做的每一次修改，就能在问题复利放大之前抓住它们；一旦失去可见性，就失去控制。而在复杂系统里，失去可见性比听起来容易得多——auth 崩溃正是"没人看见的安全改动"的直接后果。

上报协议的动机也由此而来：不是为了防止系统失控，而是因为系统*一定会*以无法预测的方式失败，所以需要一条从"什么东西坏了"到"人类知道了"的可靠路径，且这条路径本身不能以新奇的方式坏掉。

### 涌现行为的组合爆炸与测试困境

文章点出了自改进系统一个近乎无解的测试难题：可以测试单个组件，可以测试成对的交互，但**测试完整系统需要运行完整系统，而完整系统就是生产环境**。随着层间整合愈发紧密，可能的涌现行为空间呈组合式增长，任何离线测试矩阵都追不上。

这解释了为什么作者把外部操作员验证（独立 OpenClaw 实例、全新检出、token 轮换、突发流量）当作最高杠杆的测试举措，以及为什么他接受"仍有三个已知差距"（无幂等去重、同会话消息可能乱序、反向命令路径未做运行时冒烟）就发布连接器——在组合爆炸面前，务实的选择是缩小发布单元、靠可见性和快速上报兜底，而不是追求完备的测试覆盖。这也呼应了全文的核心论点：不断自我构建的系统不需要完美，需要的是透明、可观察、可调试、可引导的"混乱循环"。

## 实践启示

1. **为失败设计分层出口，而不是追求零失败。** 把"自动重试（限量）→ 编排器调解 → 人类介入"做成统一协议，让低层失败不占用人类注意力，也让真正的疑难失败必然到达能看到它的人。统一的失败消息格式让每一层都可替换。

2. **把每次生产故障显式转化为需求条目。** 崩溃取证、会话健康监控、身份绑定任务——这些功能都不是规划出来的，而是从真实失败中"结晶"的。建立"失败 → 记录 → 任务 → 会话"的固定管道，失败就变成复利而非损耗。

3. **警惕跨子系统的隐性耦合。** 一个子系统的安全加固可以默默杀死另一个子系统的认证路径，且测试抓不到。凡涉及权限、凭据、用户身份的改动，都要问一句"还有谁在读这个文件/依赖这个权限"，并保持改动可见。

4. **会话/资源的标识应绑定目的而非顺序号。** 顺序复用 ID 会在崩溃重生后制造"同名不同物"的混乱；标识符与任务绑定、配合重复任务检测，才能在大规模并行下维持对系统的认知。

5. **用可见性而非禁令来治理自改进系统。** 与其试图阻止系统修改自己，不如确保每一次修改都可观察、可回溯、有直达人类的上报通道。能在问题复利之前看见问题，比预先设计出"正确"的系统更现实。

6. **自动化打字，人类思考——诚实面对当前的自主性边界。** 战略决策（建什么、杀哪个会话、如何拆解问题）目前仍由人做出，宣称完全自治只会掩盖真实的失败模式。优势不属于拥有"干净循环"的人，而属于拥有"可观察、可调试、可引导的混乱循环"的人。
