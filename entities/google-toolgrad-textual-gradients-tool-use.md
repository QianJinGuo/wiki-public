## 深度分析

### The inversion: answer-first beats query-first by construction

The dominant dataset-generation recipe (ToolBench, ToolACE) works query-first: sample an API pool, hallucinate a plausible user instruction, then dispatch a DFS agent to search for a working tool chain. That second step is the expensive part — most exploratory trajectories fail, and the pipeline's yield is bounded by a low pass rate. ToolGrad deletes the search problem entirely: it builds a *verified* tool chain first, then asks one LLM call to write the user query that this chain answers. Because the solution is constructed rather than searched for, pass rate approaches 100% by design, and the marginal cost per valid sample collapses. The deeper insight is about information asymmetry: an explicit solution carries more unambiguous signal than a prompt, so annotating query-from-solution is a much easier task than solving query-to-solution.

### Textual gradients repurposed: from prompt optimization to workflow construction

TextGrad introduced "textual gradients" — an LLM critic's plain-text feedback steering prompt refinement. ToolGrad migrates the concept from static prompts to *executable structures*: instead of improving one text, the gradients direct the iterative assembly of API workflows. The four-module loop (API Proposer → parallel API Executors → API Selector → LLM Updater) maps cleanly onto ML's propose/test/select/update cycle, with the Selector's execution-report review serving as the directional gradient signal. The key generalization: critic-style textual feedback can optimize any artifact that has a verifiable execution trace, not just natural-language strings. This turns "optimize by critique" into a general data-engineering primitive for structured, runnable targets.

### Small-data fine-tuning that reaches proprietary SoTA

With only ~500 samples (ToolGrad-500, built on ToolBench's 16k+ APIs, generated by gemini-2.5-flash-lite), fine-tuned Gemma-3 models improve consistently at 1B/4B/12B scales. The headline result: ToolGrad-12B scores 83.1 on BFCL — a benchmark whose tool set is disjoint from the training API database (i.e., an OOD evaluation) — versus gemini-2.5-pro at 83.2, Claude 4.5 Opus at 82.8, and GPT-5 at 74.4. It also leads open tool-use specialists like ToolACE and Hammer-2.1-7B despite ToolACE's more advanced API database. The mechanism looks like verified-path curation: every training example contains a *proven-correct* chain, so the model learns from unambiguous demonstrations rather than the noise-heavy trajectories that search-based pipelines distill.

### The self-evolving twist: students surpassing their teacher

ToolGrad-500 was generated entirely by gemini-2.5-flash-lite, yet Gemma-3-12B fine-tuned on it outperforms that very teacher. This breaks the usual assumption that distillation output is capped by teacher quality. The explanation lies in the data-forming process: the textual-gradient loop filters and verifies every trajectory, so the student sees only the teacher's *successful, validated* behavior — a curated slice that can be better than the teacher's average performance. Google positions this as groundwork for continuous, on-the-fly learning and personalization, connecting ToolGrad to the broader agent self-improvement lineage where data generation itself becomes an optimization loop. ## 实践启示

1. Invert your data pipeline when solutions are verifiable. If you can check whether a tool chain (or code path, SQL query, API call sequence) is correct by executing it, generate the solution first and back-annotate the query. You replace an expensive low-yield search with a cheap high-yield construction — the pass-rate gain alone justifies the redesign.
2. Use critic feedback to build data, not just to polish prompts. Textual-gradient loops apply to any artifact with a runnable success signal: workflows, test suites, migration scripts. Treat the LLM critic + executor pair as a general-purpose factory for verified structured data.
3. Budget for ~500 verified samples before assuming you need millions. ToolGrad-500 was enough to bring a 12B open model to proprietary-SoTA parity on OOD tool-use. Verified, unambiguous small datasets beat large noisy ones — measure pass rate of your training data before scaling its volume.
4. Expect OOD transfer from API-diverse training data. Models trained on ToolBench APIs transferred to BFCL's entirely different tool set. When synthesizing training data, maximize diversity of the API/tool vocabulary rather than depth on one ecosystem.
5. Exploit verified distillation to exceed teacher quality. If your teacher pipeline filters for verified success, students fine-tuned on the output can beat the teacher itself. A cheap generator model plus a strong verification loop may outperform expensive raw generation by a stronger model.
6. Test your tool-use data on a disjoint benchmark. ToolGrad's credibility rests on BFCL being OOD with respect to ToolBench. When claiming data-quality wins, evaluate on tool inventories your generation pipeline never saw — in-distribution gains are cheap to fake.
