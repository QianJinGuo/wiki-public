# 从Vibe Coding到Harness—— 一套大仓AI工程化实战

作者：fitchzheng、leoshli^[raw/articles/从vibe-coding到harness-一套大仓ai工程化实战.md]


> 一篇属于后端微服务 + 前端微应用大仓的 Harness 实战分享。 不讲理念有多重要，只讲我们这一路是怎么搭起来、怎么撞墙、撞完怎么补的。

### 写在前面

这篇文章想聊的是一件具体的事：**怎么让 AI 在一个真实的、跨多个仓库的前后端业务工程里稳定地跑完一个需求** 。 ^[raw/articles/从vibe-coding到harness-一套大仓ai工程化实战.md]

现在大家手里都有越来越强的模型，但只要你试过让 AI 独立做完一个完整的产品需求——从产品那条 TAPD 单子开始，到方案落地、代码改完、接口跑通、CR 通过、最后 MR 提到工蜂上——你就会发现一件事：**模型够强了，工程没跟上** 。AI 一个人跑不完，因为整条链路上太多事不是"写代码"本身，而是协作、流程、信任、收口。 ^[raw/articles/从vibe-coding到harness-一套大仓ai工程化实战.md]

我们 TAB 实验平台是一个**典型的前后端业务为主的技术平台** ：拥有超过30+的微服务、10+ 个前端微应用、各平台SDK库，我们把它们集成在整个大仓做统一管理，然后用沙箱做集成验证、用TAPD 管各种需求输入、iWiki 沉淀方案、工蜂托管代码等等。在这种工程里搭建 Harness，会遇到一组很实在的一些挑战，比如： ^[raw/articles/从vibe-coding到harness-一套大仓ai工程化实战.md]

  * 你可能有时不是改一个仓库，是同时动可能跨 5 个 submodule 的代码
  * 你不仅是验证一个功能是否跑得起来，是要拉沙箱、刷 schema、起 Redis、跑真实 HTTP 接口测试，是让整个功能能够真正放心上线
  * 你不是面对一份本地用户文档，是面对 TAPD 单 + iWiki 文档 + 工蜂 MR + Knot知识库管理的四套外部输入输出系统
  * .......

我们花了一段时间把这套 Harness 慢慢搭起来。这一路上踩了不少坑、撞了不少墙、删过不少自以为正确的设计。这篇文章把这些经验完整复盘一遍，希望对正在做类似事情的同学有用。 ^[raw/articles/从vibe-coding到harness-一套大仓ai工程化实战.md]

**全文阅读约 25 分钟。**  一共 10 小节，按"先讲项目 → 再讲方法论 → 再讲撞墙 → 最后讲取舍"的顺序展开。如果时间紧，可以直接跳到第六章（门禁脚本）和第七章（Team Mode 撞墙复盘）——这两章的密度最高、踩坑最深，对其他团队可能也最有参考价值。 ^[raw/articles/从vibe-coding到harness-一套大仓ai工程化实战.md]

## 深度分析

### 从 Vibe Coding 到 Harness：大仓里真正改变的是什么

[[concepts/vibe-coding-paradigm|Vibe Coding]] 在单人小仓库里够用，是因为"写代码"本身就是交付的全部。但在 TAB 这种 30+ 微服务、10+ 前端微应用、一次改动可能横跨 5 个 submodule 的大仓里，写代码只占交付链路的一小段——改 TAPD 状态、拉沙箱刷 schema、跑真实 HTTP 接口测试、提 MR、归档方案，这些动作没人替 AI 记。文章最锋利的观察是：**卡住 AI 的四件事（改错仓、改完没人验证、交付环节碎、外部系统四套）没有一件是模型问题**，全是协作、流程、信任问题。这就把 [[concepts/harness-engineering-framework|Harness Engineering]] 的定位从"给 AI 的工具箱"扭转为"给团队的工程纪律"——SPEC-First 之所以是第一步，正是因为纪律必须先在团队层面达成共识，才能被机器执行。

### 判定权下沉：Rule、Skill、Agent 的分工逻辑

这套体系最反直觉的一层是"Rule 最后几乎没写"。原因是大仓规约绝大多数是**可判定的**（GORM 强制、覆盖率阈值、事务切面），能判定就该写成 lint 和脚本，而不是留在自然语言里给 AI 留解释空间——AI 的解释性执行（"这条规则这次场景特殊"）是脚本门禁要对抗的头号敌人。剩下三层按同一条逻辑切分：**Skill 是注意力管理而非能力增强**，把"数据访问层怎么做"这类手册从主 prompt 里拆出去按需加载；**Agent 只给认知工作分工**，4 个角色（需求/方案/开发/代码审查）的划分标准是"能写成 bash 的就别让 Agent 跑"；**Workflow 的 13 个阶段**每一段都要通过"是否有独立失败模式 + 失败回退位置是否不同"两道筛子。这其实给出了一个可迁移的工程化分层判据：约束的可判定性决定它落在哪一层，见 [[concepts/skill-engineering-principles|Skill 工程化原则]] 与 [[concepts/agentic-workflow-patterns|Agentic Workflow 模式]]。

### 反馈闭环是被弯路逼出来的：门禁、基线与前置

文章里最有方法论密度的是两段弯路复盘。其一，接口测试最早后置在验收阶段，导致最贵的代码审查环节替最便宜的几秒钟验证背锅——审查 200 行 diff 通过后接口测试才挂，全部白评；前置为硬门禁后打回次数从 1.8 降到 0.4，更重要的是把"开发完成"的定义改成了**代码 + 单测 + 验证手段**，让制造问题的人同时制造验证。其二，AI 对失败有顽强的解释能力（"历史问题""不是我引入的"），对策是开发前冻结一份门禁基线快照，验收时只对"新增失败"阻断——这是直接剥夺 AI 解释权的设计。软硬门禁的取舍同样值得记：硬门禁宁少不多，非质量红线的失败走软门禁但在审查结论、度量报告里留"伤疤"，让绕过在视觉上不舒服。这与 [[concepts/agent-role-specialization|Agent 角色分工]] 中"审查角色专责收口、下游不许改上游"的纪律互为表里。

### 基础设施角色：MCP、项目记忆与"自给自足的复杂度"

支撑层也有清晰的角色划分。**MCP 不是万能钥匙**，而是把"AI 安全地动外部系统"收敛为有明确入参、有语义、有审计痕迹的受控接口——读多写少、写操作只在初始化和交付收尾触发、写必须幂等、失败软降级，靠这四条把开发闭环扩展成交付闭环。**项目记忆**则是两层仓库内索引（代码导航地图 + 跨需求任务看板），并且刻意与个人 Memory 划界：团队共识必须落仓库可审计，Memory 只放个人偏好，否则多人并行时记忆互相矛盾。最后 Team Mode 撞墙那章给出一条对所有基础设施设计都适用的判据：一个机制若主要在解决它自己引入的副作用，八成该删——删掉 Team Mode 换成同步子 Agent 调用后，代码少了 200 多行，卡死彻底消失。YAGNI 在 Harness 设计里的权重，比多 Agent 并行的新鲜感高得多。外部接口层的细节可参见 [[concepts/model-context-protocol-mcp|MCP]]。

## 实践启示

1. **先把约束分类，再决定它落在哪一层**：能判定成 lint/脚本的规约绝不停留在自然语言 Rule 里；操作手册做成按需加载的 Skill；只有真正的认知分工才值得开 Sub Agent，确定性动作全部下沉 bash。"能写成脚本的就别让 AI 解释执行"应作为硬性设计准则。
2. **用"独立失败模式 + 不同回退位置"两问来切流程阶段**：每一段流程都要能回答"它失败的方式是否独特、失败后回到哪一棒是否不同"，两个都是才独立成阶段。同时给"信息已经充分的需求"留条件触发的快车道，不要让全员走最严路径。
3. **人工关卡按体感设计，不只按正确性设计**：关键节点（需求确认、跨仓方案确认、熔断）必须留人，但硬约束是任何用户每分钟点一次以上的交互都算设计 bug；审批入口做三级兜底（按钮/关键词/语义），任何一处卡顿都会让团队退回 Vibe Coding。
4. **先冻结基线再开发，验收只看增量失败**：开发前对全部门禁跑一次快照，交付时用差异对比阻断——把"历史问题"这把万能钥匙收走；软门禁失败不阻断但必须在审查结论和度量报告里留下显眼记录。
5. **不要一次到位，也不要为机制保留机制**：落地路径是"哪儿痛补哪儿"，先跑通开发闭环再接 MCP（写操作幂等、失败软降级、只留审计）；定期检查有没有组件只在维护它自己引入的问题——有就删，未来真需要时再加回来会更干净。
