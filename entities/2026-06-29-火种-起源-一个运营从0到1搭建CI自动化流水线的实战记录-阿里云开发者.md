## 摘要

阿里云开发者「火种&起源」系列的一线实战记录：一名高德打车区域运营同学（半年前对 CI/CD 一无所知）用 AI 辅助从 0 到 1 搭建日报自动化流水线——工作日 10:30 定时触发，从 ODPS（MaxCompute）取数、用 Qwen 大模型生成日报解读、Markdown 转 HTML 后经 Webhook 加签推送钉钉群、HTML 推回仓库 public/ 目录自动部署 Aone Pages 在线站点，从数据到阅读只需 10 分钟，替代原来每天至少 1 小时的手工取数、Excel 整理、写解读、排版发群的流程。数据准确性由 SQL 保证（0 幻觉），AI 只负责自然语言解读 ^[raw/articles/2026-06-29-火种-起源-一个运营从0到1搭建CI自动化流水线的实战记录-阿里云开发者.md]

架构上拆成两条独立流水线：daily-report-auto（python:3.11 镜像，生成日报）与 deploy-pages（alios-8u 镜像，push public/ 实时触发 + 每天 17:00 定时兜底），原因是 Aone CI 的 uses: 组件运行在完全隔离容器中、无法补装 jq 等工具。针对多人协作 HTML 全量替换互相覆盖的问题，方案是每次部署前动态发现所有远程分支、逐一合并各分支 public/ 内容、当前触发分支最后覆盖。文章沉淀了 10 个真实踩坑：triggers 复数、Secrets/Variables 语法混用取空、内网 git push 403、schedule 只从 master 读取、cron 按北京时间解释差 8 小时、[skip ci] 杀全局（应改用 paths 过滤）等 ^[raw/articles/2026-06-29-火种-起源-一个运营从0到1搭建CI自动化流水线的实战记录-阿里云开发者.md]

## 关键要点

- 日报流水线 7 步：DataClaw API 抓取 → ODPS SQL（5 个模块专属 SQL）→ Qwen 生成日报 → Markdown 转 HTML → 钉钉 Webhook 推送 → git push 留档 → 触发 deploy-pages 部署。
- 核心矛盾解法：deploy-pages 每次部署是全量替换，多人各自分支生成 HTML 会互相覆盖；部署前用 git fetch + checkout 逐一合并所有远程分支的 public/，触发分支内容最后覆盖。
- 关键安全实践：PAT 不能明文写 YAML，配置为 Secrets（${{ secrets.X }}）；ODPS 用团队公共 AccessKey，避免个人 AK 泄露、人员变动无需换凭证、新人零配置。
- Aone CI 平台特性：schedule 调度器只从 master 分支读取配置；cron 按北京时间 CST 解释而非 UTC；Aone CI 没有 $CI_COMMIT_BRANCH 内置变量（用 git rev-parse --abbrev-ref HEAD 代替）。
- 调试心法：不要从零写 YAML，先复制仓库里跑通的流水线再改；把完整报错日志复制给 AI 协助定位，配置效率取决于定位问题速度而非记住多少语法。
