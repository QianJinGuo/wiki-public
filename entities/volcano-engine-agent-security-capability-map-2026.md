# 火山引擎《智能体安全能力图谱》——企业智能体安全治理框架

> 火山引擎基于字节内部 AI 安全治理最佳实践，发布《智能体安全能力图谱》，系统性梳理了智能体安全建设的 **10 大能力维度、60 项核心技术要素**，覆盖 WorkFlow 类智能体、办公类智能体、AI Coding 类智能体，并提供 L1→L2→L3 三阶段可落地的建设路径（从"基础防护"走向"体系化治理"到"可持续运营"）。^[raw/articles/volcano-engine-agent-security-capability-map-2026.md]

## 背景与问题

企业智能体部署已进入规模化落地阶段，多元化、异构化的智能体深度融入企业核心生产业务系统与办公开发场景，在重塑企业 IT 架构的同时导致安全风险激增，对传统安全防护体系带来极大冲击。企业需要重新思考并构建适配 AI 时代的安全防护和治理体系框架。^[raw/articles/volcano-engine-agent-security-capability-map-2026.md]

## 10 大能力维度（60 项核心技术要素）

- **1. 智能体合规准入**：设计及规划阶段安全介入，基于岗位职责、行为权限、使用场景做分类分级，构建安全基准线 + 可嵌入的安全描述文件，为后续管控做准入准备
- **2. 智能体资产与供应链安全**：构建智能体及核心组件清单（AI-BOM），细粒度盘点资产，定期供应链风险巡检
- **3. 内容安全合规**：输入输出内容安全检测，实时拦截有害内容，行业红线敏感话题管控，AI 生成内容深度鉴伪打标签
- **4. 常态化安全测评与加固**：合规测评 + 红队测评实现安全左移，构建上线准入要求与整改加固建议
- **5. AI 安全网关**：统一接入、敏感数据识别与脱敏、数据跨境管控、模型路由、资源耗尽防护、成本治理，降低算力消耗同时实现出入口全面防护
- **6. 身份与认证管理**：非人类身份体系 + 可信身份令牌 + 委托链与意图声明做全链路身份传播，凭据托管避免敏感凭据写入工具代码
- **7. 权限与访问控制**：用户/智能体为主体、知识库/技能工具为客体，运行态对用户→总控智能体→子智能体→工具的委托链逐节点权限控制，动态权限 + 高风险行为阻断或强制 HITL
- **8. 运行时安全监控与防护**：全链路检测，针对工具滥用、越权、记忆投毒、注入攻击提供实时拦截，支持自定义场景策略
- **9. 安全可观测性与运营管理**：全量日志记录、行为审计、事件分析、自动化处置；建立智能体 UEBA / AEBA 基准实现动态化场景运营
- **10. 模型与推理安全**：机密计算防护（芯片级信任 + 端到端全链路加密 + 远程证明 + 可追溯审计），轻量化投入实现等同私有化部署的高等级防护

## L1→L2→L3 三阶段建设路径

- **L1 智能体基础安全 AI 防护**：先解决"能否安全上线"。覆盖维度 1-4（合规准入、资产供应链、内容安全、安全测评）。目标是为每个进入企业的智能体建立统一、可执行的安全基线。^[raw/articles/volcano-engine-agent-security-capability-map-2026.md]
- **L2 智能体精细化管控**：再解决"运行过程是否可控"。覆盖维度 5-8（AI 安全网关、身份认证、权限控制、运行时监控）。围绕统一入口、可信身份、细粒度授权与运行时拦截，建立覆盖每一次调用和执行的控制体系。^[raw/articles/volcano-engine-agent-security-capability-map-2026.md]
- **L3 智能体安全持续运营**：最终解决"规模化后能否持续运营机密可信"。覆盖维度 9-10（可观测性运营、模型推理安全）。让企业不仅全面发现处置风险，还能基于全链路数据持续验证安全状态、优化策略，并做到模型推理的机密可信。^[raw/articles/volcano-engine-agent-security-capability-map-2026.md]

## 与既有智能体安全框架的关系

该图谱与 wiki 中既有的智能体安全框架互补：[[entities/agent-security-three-step-sequence-harness-governance-identity-crewai|三步序列框架（治理/身份）]] 侧重治理与身份的时序编排，本图谱则以 10 大能力维度 + 三阶段成熟度模型给出企业级全景能力清单；[[concepts/agent-security-architecture|智能体安全架构]] 从架构视角组织防御面，本图谱则以能力建设路径（L1/L2/L3）组织落地顺序。AI 安全网关作为独立能力维度，与 [[entities/ai-gateways-vs-mcp-gateways-what-security-teams-need-to-know|AI 网关 vs MCP 网关]] 的判别互补。

## 深度分析

### 10 大维度的重心：安全从"代码"转向"身份、权限与行为"

把 10 个维度拆开看，会发现图谱的重心与传统应用安全明显错位：传统 AppSec 的核心对象是代码与接口（漏洞扫描、渗透测试、WAF），而这份图谱里真正的"重资产"维度是身份（6）、权限（7）、运行时行为监控（8）和安全可观测性（9）——四个维度合计占了 L2/L3 的绝大部分篇幅。工具调用取代了 HTTP 请求成为核心管控单元：委托链（用户→总控智能体→子智能体→工具）逐节点鉴权、高风险行为阻断或强制 HITL，本质上是在为一个"会自主发起动作的非人类主体"重建访问控制模型。相比之下，传统强项如内容安全（3）和测评加固（4）被压缩为前置准入环节。这说明在智能体安全里，攻击面的重心已从"注入到进程"迁移到"诱导到决策"——提示注入、记忆投毒、工具滥用都是对决策链路的攻击，而非对代码的攻击。这与 [[concepts/agent-security-threat-models|智能体安全威胁模型]] 中以意图与行动为中心的威胁分类相互印证。

### L1→L2→L3：成熟度路径背后的组织假设

三阶段路径不只是技术分期，更暗含了对组织成熟度的三个假设。L1（维度 1-4）假设组织还没有统一的智能体台账，第一步是"知道自己有什么"——合规准入 + AI-BOM 资产盘点 + 上线测评，本质是治理动作而非技术动作，需要安全团队拿到"准入否决权"才可执行。L2（维度 5-8）假设组织已经有一个能被所有智能体流量经过的统一入口，AI 安全网关、统一身份、运行态拦截都要求智能体接入方式标准化——这背后是平台工程的投入，安全建设实际是搭平台建设的便车。L3（维度 9-10）假设企业已积累全链路行为数据，才能做 UEBA/AEBA 基线和基于数据的持续策略优化，同时机密计算（芯片级信任 + 远程证明）是高投入选项，只有规模化的企业才摊得平成本。由此看，跳级是不可行的：没有 L1 的资产清单，L2 的网关不知道该拦谁；没有 L2 的全链路日志，L3 的行为基线无从建立。

### 与 wiki 中其他智能体安全框架的对照

wiki 中尚无 OWASP Agentic AI 专项条目，可比对的框架有三类。与 [[entities/agent-security-three-step-sequence-harness-governance-identity-crewai|三步序列框架（治理/身份）]] 相比：三步框架回答"先做什么后做什么"（治理 → 身份 → 运行时），本图谱回答"总共要做全哪些"；二者正交，三步序列可作为 L1→L2 的执行顺序参考。与 [[entities/anthropics-zero-trust-for-ai-agents-sets-the-right-test-the|Anthropic 的零信任测试框架]] 相比：零信任框架给出的是"验证式"心智模型——每个动作都不可信直至验证，本图谱给出的是"建设式"能力清单，前者是设计原则，后者是工程目录。与 [[entities/youre-building-agent-security-in-the-wrong-order|反序建设观点]] 的争议点在于：该文主张身份与权限应最先建设，而图谱把合规准入与资产盘点放在 L1、身份放 L2——这个分歧更适合解读为"绿地企业"与"已有大量存量智能体企业"的起点差异。

### 图谱的盲区：供应链纵深、多智能体与跨组织信任

维度 2 虽然覆盖了 AI-BOM 与供应链巡检，但基本停留在"清单 + 巡检"层面，未触及三类更深的问题：一是技能/Skill 与 MCP 工具市场的第三方投毒（恶意 Skill 诱导越权），这恰是 2026 年多起真实攻击的入口；二是多智能体系统内部的风险传播——子智能体被攻陷后沿委托链横向移动，图谱的逐节点权限控制是对的方向，但缺少对 [[concepts/multi-agent-systems|多智能体系统]] 中编排器自身成为单点失陷面的讨论；三是跨组织信任：企业 A 的智能体调用企业 B 的 MCP 服务或 SaaS 工具时，身份联合、责任划分、数据出境（维度 5 提及跨境管控但仅从数据侧）均无对应能力要素。此外，图谱以单企业视角展开，对开源社区披露的智能体漏洞如何进入企业补丁周期（传统 CVE 流程不覆盖 Skill/Prompt 资产）也没有给出答案——这些缺口大概率要靠 [[concepts/ai-security-landscape|AI 安全全景]] 中的社区标准化工作补齐。

## 实践启示

1. **先建台账再谈防护**：没有 AI-BOM 级别的智能体清单（谁建的、什么权限、碰哪些数据），任何网关和监控都是无的放矢。L1 的资产盘点是后续一切能力的索引，应作为立项第一交付物。
2. **把安全准入挂进研发流程而非事后审批**：维度 1、4 的"安全左移"意味着智能体立项时就要有安全描述文件和分类分级，等上线再补做合规的成本远高于设计期介入；建议将安全基准线纳入智能体的上线 CI 门禁。
3. **身份体系按"非人类员工"设计而非"API Key"设计**：委托链 + 意图声明 + 凭据托管三件套是图谱给出的最小集；关键是让每一个工具调用都能回答"替哪个用户、出于什么意图、经过谁授权"，凭据绝不下沉到工具代码。
4. **统一网关的卡位比功能重要**：L2 的前提是所有智能体流量可被路由和观测。若企业内已有多个团队各自直连模型 API，先解决接入标准化（哪怕功能简陋），再迭代脱敏、限流与成本治理——网关的议价能力来自覆盖率而非特性数。
5. **高风险动作用 HITL 兜底而非追求全自动拦截**：运行时防护（维度 8）在误报与漏报间摇摆，对企业场景，"删除数据、对外发送、支付类工具调用默认强制人工确认"是比智能拦截更稳的第一版策略。
6. **对图谱盲区自补三道防线**：Skill/MCP 供应链扫描（上线前 + 定期）、多智能体委托链的横向隔离演练（红队视角）、以及跨组织调用时的最小数据暴露与审计留存——这三项图谱未细化，但都是可预见的攻击路径。
