# 97.9%采纳率，胶水编程：业务需求出码最佳实践【天猫AI Coding实践系列】

**来源**: 大淘宝技术
**发布日期**: 2026-03-27
**原文链接**: https://mp.weixin.qq.com/s/G3aKbzdGUyD2h1aVjvbr2g
## 摘要

天猫品牌行业前端团队在半年内把一个全栈化试点业务域的 AI 代码采纳率从约 50% 提升到 90%+（峰值 97.9%），核心变量不是模型升级，而是一套名为"胶水编程"（Glue Coding）的物料体系：别让 AI 写代码，让它抄代码。SPEC 管意图、物料管执行，四层物料（开发规范、代码模式、领域知识、任务规格）分层注入 Agent，让 AI 只在业务差异点写 10% 的"胶水代码"^[raw/articles/979采纳率胶水编程业务需求出码最佳实践天猫ai-coding实践系列.md]。这套实践最有价值的结论是：AI 编码的质量上限取决于你喂给它什么，而非模型本身有多强。

## 核心要点

- **核心哲学：别让 AI 写代码，让它抄代码**。中后台业务 90% 的代码本有现成参照（列表页、表单页、详情页高度模板化），让 AI 从零"创作"既浪费又不可控——能抄不写，能连不造，能复用不原创。
- **技术直觉：顺应 LLM 的能力结构而非对抗它**。大语言模型的训练目标是根据已有信息预测下一个 token，因此在有参照物时表现显著优于无参照物时——给它一份样板代码，它能精准拟合出风格一致的新实现。
- **可控性阶梯**：Vibe Coding 解决"能不能用 AI 写代码"，SPEC Coding 解决"写的对不对"，Glue Coding 解决"写的是不是你们的"——三者递进，企业中后台要的恰恰是最后一步。
- **四层物料堵四种独立失败模式**：任务规格（做什么）、开发规范（什么不能做）、代码模式（代码长什么样）、领域知识（有什么要注意的）——四个决策彼此独立，答对一个不保证其他三个对，少一层就多一种漏洞。
- **97.9% 的口径很严格**：以周期内所有 CR 合并上线的代码总行数为分母、AI 生成行为分子，按行级加权统计，不按迭代平均——避免了大小迭代失真，不是单次实验的最佳值。
- **从 50% 到 90%+ 的每一步都对应一次物料补全**：~50%（只有知识库）→ ~76%（AGENTS.md 云端下发 + 知识库数据运营）→ 90%+（四层物料齐备），提升来自纪律而非更好的 prompt。
- **90% 抄，10% 写，胶水只在缝隙处**：Agent 从样板间组装骨架、按规范守底线、检索知识避坑，只在 SKU 阶梯价格表、状态流转等真正的业务差异点写新代码。
- **主力用户是近两百名后端工程师**，不是前端——没有样板间可抄他们写不出符合团队规范的前端代码，这反过来证明物料的必要性。

## 深度分析

### 假设转变：从"作者"到"装配工"

传统 AI 编码的隐含假设是把 AI 当作**作者**——给它足够好的需求描述，它就能写出好代码，于是投资都流向 prompt 工程和等待更强的模型。胶水编程的假设是把 AI 当作**装配工**：它不应该"写"代码，而应该"抄+改"代码，于是投资流向内部物料体系和需求规格的持久化管理^[raw/articles/979采纳率胶水编程业务需求出码最佳实践天猫ai-coding实践系列.md]。

这个转变引出一个反直觉的质量标准：**在可标准化的部分，原创越少越好**。好的 AI 编码不是"生成了多少代码"，而是"原创了多少代码"——原创比例高说明物料体系有缺口。团队资产观随之改变：已有项目代码是可复用的"样板间"资产，已完成的需求规格是后续需求的决策上下文，每次交付都在积累物料，形成复利效应^[raw/articles/979采纳率胶水编程业务需求出码最佳实践天猫ai-coding实践系列.md]。

文章还回应了一个长期主义顾虑：任何为模型行为搭的工程脚手架（如 AGENTS.md 静态注入）都有隐形的保质期，可能被下一代模型原生能力取代。但胶水编程押注的不是脚手架而是知识资产——加载机制会过时，团队的代码模式、领域知识、开发规范不会。模型会换代，脚手架会扔掉，团队知识只会越积越厚^[raw/articles/979采纳率胶水编程业务需求出码最佳实践天猫ai-coding实践系列.md]。

### 四层物料的分层注入：用最少 token 传递最高密度信号

四层物料按加载方式分为两类，对应 LLM 上下文工程的关键权衡^[raw/articles/979采纳率胶水编程业务需求出码最佳实践天猫ai-coding实践系列.md]：

| 物料层 | 加载方式 | 机制 | 时机 |
|--------|----------|------|------|
| 开发规范 | 静态注入 | 云端配置 → 自动生成 AGENTS.md → system prompt | 打开仓库自动加载 |
| 代码模式 | 静态注入 | 样板间代码文件经提示词引用注入 | 打开仓库自动加载 |
| 领域知识 | 动态检索 | Agent 通过 MCP 调用 knowledge Server | 编码中按需触发 |
| 任务规格 | 动态生成 | SPEC 模板 → spec.md 初始上下文 | 每次需求启动时 |

开发规范必须静态加载的理由有硬数据支撑：Vercel 评测显示 56% 的场景中 AI 根本不会主动调用文档工具，同样的内容写入 AGENTS.md 后通过率从 53% 升到 100%——关键规则不能依赖 AI 的主动调用。而不把所有物料一股脑塞进去的理由来自 Anthropic 与 Chroma 的研究：一个精准的 300 token 上下文往往胜过混杂的 113,000 token 上下文，且上下文越长安全特性实现反而下降 47%^[raw/articles/979采纳率胶水编程业务需求出码最佳实践天猫ai-coding实践系列.md]。

领域知识层尤其值得注意其构成：**内部组件物料文档占日常消费的 60-70%**，踩坑经验只占 20-30%——Agent 最频繁的需求不是"有什么坑"，而是"这个私有组件怎么用"。判断标准很简单：模型能从公开资料获取的不入库。团队还用"调用率 × 采纳率"四象限清理低效条目，把知识库关联采纳率从 18% 翻倍到 35%，印证"物料的价值不在数量，在精准度"^[raw/articles/979采纳率胶水编程业务需求出码最佳实践天猫ai-coding实践系列.md]。

### 样板间 > 规则：50 行代码胜过 50 条规则

代码模式（样板间）是四层中的核心。文章给了一个真实 CR 对比：开发规范和知识库都已生效、组件用对、请求规范守住的情况下，没有样板间时 Agent 手写 useState、表单表格内联在单文件——功能正确但 CR 打回，因为代码组织跟团队习惯不一样；有了样板间后同样需求产出 `useProTableRequest` 一行接管状态、Form/Table/services 拆分文件——CR 直接通过^[raw/articles/979采纳率胶水编程业务需求出码最佳实践天猫ai-coding实践系列.md]。

原因在于规则的描述力边界：开发规范能写"用 useProTableRequest"这一条规则，但没法描述 formProps 怎么传给 SearchForm、PageContainer 里怎么嵌套——**微观组合模式只有看一份完整代码才能传递**。开发规范是"装修手册"，样板间是"样板间房子"，LLM 是 in-context learner，照代码抄远比按抽象规则写擅长。任务规格过载是样板间缺位的最好证据：一份 329 行的 Plan 文档里有 200+ 行内联代码实现，本质是 Agent 找不到样板间只能写"临时样板间"——胶水编程的核心由此可量化：**AI 的工作量应正比于需求的差异度，而非需求的复杂度**^[raw/articles/979采纳率胶水编程业务需求出码最佳实践天猫ai-coding实践系列.md]。

样板间采用两层继承设计：架构组维护 5 个工作台级样板间兜底（Day 1 覆盖率 100%），域负责人按需 fork 扩展域特有模式。配套的 System Prompt 也变了——AI 从"资深前端专家"变成"代码缝合专家"：先查样板间，复制最像的作骨架，替换字段，只在差异点写新代码^[raw/articles/979采纳率胶水编程业务需求出码最佳实践天猫ai-coding实践系列.md]。

### 97.9% 背后：口径、路径与物料飞轮

97.9% 不是营销口径：分母是周期内所有 CR 合并上线的代码总行数（行级加权），分子是 AI 生成行，明确声明"不按迭代平均，避免大小迭代失真"。提升路径三阶段清晰对应认知升级：~50% 时"让 AI 写代码"（只有知识库，风格随机）→ ~76% 时"让 AI 按规矩写"（AGENTS.md 下发 + 知识库运营）→ 90%+ 时"让 AI 照着抄"（四层齐备）。累计 40+ 个百分点全部来自物料补全，同一基座模型前后产出"判若两人"^[raw/articles/979采纳率胶水编程业务需求出码最佳实践天猫ai-coding实践系列.md]。

这套体系不是一次性重资产，而是内置正循环的物料飞轮：踩过的坑经信号检测 + LLM 提取自动沉淀为领域知识（审核通过率 93.4%，覆盖 30 个仓库）；好的实现经评审提炼为样板间；发现的规范缺失补规则。每个需求还在 `.ai/tracks/` 留下持久化 spec.md，后续 AI 编码同一模块自动读取历史决策——针对 GitClear 报告的"AI 辅助后代码重复率增长 8 倍"，根因正是缺乏全局上下文，Track 让上下文延续。规格同步则走务实中间路线：手动触发、AI 辅助、人确认，不做全自动双向同步^[raw/articles/979采纳率胶水编程业务需求出码最佳实践天猫ai-coding实践系列.md]。

## 实践启示

1. **先盘点"可抄"再谈 prompt**。中后台/CRUD 类业务先问：这个需求的 90% 在代码库里有没有参照？有就建样板间让 AI 抄，比打磨 prompt 的 ROI 高一个量级。
2. **关键规则静态注入，别赌 AI 主动性**。56% 场景 AI 不主动查文档——底线约束必须进 AGENTS.md 全程在场，按需检索只留给补充参考。
3. **四层物料缺一即漏**。理解需求但违反禁用规矩 = 缺规范；守规矩但文件组织乱 = 缺样板间；结构规整但踩私有组件坑 = 缺领域知识。排查 AI 产出问题先定位缺哪层，而不是换模型。
4. **度量口径决定改进方向**。行级加权的 CR 合并口径比"单次会话采纳率"诚实得多；同理，知识库用"调用率 × 采纳率"清理低效条目，物料贵精不贵多。
5. **SPEC 与物料正交，缺一不可**。物料完善后更不能轻视 SPEC——风格统一的代码做错了功能更危险。SPEC 管"做什么"，物料管"怎么做"，这是与 [[concepts/harness-engineering-framework|Harness Engineering]] 中 harness 管执行层的思想相通的。
6. **AI 是团队最大的"新人"**。当知识的消费者从人变成 Agent，口头传递的路径断了——所有隐性知识必须显性化为资产，这才是模型升级也带不走的护城河。
