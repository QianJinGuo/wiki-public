# Measurements for Understanding the Pace of AI Development Inside Frontier Labs

## 摘要

Anthropic 提出度量 frontier lab 发展速度的三维框架：AI 自我自动化程度 / 人类监督能力 / 资源投入，并首次公布内部快照——pacing 讨论的可操作度量基础^[raw/articles/anthropic-measuring-pace-ai-development.md]

## 深度分析

### 为什么度量"模型如何被造出来"与能力评估同样重要

能力评估回答的是"模型能做什么"，而这套框架回答的是"模型是怎么被生产出来的"——即把算力等生产投入与模型能力等产出关联起来，还原 AI 研发的生产函数^[raw/articles/anthropic-measuring-pace-ai-development.md]。这两类信息在治理上承担不同角色：能力评估（通过 RSP 风险报告对外发布）约束单次模型发布，而生产过程度量让外部世界得以观察 labs 的研发速度本身是否在加速，为 pacing（放缓前沿）讨论提供事实底座。两者互补而非替代：一个模型当前能力平平，但若其研发流程已高度自动化，下一代模型的出现速度就可能超出仅看能力评估得出的预期。AAIF 框架中提出的透明度义务（如强制发布风险报告）正是把这类过程度量从企业自愿行为变成政府可要求的外部监测起点。

### AL 自动化分级指数的设计与其"自我裁判"困境

R&D Automation Index 的方法是把公司内每一类 AI 研发工作编目，逐项评定当前的自动化程度，再聚合为单一指数。评级借用 Epoch AI 的 AL0-AL5 量表：AL0 完全无 AI 参与，AL3 为"AI 协作"（在人类紧密指导下完成大块工作），AL4 为"AI 主导"（从高层指令端到端完成大部分任务、人类仅监督），AL5 为完全自主、无人闭环^[raw/articles/anthropic-measuring-pace-ai-development.md]。2026 年 8 月的内部快照显示：Claude 在所有被度量的研发工作中均未达到完全自主运行，"AI 主导"占 26%，而达到"AI 协作"及以上水平的工作超过 90%——这组数字把"距离递归自我改进还有多远"这个抽象问题转译成了可跟踪的量化距离。

但这套指数有一个结构性的利益冲突：Anthropic 在用自己的模型评估自己的系统，充当"裁判"的模型可能与被检查的模型犯同类的错误，导致自动化程度被系统性误估。文章承认的两个跨 lab 比较障碍——缺乏公共方法论、自评偏倚——前者靠统一公开方法解决，后者只能靠第三方验证或其他开发商的模型交叉评级（并加护栏避免交换竞争敏感数据）来缓解。换言之，指数的数值本身是可复现的，但它的"校准权"目前仍掌握在被度量者手中。

### 在线 vs 离线监控：按危害可逆性与时间尺度分解

监督体系的设计逻辑不是"一套监控抓所有问题"，而是按危害的性质把两类监控分开^[raw/articles/anthropic-measuring-pace-ai-development.md]。在线监控在动作执行前实时检查，针对**发生快且不可逆**的危害——典型例子是 agent 把模型权重复制出系统，一旦发生无法撤回，所以必须事前阻断或改向。离线监控在事后读取活动记录，针对**发展缓慢且可逆**的危害——例如模型错位（misalignment）的早期迹象，这类问题需要积累观察才能确认，且发现后有补救窗口。`coverage`（多大比例的动作经过监控）、`review latency`（从动作发生到自动/人工复核的时间）和 `escalation rate`（被阻断/改向或被标记待审的比例）三个指标共同把"监督能力"从口号变成可审计的数字。

截至 2026 年 8 月，Anthropic 内部主力平台上约有 3 万个 agent 同时在做研发与工程工作；两类监控目前对动作的覆盖率均为 100%，被在线监控阻断的动作由人工在一周内复核。文章还指出了一个规模换算问题：单个 agent 的不良行为在内部数据中很罕见，但当经济体中有数百万乃至数十亿 agent 运行时，稀有事件也会常态化发生——监督体系必须为"跨大量 agent 才显现的问题"设计，而不能只做单点防护。

### 什么让这些度量可信：第三方嵌入、跨 lab 可比性与政策触发器

自我报告的数字天然可疑，这套框架的可信度建立在三层机制上。其一是**第三方嵌入**：Anthropic 计划让多家独立机构的评估者入驻，接触与内部风险评估团队相当的流程、系统和数据，由他们验证安全实践、报告事故、复核这些关键指标。其二是**跨 lab 可比性**：任何前沿开发商都可以按公开方法论定期发布同类数字，使指标能随时间追踪、并在 labs 之间横向比较——前提是先解决方法论统一与自评偏倚两个障碍。其三是**政策触发器**：这些度量被明确设计为可以挂接更强要求的开关，例如当自动化指数越过某阈值时，强制新模型在投入 AI 研发前经过固定测试窗口。三者的组合把"lab 说自己很安全"转变为"外部可验证的 paced 开发证据"，这也正是文章预期若前沿形成协调放缓，这些数字应当随之移动的原因。与 [[entities/anthropic-institute-when-ai-builds-itself-jiagoux-interpretation]] 的自我自动化讨论、[[entities/agent-autonomy-levels-l0-l5-addy-osmani-2026]] 的分级框架和 [[entities/mirrorcode-long-horizon-benchmark-epoch-ai-metr]] 的长程基准互为印证。

## 实践启示

1. **为组织建立自己的"研发自动化清单"**：不必照搬 Anthropic 的指数，但可以枚举团队内每类 AI 研发/工程任务，标注其自动化等级与演进趋势——这是判断"AI 在替你工作还是你在替 AI 收尾"的最直接证据。
2. **监控设计先分类危害再选机制**：问两个问题——这个危害是否可逆？它的显现时间尺度是秒级还是月级？不可逆且快的（数据外泄、权重外拷）走事前在线阻断，可逆且慢的（行为漂移、错位迹象）走事后离线审计，两者覆盖面都要报告而非只报其一。
3. **自评指标要预留外部校准通道**：凡是"用自家模型评自家系统"的指标（评审、评级、评测），都应假设存在同源偏倚，提前设计交叉验证或第三方复核路径，而不是等数字被质疑后再补。
4. **把内部度量写成可跨期比较的公开格式**：采用公共方法论 + 定期快照的形式发布，即使不对外，也便于追踪自身自动化率、监督覆盖率随时间的斜率——斜率比单点数值更能预示拐点。
5. **用稀有事件×规模做风险预算**：单 agent 故障率极低不等于安全，按部署总量换算期望事故数（30,000 个 agent 与 30 亿个 agent 对同一故障率的含义完全不同），据此决定阻断策略的严格度。
6. **把度量挂到动作上而非报告上**：为关键指标预设阈值和触发动作（如固定测试窗口、部署收缩），让度量直接接入治理流程，避免指标沦为定期的公关材料。
