### 从 AWS Lambda 走向基于控制面架构的 Unikraft 微型虚拟机

## 演进历程

在 Browser Use ，我们运行着数百万个网页智能体（Web Agents）。起初，我们使用 AWS Lambda 运行纯浏览器智能体，其优势在于每次调用都是隔离的、扩展是即时的，且无需担心密钥安全。 ^[raw/articles/我们如何构建安全可扩展的智能体沙箱基础架构.md]

随后，我们增加了 代码执行 功能。智能体可以编写并运行 Python 代码、执行 Shell 命令、创建文件。我们将此构建为一个被智能体视为“工具”的隔离沙箱。安全性表现良好：代码在沙箱中运行，而非在后端运行。 ^[raw/articles/我们如何构建安全可扩展的智能体沙箱基础架构.md]

但问题在于： 智能体循环（Agent Loop）仍然与我们的 REST API 运行在同一个后端。 重新部署 API？所有运行中的智能体都会崩溃。智能体占用大量内存？API 响应变慢。两种截然不同的工作负载在共享同一个进程。 ^[raw/articles/我们如何构建安全可扩展的智能体沙箱基础架构.md]

## 两种模式

当一个智能体可以执行任意代码时，它理论上可以访问机器上的任何内容：环境变量、API 密钥、数据库凭据、内部服务。因此，它必须与你的基础设施和秘密（Secrets）隔离。实现这一点有两种方式： ^[raw/articles/我们如何构建安全可扩展的智能体沙箱基础架构.md]

- 模式 1：隔离工具（Isolate the tool）。
  智能体运行在你的基础设施上。危险操作（代码执行、终端访问）在独立的沙箱中运行。智能体通过 HTTP 调用沙箱。代码在没有泄露风险的地方运行。 ^[raw/articles/我们如何构建安全可扩展的智能体沙箱基础架构.md]

- 模式 2：隔离智能体（Isolate the agent）。
  整个智能体都运行在一个没有任何密钥的沙箱中。它通过一个持有所有凭据的控制面（Control Plane）与外界通信。 ^[raw/articles/我们如何构建安全可扩展的智能体沙箱基础架构.md]

智能体变成了“即用即弃”的。 没有可窃取的秘密，没有需要保留的状态，你可以随时杀死它、重启它、独立扩展它。控制面掌握着“真相”。 ^[raw/articles/我们如何构建安全可扩展的智能体沙箱基础架构.md]

我们最初采用了模式 1，后来转向了模式 2。

## 沙箱环境

相同的容器镜像在任何地方都能运行。在生产环境中，它作为 Unikraft 微型虚拟机 (micro-VM) 运行；在本地开发和评估（Evals）中，它作为 Docker 容器 运行。通过一个简单的配置开关 (  sandbox_mode: 'docker' | 'ukc'  ) 即可控制环境。 ^[raw/articles/我们如何构建安全可扩展的智能体沙箱基础架构.md]

### 生产环境中的 Unikraft

每个智能体拥有独立的 Unikraft 微型虚拟机，启动时间 不到一秒 。我们通过 Unikraft Cloud 的 REST API 在 AWS 的专用裸金属服务器上进行配置。 ^[raw/articles/我们如何构建安全可扩展的智能体沙箱基础架构.md]

沙箱仅从外界接收三个环境变量：  SESSION_TOKEN  、  CONTROL_PLANE_URL  和  SESSION_ID  。没有 AWS 密钥，没有数据库凭据，也没有 API 令牌。 ^[raw/articles/我们如何构建安全可扩展的智能体沙箱基础架构.md]

Unikraft 提供了开箱即用的 “缩容至零”（Scale-to-zero） 功能。当沙箱空闲时，VM 会挂起；当下一个请求进入时，它会立即恢复。在查询间隙，沙箱几乎不产生费用，但能瞬间唤醒执行后续任务。 ^[raw/articles/我们如何构建安全可扩展的智能体沙箱基础架构.md]

## 深度分析

### 工作负载混杂是架构演化的真正驱动力

文章的起点并不是安全问题，而是耦合问题：智能体循环与 REST API 同处一个后端进程，导致部署、内存、延迟互相牵连。这揭示了一个常见陷阱——团队往往以"加个功能"的方式叠加智能体能力，而忽略不同工作负载（请求式 API vs 长时循环）在生命周期和故障域上的根本差异。Browser Use 从 Lambda 到工具沙箱再到智能体整体沙箱的迁移路径，本质上是不断切割故障域和扩展单元的过程。

### 模式 2 的本质是把信任边界与状态所有权对齐

隔离工具（模式 1）只移动了危险代码的执行位置，智能体进程本身仍握有基础设施的入口；隔离智能体（模式 2）则把整个智能体推进无密钥环境，凭据收敛到控制面。其深层收益是"可抛弃性"：因为沙箱内既无可偷的秘密也无须保留的状态，杀死、重启、独立扩展都成了零成本操作。控制面成为唯一的"真相持有者"，会话状态（如完整对话历史）集中在数据库而非运行时中，这使得任何一层都可以无状态地水平扩展。

### 同一镜像跨环境运行消解了"生产漂移"

用 `sandbox_mode: 'docker' | 'ukc'` 一个开关切换 Docker 与 Unikraft micro-VM，配合相同的入口点和控制面协议，意味着开发、评估、生产执行的是字节级一致的代码路径。这比"本地模拟一套简化版"的模式可靠得多——评估结果对生产行为的预测力直接取决于环境同构程度。Gateway Protocol 这类接口抽象（生产走 HTTP 控制面、开发直连内存实现）让智能体代码对后端差异完全无感，是支撑这种同构的关键工程手段。

### 安全设计是纵深防御而非单点防线

沙箱的加固链条环环相扣：构建期删除 .py 源码只留字节码（提高逆向与篡改门槛）、root 启动后立即 setuid/setgid 降权、读取三个环境变量后从 `os.environ` 中抹除、VM 置于私有 VPC 且令牌离开控制面通信即失效。任何一层被绕过，下一层仍然兜底。这与"给沙箱发一个长期密钥"的常见做法形成鲜明对比——短期会话令牌 + 最小暴露面 + 网络隔离的组合，把单次泄露的爆炸半径压到接近于零。

### 权衡的诚实账本：多一跳网络 vs 可忽略延迟

模式 2 并非免费：每次外部交互多一跳网络，且要部署三个服务而非一个。但作者的账算得很清楚——相对 LLM 秒级响应，代理跳转延迟可忽略；运维复杂度在团队能力范围内。架构决策的关键不是罗列优缺点，而是把成本放到具体负载的量纲里比较。这一权衡框架适用于所有"是否引入中间层"的决策。

## 实践启示

1. **尽早分离智能体循环与 API 后端**：如果智能体循环与业务 API 共享进程，先拆为独立部署单元——这比任何安全加固都更早成为扩展瓶颈。
2. **优先考虑"隔离智能体"而非"隔离工具"**：只要智能体可执行任意代码，就应让它运行在无密钥环境中，凭据统一收敛到控制面；后者的代理模式（LLM、文件、计费）可以渐进建设。
3. **让沙箱"不值得被攻击"**：注入的环境变量读完即从 `os.environ` 删除，令牌设计为短会话生命周期，VM 放入无出网权限的私有网络——目标是沙箱内不存在任何泄露后仍有价值的东西。
4. **用配置开关统一开发与生产镜像**：同一镜像通过 `docker | micro-vm` 开关切换运行时，配合接口抽象（如 Gateway Protocol），确保评估环境与生产行为同构。
5. **状态外置以换取可抛弃性**：会话历史、文件（经预签名 URL 同步到对象存储）全部放在沙箱之外，沙箱随时可杀可重建——这是实现每会话独立 micro-VM 与缩容至零的前提。
