# Retrieval-Augmented Generation (RAG)

> RAG = Retrieval（检索）+ Augmentation（增强）+ Generation（生成）

RAG 是将外部知识检索与 LLM 生成结合的技术架构，旨在解决 LLM 的幻觉问题和知识时效性问题。本文综合多篇实体文档，梳理 RAG 从简单向量检索到知识图谱增强的技术演进路径。

## 一、传统向量 RAG 的局限性

### 1.1 向量库的核心缺陷

向量库（Vector Store）作为早期 RAG 的标配组件，其本质缺陷在于**将知识压缩为孤立的"语义点"**：

| 问题类型 | 具体表现 | 后果 |
|---------|---------|------|
| **上下文割裂** | Chunking 过程中对原始文档完整性的破坏 | 关键信息被分隔，如"适用症"与"妊娠期禁用"被分开 |
| **信息淹没** | 长文本向量需要概括过多信息 | 稀释核心语义，难以在相似性搜索中被选中 |
| **语义脆弱性** | 依赖"语义相似性"而非"关系推理" | 断章取义，医疗/法律场景存在严重安全隐患 |

典型失败案例：
- 电商"退款助手"场景：RAG 只召回"T+1"，遗漏"黑名单/已发货订单除外"，导致误退款
- 医疗场景：临床指南按段落切分，"适用症"与"妊娠期禁用"提示被分隔

### 1.2 向量库的适用范围

向量库并非 RAG 的必须选择，它更适合作为：
- **模糊问法的补充检索工具**
- **非结构化内容的预筛选层**
- **与关键词检索、规则路由混合使用**

真实系统往往是：**关键词路由 + 向量检索 + 图谱查询的混合体**。

## 二、知识图谱的范式价值

### 2.1 知识图谱 vs 传统知识库

| 维度 | 传统知识库 | 知识图谱 |
|------|-----------|---------|
| **存储结构** | 表结构（数据库表） | 图结构（实体-关系-属性） |
| **认知模式** | 点状/分类存储 | 网状/关系推理 |
| **扩展性** | 新关系需修改数据库模式 | 新三元组低成本添加 |
| **推理能力** | 有限 | 可追溯的推理链 |

知识图谱的三大元素：
1. **实体（Entities）**：图中的节点，代表真实世界的事物、概念
2. **关系（Relations）**：实体之间的连接，描述互动
3. **属性（Attributes）**：描述实体或关系的特征

### 2.2 知识图谱的演进路径

```
CDSS阶段（AI 1.0）→ 向量RAG阶段 → GraphRAG阶段
纯规则驱动           语义检索         图谱+LLM结合
泛化能力不足         上下文割裂       置信度验证
```

## 三、GraphRAG 架构

### 3.1 三层防御体系

GraphRAG 通过路由、查询规划形成自上而下的三层防御：

```
┌─────────────────────────────────────┐
│          置信度验证层                │
│   >90% 直接输出，否则专家复核       │
├─────────────────────────────────────┤
│          图谱推理层                  │
│   复杂、多模态、涉及实体关系的问题   │
├─────────────────────────────────────┤
│          RAG 基础层                  │
│   简单、标准查询                     │
└─────────────────────────────────────┘
```

### 3.2 医疗置信度的四个维度

| 维度 | 含义 |
|------|------|
| **数据溯源** | 每条诊断结论可追溯到权威指南、临床文献 |
| **一致性** | 多模态数据（症状、检查、影像）推理结果一致 |
| **动态性** | 实时更新最新医学研究和临床指南 |
| **可解释推理链** | 附带详细判断依据和证据来源 |

## 四、本体论的核心作用

### 4.1 本体论定义

本体论（Ontology）在 AI 知识系统中，核心职责是**表述这个世界应该如何被定义**：

```json
{
  "实体类型": ["疾病", "症状", "药物", "检查", "指南", "禁忌证", "适应证"],
  "允许关系": [
    "疾病表现为症状",
    "药物治疗疾病", 
    "药物禁用于某类人群"
  ],
  "语义强度": ["因果", "相关", "并发", "风险提示", "弱关联"],
  "推理规则": ["哪些关系可传递", "哪些不能", "哪些结论需结合证据等级"]
}
```

### 4.2 本体论 vs 知识图谱

| 概念 | 角色 | 价值 |
|------|------|------|
| **知识图谱** | 知识的呈现形式 | 一张网 |
| **本体论** | 网背后的建模逻辑 | 定义规则 |

> 没有本体论的图谱是"没有 KnowHow 的骨架"——高风险行业（医疗、法律、金融）不能仅靠 LLM 自动抽取三元组，必须有领域专家参与本体论建设。

### 4.3 关系语义强度示例

```json
{
  "二甲双胍 —— 治疗 —— 2型糖尿病": "明确适应证，置信度高",
  "二甲双胍 —— 可能导致 —— 体重下降": "临床观察或副作用层面的关联",
  "二甲双胍 —— 通过AMPK通路影响 —— 代谢调节": "作用机制层面的解释"
}
```

三条关系都对，但医学含义完全不同，没有本体论会被粗暴理解为"二甲双胍可以减肥"。

## 五、工程实践与未来方向

### 5.1 重新评估向量库定位

向量库不应再被视为 RAG 的"标配"，而应是：
- 模糊问法的补充检索工具
- 非结构化内容的预筛选层
- 与关键词检索、规则路由混合使用

### 5.2 知识图谱构建优先级

对于高风险行业（医疗、法律、金融）：
1. **先建本体论**：明确实体类型、关系语义、推理规则
2. **再建图谱**：基于本体论构建领域知识网络
3. **最后引入 LLM**：用 LLM 增强图谱的构建效率和推理能力

### 5.3 未来演进方向

从"检索增强"走向"推理增强"：
- 未来的 AI 知识系统将不再显式区分组件
- 将知识系统内化为 Agent 的自主规划、多步推理、自我校验能力
- Google NotebookLLM 的技术路径可能是方向之一
