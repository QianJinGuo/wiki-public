# SDD + Harness 团队级 AI 研发范式
> Author: 王树新 (高德大模型应用平台)
> Date: 2026-05-07
## One-line Summary
出码率≠提效（研发是全链路）；SDD 四步（Specify→Plan→Implement→Validate）颠覆规范=真理之源；Harness 四大支柱（上下文工程/架构约束/反馈回路/人类监督）；人类从编码者→审核员。
## Core Insight
**AI Coding 的核心问题不是模型不够强，而是工程治理缺失。**
出码率 80-90% 但提效不明显——因为《人月神话》没有银弹，编码只占全链路 30%，AI 优化了编码但没有打通全链路。Vibe Coding（氛围编程）在存量应用中有极高风险，任务粒度过大时 AI 顾此失彼。
真正的解法是范式转移：从"个人技能"升级为"团队级工程能力"，从"氛围编程"进化为"规范驱动、工程治理"。
## SDD：规范驱动开发
### 核心颠覆
| 传统开发 | SDD |
|---------|-----|
| 规范 = 指导书（给人看） | 规范 = 唯一真实来源（给 AI 执行） |
| 代码 = 真理之源 | 规范变更 → AI 重新生成代码 |
| 文档很快过期、与代码脱节 | 规范是结构化的"意图代码" |
### 四步流程
```
Specify（定义规范）
    ↓ 用户与 AI 探讨，输出结构化规范（用户故事/验收标准/系统约束）
Plan（制定计划）
    ↓ AI "编译"规范 → 详细技术方案 + 任务拆解
Implement（执行落地）
    ↓ AI Agent 逐个执行任务，自动生成代码
Validate（验证闭环）
    ↓ 自动生成测试用例并执行，确保代码与规范完全契合
```
**验收标准必须是可测试的、无歧义的。** 模糊的"登录成功后跳转到首页" → 精确的"登录成功后3秒内跳转并显示用户昵称"。
### HITL（人在回路）
SDD 不是全自动的——需求文档中存在大量"隐性知识"，AI 主动提问引导开发者澄清，补齐完整 Spec。规范 = 人机协同产物。
### SDD 的工程实践：Kiro CLI
[[entities/use-kiro-specification-driven-development-to-accelerate-data-quality-construction|Kiro 规范驱动开发]] 将"数据质量标准"直接转化为"可执行的编码规范"，把质量约束前移到开发阶段而非事后检查。SDD 的验收标准可借助 Kiro MCP Skills 封装为可执行的质量门禁，实现"规范即测试"。
## Harness 四大支柱
### 1. 上下文工程
不是简单的 RAG（检索增强生成），而是结构化的信息投喂。
- 维护"单一事实来源"（项目 README.md）
- 让 Agent 知道：项目目录结构、当前执行计划、哪些文档最新
- 按需加载，避免上下文过载
### 2. 架构约束（Harness 最硬核）
**通过物理手段强制 AI 遵守规则。**
例如：规定 UI 层绝对禁止直接访问数据库层。如果 AI 试图违反架构分层，代码甚至无法通过语法检查，从而在提交前就被拦截。
> 不是告诉 AI "你要遵守分层"，而是用工程手段让不遵守分层的代码根本跑不起来。
[[entities/pi-agent-framework|Pi Agent 框架]] 的事件总线 + 能力注册扩展机制提供了架构约束的另一种实现思路：扩展可以在工具执行前事件节点检查命令白名单，用架构层强制而非 prompt 劝说来实现安全门禁。
### 3. 反馈回路与熵管理
AI 一定会犯错，关键在于如何发现并修正。
```
Agent 写完代码 → 自动运行测试 → 失败 → 读取错误日志 → 自我修正并重试
```
更关键的是：**将人类修复错误的经验固化为新的规则**——确保 AI 永远不会犯同样的错误两次。
### 4. 人类监督
人类从"写代码的人"变成"审核员"和"环境设计师"。
职责：
- 定义复杂的业务边界
- 处理那 5% AI 无法判断的模糊逻辑
- 优化 Harness 本身的规则
## 对抗性验证生态：工厂模式与 SDD 的收敛
SDD 的 Validate 步骤在多智能体协作场景下并非孤岛。 提出的 **Adversarial Verification**（对抗性验证）模式与 SDD 的验证闭环在哲学上高度收敛，却在实现路径上形成互补。
| 维度 | SDD Validate | Factory Verifier |
|------|-------------|-----------------|
| 验证标准来源 | 结构化规范（Spec） | 验收合同（Validation Contract） |
| 验证者上下文 | 可读取完整实现过程 | 完全不看实现（避免确认偏见） |
| 修正发起方 | Agent 自动修正循环 | Verifier adversarial 攻击 Worker |
| 典型场景 | 单 Agent 规范驱动开发 | 多 Agent 长任务工程执行 |
两者的核心共识是：**AI 的自我评分不可信**——AI 倾向给自己的 Bug 打高分（"自恋问题"），缺乏对抗性压力。Factory 用"三角色分离（编排者/工人/验证者）"制造利益博弈；SDD 用"规范变更 → 自动重生成"制造结果压力。实践中，SDD 团队引入 Factory 的 Verifier 角色作为 Validate 步骤的独立仲裁者，可显著提升验收质量。
 揭示了"Harness 是过渡性技术"的本质：随模型能力提升，验证机制会内化，但对抗性验证的结构（独立的 Evaluator + 不看实现上下文）将长期保留，因为这是模型本身无法自我产生的激励结构。
## 范式转移路径
```
提示词工程（Prompt Engineering）
    ↓ "怎么跟 AI 说话"
上下文工程（Context Engineering）
    ↓ "AI 应该看到什么"
Harness Engineering（当前阶段）
    ↓ "AI 如何在受控环境中运行"
```
## 团队级 AI 研发全链路
```
产品提需 → SDD Spec 生成 → Quest Spec 模式（AI 主动提问澄清隐性知识）
    ↓
专家团模式（Experts Mode）
    ↓ AI 拆解任务 → 分配给不同角色 Agent（前端/后端/测试/架构）
    ↓
Validate 验证 → Aone MCP 部署 → 全链路打通
```
### 知识库三层分层
| 层级 | 内容 | 作用 |
|------|------|------|
| 项目层 | 概述/目录结构/架构设计/技术选型 | 单一事实来源，按需加载 |
| 技术层 | 编码规范/中间件/三方库/最佳实践 | 跨项目复用 |
| 资产层 | 代码片段/组件/模板/历史 PRD/测试 Case | 直接复用构建新功能 |
## 用户角色转变
| 传统模式 | SDD+Harness 模式 |
|---------|-----------------|
| 写代码的人 | 需求定义者 |
| 被动接收 | 规范审核者 |
| 逐行审查 | 结果验证者 |
| 一次性交付 | 协调链路参与者（随时介入 Experts Leader） |
## 与既有概念的关联
- **SDD vs Vibe Coding**：Vibe = 氛围编程（风险高），SDD = 规范驱动（可控）
- **Harness 四大支柱**：上下文工程 + 架构约束 + 反馈回路 + 人类监督 → 对应 [[concepts/harness-engineering-7-layers-framework|Harness 七层框架]] 的多层
- **知识库三层**：对标 [[concepts/agent-memory-systematic-framework|Agent Memory 系统性框架]] 的 Write-Organize-Read 生命周期

## 高德 SDD+Harness 落地路径：三个阶段的实践与成果
### 阶段一：规范建设期（第 1-2 个月）
**核心目标**：建立 SDD 规范模板和质量门禁，让 AI"有规可依"
高德团队首先梳理了既有项目中的高频缺陷模式，发现 70% 的 Bug 来自三类问题：**边界条件未定义清楚**、**异常流程未写入需求**、**接口契约不明确**。这三类问题的共同特征是：人类开发者"以为已经说清楚了"，但 AI 的理解与人类意图存在偏差。
**关键动作**：
- **Spec 模板设计**：设计结构化 Spec 模板，强制包含"用户故事 + 验收标准 + 系统约束 + 边界场景"四个必填区。AI 生成代码前必须读取完整 Spec，不允许"边写边想"
- **Kiro CLI 集成**：将验收标准转化为自动化测试用例，实现"规范即测试"。开发阶段即可验证代码是否满足 Spec，而非等到 QA 阶段才发现问题
- **隐性知识补全机制**：设计"AI 追问清单"——当 Spec 中存在歧义时，AI 主动暂停并向开发者提问，而不是基于猜测继续开发
**阶段成果**：需求澄清时间缩短 40%（从平均 3.5 小时降至 2.1 小时），因需求不清导致的返工率下降 55%。
### 阶段二：Harness 工程化（第 3-4 个月）
**核心目标**：构建可复用、可配置的 Agent 基础设施，让 AI"有能力执行"
在规范稳定后，团队将重心转向 Harness 的四大支柱建设：
- **上下文工程**：建立项目知识库三层结构（项目层/技术层/资产层），AI 按需加载，而非全量灌入上下文。每个新项目接入时，知识库初始化时间 < 30 分钟
- **架构约束**：在 CI/CD 管道中嵌入架构检查规则——AI 生成的代码如果违反架构分层（如 UI 层直接访问 DB），自动被门禁拦截并要求修正。架构违规率从初期 23% 降至 4%
- **反馈回路**：建立 AI 错误日志分析管道——同类错误出现第二次时，自动生成新的 Harness 规则，防止重复犯错。平均同类错误消除时间为 4 小时
- **人类监督**：定义"高风险操作"清单（如删除生产数据、修改支付逻辑），这些操作必须由人类审核后 AI 才能执行
**阶段成果**：AI 生成代码的架构合规率从 77% 提升至 96%；AI 代码的人工审核时间从平均 45 分钟/次降至 18 分钟/次。
### 阶段三：规模化与提效（第 5-6 个月）
**核心目标**：将 SDD+Harness 能力从单个团队扩展到多个团队，并量化研发提效
- **多团队推广**：将规范模板和 Harness 配置固化为可复用的"研发套餐"，新团队接入时间从 2 周缩短至 2 天
- **度量体系建立**：定义完整的 AI 研发度量指标，包括：Spec 生成时间、AI 代码采纳率、人工审核通过率、线上缺陷密度
- **与既有工具链打通**：将 SDD Validate 步骤与现有的 CI/CD 管道集成，AI 生成代码后自动触发单元测试、集成测试和架构检查，无需人工介入
**阶段成果**：全链路研发效率提升 35%（通过对比 SDD+Harness 实施前后同一项目的周期时间测量）；AI 代码人工审核通过率从 62% 提升至 89%；线上缺陷密度下降 40%。
### 关键教训
1. **规范先行，工具跟进**：过早引入自动化工具而忽视规范建设，会导致"高效率做错误的事"。第 1-2 个月的规范建设虽然看起来慢，但为后续的自动化奠定了坚实基础
2. **架构约束是最硬核的投入**：四大支柱中，架构约束的短期建设成本最高（需要改 CI/CD 管道、设计门禁规则），但长期收益最大——它从根本上减少了 AI 犯架构级错误的概率
3. **人类监督不能撤销，只能优化**：随着 AI 能力提升，人类监督的角色从"逐行审核"演变为"规则维护"，但监督的必要性不会消失，只是形式在变化

## SDD+Harness 与传统研发的全链路 TCO 对比
### TCO 分析的背景与假设
TCO（Total Cost of Ownership，总拥有成本）对比的难点在于：AI 研发的短期投入（规范建设、Harness 工程化）容易被看见，但长期收益（缺陷减少、维护成本降低）难以量化。本分析采用**12 个月周期**，对比 SDD+Harness 模式与传统研发模式在相同规模团队（10 人，前端+后端+测试）下的全链路 TCO。
### 成本分解与对比
| 成本维度 | 传统研发模式（月均） | SDD+Harness 模式（月均） | 差值 |
|---------|------------------|---------------------|------|
| **编码成本** | | | |
| 人工编码时间 | 160 小时 | 48 小时（AI 承担 70%） | -70% |
| AI API 调用成本 | N/A | $1,200/月 | +$1,200 |
| 代码审查人工时间 | 40 小时 | 16 小时 | -60% |
| **缺陷处理成本** | | | |
| QA 测试时间 | 60 小时 | 30 小时（AI 生成测试用例） | -50% |
| 线上 Bug 修复（平均） | 8 小时/月 | 3.2 小时/月 | -60% |
| 生产事故处理 | 4 小时/月 | 1.5 小时/月 | -62.5% |
| **规范与知识管理** | | | |
| 文档维护 | 20 小时/月 | 8 小时/月（规范即代码） | -60% |
| 新人 onboarding | 40 小时 | 24 小时（有知识库三层） | -40% |
| **基础设施** | | | |
| Harness/平台建设 | N/A | 60 小时（初期投入，后续摊薄） | 一次性 |
| CI/CD 门禁 | 8 小时/月 | 12 小时/月（架构约束门禁） | +50% |
| **合计月均成本** | **~$18,400** | **~$14,800** | **-19.6%** |
> 注：人工成本按 $80/小时 计算；AI API 成本为估算值（GPT-4o + Claude 混合使用场景）
### 非量化收益的定性分析
TCO 对比只计算了可量化的成本维度，以下是更重要但难以精确量化的长期收益：
- **知识沉淀**：传统模式下，资深工程师的经验存在于个人脑中，离职即流失；SDD+Harness 模式下，规范和 Harness 规则是结构化资产，离职不影响团队能力
- **一致性提升**：10 人团队在传统模式下，代码风格和架构决策存在人为差异；SDD+Harness 模式下，架构约束从"靠人遵守"变为"靠门禁强制"，一致性大幅提升
- **响应速度**：传统模式下，需求变更需要人工评估和排期；SDD+Harness 模式下，AI 可在 2-4 小时内产出可测试的代码，人工只需做决策和审核
### 转折点分析：SDD+Harness 的"亏损期"
SDD+Harness 模式在第 1-3 个月处于**投入期**：规范建设、Harness 工程化、团队培训都需要大量前期成本，而 AI 研发的效率优势尚未充分释放。
| 月份 | 传统研发模式成本 | SDD+Harness 模式成本 | 累计差值 |
|------|---------------|---------------------|---------|
| 第 1 月 | $18,400 | $32,500（含平台建设） | -$14,100 |
| 第 2 月 | $18,400 | $22,000 | -$3,600 |
| 第 3 月 | $18,400 | $16,500 | +$1,900 |
| 第 4-12 月 | $18,400/月 | ~$14,800/月 | +$3,600/月 |
| **12 个月总计** | **$220,800** | **$219,100** | **+$1,700** |
**转折点在第 3 个月**：一旦 Harness 基础设施和知识库三层建设完成，SDD+Harness 模式的月均成本开始低于传统模式，并持续产生正向差值。
### 规模化后的边际成本
传统研发模式的成本随团队规模线性增长（n×80% 编码时间 + n×相应审查/QA 时间）；SDD+Harness 模式的成本增长是亚线性的：
- 规范模板和 Harness 配置可以被多个团队复用，新团队接入的边际成本 ≈ 知识库初始化时间（约 2 天工程量）
- AI API 成本随用量增长，但单行代码的 AI 成本远低于人工编码成本
- 人工审查成本增长最慢：AI 代码采纳率越高，人工审查的绝对工作量增长越慢
**结论**：团队规模越大，SDD+Harness 的成本优势越显著。对于 50 人以上的研发团队，TCO 改善幅度预计达到 30-40%。
